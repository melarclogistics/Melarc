# Published protocol vectors

The vectors both sides of the rider device protocol hold themselves to ([SECURITY_DESIGN.md](../../../../architecture/SECURITY_DESIGN.md) §13.6), and the chains the API is held to the real verifier service by (§15.2). The Node tests under `apps/api/src/platform/auth/` read them; the Rider app's tests read the same files, and the protocol counts as interoperable only when they pass on both sides.

| File                         | Holds                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | Made by                                                                                                                                                                    |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `enrolment-uri.v1.json`      | the valid version-1 QR payloads (127 characters) and each way of being wrong                                                                                                                                                                                                                                                                                                                                                                                                                                                       | `node generate-enrolment-uri-vectors.mjs > enrolment-uri.v1.json`                                                                                                          |
| `device-key.v1.json`         | public keys and signatures, valid and not: encodings, the signed message, a double hash, DER against P1363                                                                                                                                                                                                                                                                                                                                                                                                                         | `java GenerateDeviceKeyVectors.java > device-key.v1.json`, on the JDK the verifier service is pinned to                                                                    |
| `attestation-chains.v1.json` | the Android key-attestation chains the API sends to the real verifier service in `rider-device-enrolment-attested.db.test.ts`, one for each class of evidence the acceptance criteria name (a hardware-attested key; a software one; the wrong package or signer; an unknown root; revoked certificates; an appended extension; another challenge; an unlocked or unverified device; another key), with the challenge each carries, the key to submit, the service settings the chains assume and the verdict the policy must give | `./gradlew :service:attestationVectors` in `apps/attestation-verifier`, from the verifier's deterministic fixtures; `AttestationVectorsTest` holds the file to a fresh run |

The generators are deterministic, so a second run gives the same bytes; the generator of the keys and signatures checks every vector against its own intent before it writes it, and stops on a vector the Java security API disagrees with. The files hold no private key. A vector is added by changing the generator and regenerating, never by editing the file.
