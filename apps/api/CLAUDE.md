# API (`apps/api`)

NestJS modular monolith. It holds the technical platform and, since S0.31, the credential setup, sign-in and second-step routes of `src/platform/auth/staff/` (the first product routes): `src/tools/contract/implemented-scope.ts` lists the operations that exist. Run and test it as [DEVELOPMENT.md](../../DEVELOPMENT.md) says; what each bootstrap task left undone is in the runbook ([B0.2 and B0.3](../../delivery/planning/BOOTSTRAP_B0_RUNBOOK.md#carried-forward-from-b02-and-b03), [B0.6](../../delivery/planning/BOOTSTRAP_B0_RUNBOOK.md#carried-forward-from-b06)).

## Layout

- `src/platform/`: technical infrastructure (audit, auth, config, contract, database, delivery, execution, health, http, idempotency, lifecycle, limiter, logging, metrics, openapi, routes, settings). Its production files may import packages and each other, but no relative import may leave `src/platform/` (`src/architecture.test.ts` fails otherwise; test files are exempt).
- `src/platform/auth/ports/`: the ports `platform/auth` reaches domain data and I/O through ([architecture §5](../../architecture/SOLUTION_ARCHITECTURE.md#5-module-boundaries)), each an interface, a token and a descriptor. `src/app.module.ts` binds adapters to the tokens; an adapter (a `*.adapter.ts` file, or any file that implements a port) is imported only by the composition-root files `src/architecture.test.ts` lists, never by a module for being a module. A new adapter is also added to `ALLOWED_PORT_IMPLEMENTATIONS` and `ADAPTED_PORTS` there, and bound as a singleton with no `scope`.
- `src/platform/auth/crypto/` and `credentials/`: the S0.3 adapters (hashing, tokens, TOTP, sealed values), `randomUUIDv7` and the credential and work-email rules. They are not bound in the runtime composition until the task that consumes each port binds it ([plan §7.4](../../delivery/planning/SLICE-000-IMPLEMENTATION-PLAN.md#74-carried-from-s03)).
- `src/<domain>/`: one module per permission domain, siblings of `platform/` ([architecture §5](../../architecture/SOLUTION_ARCHITECTURE.md#5-module-boundaries)). A new domain needs a Product Owner decision. Domains depend on platform, never the reverse. `pickup` and `fleet` import nothing of each other: they meet over a run through the two ports of `platform/domain-ports/` (a port takes the caller's transaction handle and opens none; `src/domain-ports.module.ts` wires them; `architecture.test.ts` pins it), and only a schema file may name the other's schema, for a foreign key. A new pair that must meet does the same, and the crossings that predate this are OB-S1-47. The read that counts queues (`getQueueSummary`) and the read that finds a record (`lookupRecords`, task C2) call the domains' counters and record sources the same way (`platform/queue-summary/`, `platform/lookup/`; ports `queue-counter.port.ts` and `record-lookup.port.ts`), each kind or queue under the key of its own read. `lookupRecords` is a POST that changes nothing (its text is in the body and never in a URL: the Product Owner, 6 November 2026), so it runs through `OperationRunner.mutate`, the one door the runner leaves a request of a method that is not safe, takes the session's CSRF protection like any staff POST and no `Idempotency-Key`; its name search of pickup requests covers current work only (`NAME_SEARCH_WINDOW_DAYS`, `pickup-record-lookup.adapter.ts`). `permission/`, `settings/` and `staff/` hold the S0.35 reads and, in `staff/`, the S0.36 and S0.37 mutations (a controller, a service and a provider each; `productRoutes: false` leaves their modules out): a read runs through `OperationRunner.read` in the caller's own context (a staff read learns the second-factor facts only through `melarc.staff_reset_facts`, at `REPEATABLE READ`), a hub-scoped table gets its policy, probe policy and `RECORD_ENTITIES` row together, and `listSessions` records one `auth.hub_boundary.crossed` per foreign hub it shows, a tier that depends on a query value is `tier.byQuery` and decides before the validation, a note a person gives is checked by `checkedNote` before the work and recorded once on the operation's primary event, a session outside the caller's hubs is told from an absent one by the hub-set probe, and a mutation runs through `OperationRunner.mutate` in the caller's own staff context, admitted by a policy that names **the authorization key of the operation** (migrations `0029`, `0030`; [plan §7.34](../../delivery/planning/SLICE-000-IMPLEMENTATION-PLAN.md#734-carried-from-s036-and-s037-22-and-23-october-2026)): it locks the identity first with `lockStaffIdentity` (`melarc.staff_locked_facts`, `READ COMMITTED`, which also binds `melarc.locked_identity`, the only thing the policies that read or change a grant or a delivery job name, since the worker reads those tables and not `staff_identity`), compares `If-Match` against the ETag recomputed after the lock, and revalidates; never run a staff operation under `authentication`, spoof `staff.read`, or open a mutation at a stricter level. The maker-checker refusal of `approveStaffIdentity` (`SELF_APPROVAL_FORBIDDEN`) stays the last refusal and does not apply when the acting grant is at tier P (`meetsTier(authorized.grant?.tier, 'P')`, a Platform Admin; the Product Owner's decision of 25 October 2026, [permissions.md](../../contracts/permissions.md) §6); the trigger `staff_identity_transition_checker` (migration `0032`) holds the same rule for every writer, by the maker's own bundle grant. `dispatch/` holds the rider roster (S0.53: `listRiders` and `getRider`, `dispatch.read`, scoped through each rider's primary hub; the record's `ETag` is the version `reregisterRiderDevice` takes) and `staff/` the rider's device acts (S0.57, S0.58: `registerRiderDevice` and `reregisterRiderDevice` issue the enrolment grant, the first with the sealed idempotent replay and a refusal of a rider who holds or held a device, the second under `If-Match`; `revokeRiderDevice` takes neither and is a no-op for a rider with no `ACTIVE` device; a `SUSPENDED` or `OFFBOARDED` rider is given no binding). `fleet/` holds the run custody handover (S1.24: five operations, `src/fleet/`; the origin is read with `melarc.run_custody_holder`, never sent; `fleet` uses seven named files of `pickup` and `pickup` imports nothing of `fleet`, which `architecture.test.ts` holds); a run in progress with nothing left is completed by the system in the transaction of the act that left it so (`src/pickup/pickup-run-completion.ts`, S1.23: the stop's lock, then the manifest's, only for a run in progress, with the stops counted after the lock), and the stop columns (`STOP_COLUMNS`) give a non-staff principal a skip without its note. **Queue counts (C1)**: `getQueueSummary` (`src/platform/queue-summary/`, a `self` read, `background`, each count bounded at 3 seconds by `statement-limit.ts`, `AC-QSUM-13`) asks the `QueueCounter` of each domain (the port is `src/platform/domain-ports/queue-counter.port.ts`, bound in `src/domain-ports.module.ts`, implemented by `src/pickup/pickup-queue-counters.adapter.ts` and `src/staff/staff-queue-counter.adapter.ts`) under the context of the grant of **that queue's list key** (`authorizationForKey`), never a wider one; a count and its list call one function for the filter, the hub (`hub_id`, task C3) included, which is a statement parameter and never part of the context (`src/pickup/pickup-request-criteria.ts`, `src/pickup/pickup-manifest-criteria.ts`, `src/staff/staff-identity-criteria.ts`), so change the filter there, hold it with `test/database/queue-summary.db.test.ts` (count equals list for an officer, Senior Ops and Platform Admin), `test/database/hub-filters.db.test.ts` (the hub: partition, sum and hand-written figures, so that a hub lost from the one function both call is seen) and `test/database/pickup-request-criteria.db.test.ts` (the planner-shaped criteria against the plain definition), and read a plan at scale before adding a count. A staff caller's `hub_id` outside the set of the key's grant is answered with no transaction and no statement (task A1: `hubOutsideStaffGrant`, `src/platform/authorization/authorized-request.ts`, decided key by key in the summary), because the time of a walk of that hub's index would tell whether the hub exists and how much it holds; a Vendor's list of requests and a Rider's list of runs name what they own in the statement (`ownedByCaller`) so that the planner starts from their index and not the hub's, and a Rider's list of requests judges the hub and does not apply it. `test/database/alone/hub-filter-timing.db.test.ts` holds the time at 200,000 rows.
- `src/tools/`: command-line tools that run from `dist`. `migrations/`: the one canonical migration history (Drizzle). `test/`: process and database tests.

## Rules

- Keep layers apart: controller, application service, domain rules, persistence. A controller never calls another controller, and no business operation bypasses its service.
- Implement an operation contract-first ([plan §7](../../delivery/DEVELOPMENT_EXECUTION_PLAN.md#7-contract-first-implementation)). Each ships negative-access tests ([standards §3.1](../../standards/engineering-standards.md#31-negative-access-tests-are-mandatory-at-five-surfaces)) and tests of its own headers, cookies and status and error pairs ([B0.6 notes](../../delivery/planning/BOOTSTRAP_B0_RUNBOOK.md#carried-forward-from-b06)).
- An operation exists only when its `operationId` is in `IMPLEMENTED_OPERATIONS` and its handler carries `@ContractOperation(id)` (`src/platform/contract/contract-operation.ts`), in the same change; `pnpm run contract:check` fails on any disagreement. A DTO class cannot state `additionalProperties: false`, `if`/`then` or `allOf`: give an explicit schema with `@ApiBody({ schema })`. The description also states what a decorated class cannot (`src/platform/openapi/operation-statements.ts`, the implementation's own account, compared with the contract and never copied from it): credentials with `DescribeSecurity` (each argument an alternative, the schemes inside it all required; no argument is an explicit anonymous `security: []`, and an operation that states nothing inherits the default posture, a browser session with its CSRF token or a rider session), the cookies of a response with `DescribeCookies`, and a Rider operation's hosts with `DescribeServers(RIDER_SERVERS)`. Write a cookie only through `src/platform/auth/cookies/cookie-writer.ts` (`Max-Age=0` literally on expiry; the vendor device cookie is never expired). An error code and its status come from `ErrorCode` and `statusOf` (`src/platform/http/error-codes.ts`, all 123 codes); `SETTING_MISSING` and `SETTING_INVALID` have no decided status, and `ApiException` sets only the headers the contract declares on an error.
- Every route must declare how it is reached (`src/platform/routes/access-declaration.ts`): `@TechnicalEndpoint()` for probes only, never on a business route, or `@Anonymous(limit?, client)`, `@Self(options)` or `@RequiresPermission(key, options)`, each of which also states the same fact in the description; the last two name the surfaces they serve and an activity policy (`qualifying` or `background`; a route with none stops the API at start) and may name a record whose existence rule the guard applies (for the callers of some of the surfaces it serves only, `record.surfaces`: `acceptRunCustodyHandover` asks staff which hub and leaves a rider to be told `NOT_ASSIGNED_RIDER` by the operation) and a `tier` (a minimum, and a rule that derives what the record needs) that the guard decides at step 6, before the scope and the validation. An undeclared route stops the API at start, and is refused `403` if one is ever served. The guards run in the order of `guard-chain.ts`: declaration, rate limit, authentication, CSRF and Origin, authorization. The rate-limit guard takes a bucket's identifier from the body with `boundedIdentifier` before anything is verified and fails closed (`503`) when the limiter cannot decide or none is composed; the runtime composition binds the PostgreSQL limiter only for `RATE_LIMITER=postgres` with a database and local key custody. The CSRF slot (`csrf.guard.ts`, `platform/auth/csrf/`: exact `Origin`, Fetch Metadata, the synchronizer token) and the authorization slot (`authorization.guard.ts`, `platform/authorization/`: surface, permission from the snapshot, tier, scope) are built; a use case opens its transaction through `OperationRunner` (`read`: no policy lock, refused for a state-changing request; `mutate`: the shared policy locks first, the session judged again under them). **The authenticated limiter's `429`** (A2 of the audit, `AC-SLICE-000-131`): the authentication guard counts every request of a route that needs a session (`needsSession`, `access-declaration.ts`) in `rate_limit_authenticated_api` and refuses the one past the limit with `ApiException.rateLimited(decision.retryAfterSeconds)`, a `429 RATE_LIMITED` with `Retry-After` in whole seconds (1 to 60); a refusal before a session exists (`rate-limit.guard.ts`, a full hash admission) carries none, and `ApiException.of` is how it is made. The application's description states that `429` for every such operation itself (`src/platform/openapi/rate-limit-statement.ts`, from the same `needsSession`), so a controller does not list `RATE_LIMITED` for the bucket; the contract declares the shared `RateLimited` response and the code for each (`RateLimitedAnonymous`, which carries no header, for the operations reached before a session exists), `rate-limit-coverage.test.ts` derives the covered operations from the route inventory, and `contract-consistency.test.ts` holds the contract itself to the same rule, so a new operation cannot leave it out.
- Sessions (`src/platform/auth/sessions/`): the `session` row is the whole mechanism; it is active while `terminated_at` is null and holds only `TokenService.hash` of its token. The authentication guard authenticates a `self` or `permission` route from `melarc_session` (staff, vendor) or a bearer credential (rider), never both and never the wrong one for the session (`session-credentials.ts`). `SessionAuthenticator` looks the session up by hash under the `authentication` capability and judges it on one fresh database time (`session-judgement.ts`: `now >= expires_at` ends it, and for a browser session `now - last_activity_at >= idle`; equality expires; a rider has no idle rule), refuses everything with the one `SESSION_INVALID` (`SESSION_SUPERSEDED` for a displaced vendor), and judges authority without a lock (`session-authority.ts`: a session below its bundle's `reduction_floor`, or a Vendor or Rider session below the fixed policy's `minimum_revision`, is `SESSION_INVALID` and ended `AUTHORITY_CHANGED`; an instance that cannot be sure of the policy answers `503`, ends nothing and reports `policy_superseded`). `ReferenceDataReadiness` (`reference-data-readiness.ts`) is registered wherever a database is composed, so `/readyz` is `503` with `reference_data_missing` until the reference seed has run. A request that finds a session out of time ends it `EXPIRED` and records it by the system in the same transaction (`session-expiry.ts`; `SessionStore.expire` judges again after the row lock); every other refusal writes nothing. It writes no activity: `SessionActivityInterceptor` records it after the request by the route's policy and the outcome, through `ActivityRecorder` (coalesced by `ACTIVITY_COALESCE_MS`; the row lock first, then one statement on the database's clock that finds the session live). A request context is built from a session only by `contextOfSession`, which always carries the session id. `SessionIssuer` is the §13.10a protocol on the S0.7 toolkit and the only way a session is created: discover, plan the shared bundle lock (and for a vendor and a rider the fixed one), lock, take the identity lock (`FOR NO KEY UPDATE`, which the runtime may take because it holds `UPDATE` on the two credential columns), revalidate, restart at most `POLICY_MAX_ATTEMPTS` times, then copy the bundle, take one database time, issue and audit in one transaction. The caller states the credential it verified by its generation (`verifiedCredentialGeneration`, the `credential_generation` it read) and the issuer refuses `CREDENTIAL_CHANGED` when the identity holds another under the lock; whoever replaces a credential raises the generation by one (a trigger holds it: only by one, never back, and `credential_established_at` changes only with a new generation and may repeat), and a rehash changes neither (OB-128). The issue is the sign-in's one transaction owner: it runs the request's `steps` (typed writes of identity proofs, such as spending a proof, before any session row is locked; database work by convention and review, not a sandbox) and ends a Vendor's or Rider's earlier session inside its transaction. The runtime has no `SELECT` on `credential_hash`: only the authentication capability reads it, through `melarc.staff_credential_hash`; nor on a session's `token_hash`, `csrf_token_hash`, `bundle_snapshot` and `client_root_signal`, nor on a factor's `secret_*` columns (migration `0031`, F01), in any context, so an administrator's policy cannot hand out a credential: the authentication capability finds a session with `melarc.session_by_token_hash` and opens a seed with `melarc.mfa_factor_sealed_seed`, and an idle tier reads the generated `session.privileged`. Those readers decide by settings the runtime sets itself, so they narrow what a statement can read under the current runtime context and do not stop arbitrary SQL, which can assert that context itself (SECURITY_DESIGN.md, plan 7.36). Ending sessions is `SessionStore.terminate` (by session, principal or bundle, locks in id order); no code updates `session` or takes a policy lock of its own. `SessionController` (S0.34): `getCurrentSession` (`background`, built by the sign-ins' `currentSessionOf` under `authentication`, so a Vendor's or Rider's read is not filtered quietly; its `authorized_hubs` lists every hub for a snapshot that holds a grant of the all-hub scope, and `authorized_hub_ids` stays what the session was issued with) and `signOut` (through `OperationRunner.mutate` under the principal's own context: migration `0023` lets a principal end only the session it acts in, with `SIGNED_OUT`, and a Vendor or Rider write only its own `auth.session.terminated`). A handle is made only by the unit of work or the coordinator (`architecture.test.ts` refuses `bindTransactionHandle` elsewhere). A raw statement returns an instant as text: read it with `timestampOf`.
- Configuration is validated at start and the process refuses to start on a bad value; [.env.example](.env.example) lists every key. Never log a credential, token or connection string. A secret value is a `Secret` (`src/platform/config/secret.ts`: it prints as `[REDACTED]`, and only `reveal()` returns it). A new setting goes in every place it belongs, and a test fails when one is missed: `config-settings.ts` (name, expected text, schema), `load-config.ts` (the field and any relation), `.env.example` and its form in `env-example.test.ts`, `scripts/setup-env.ts` if it holds key material, `e2e/harness/api-environment.ts`, and the table in [DEPLOYMENT_AND_ENVIRONMENTS.md](../../architecture/DEPLOYMENT_AND_ENVIRONMENTS.md) §12.5 (a deadline or limit also goes in its "Deadlines" map: a receipt limit does not bound a handler). A setting is validated at start and applied only by the task that owns it; do not call validation enforcement. `adapter-refusals.ts` says what each environment refuses; the describe composition (inert adapters) is for a local run and for tools only, and the runtime composition refuses an inert adapter. Every port binding is an application singleton: a request or transient one is refused, and `port-binding-check.ts` asks the container, before the app listens, about the effective scope of each bound port.
- The API connects only as `melarc_api_runtime` (not the owner, no row-level-security bypass); migrations run as `melarc_migration_elevated`. Run protected queries through `DatabaseService.transactionWithContext`, which sets the row-level-security context and owns the connection: never open a transaction inside another (it is refused) and never keep the transaction object past the work (it stops working). It is the only door: there is no `db` handle, no pool and no transaction without a context, and `src/architecture.test.ts` fails on `pg`, `drizzle-orm/node-postgres` or `DATABASE_POOL` outside `src/platform/database/` and `src/tools/`. Build driver settings with `postgresConnectionSettings(url)` (`src/platform/database/postgres-url.ts`): never give a driver a `connectionString` (lint refuses it) or a URL with a query string.
- A `SYSTEM` context carries one `taskCapability` of the closed list in `src/platform/database/task-capabilities.ts`, and no other principal does. `capability-access.ts` is the access matrix of [data-scope-registry §5.2](../../contracts/data-scope-registry.md) in code (a test reads the registry): the service refuses a capability whose identity is not the connection's `current_user`, and `architecture.test.ts` refuses `taskCapability: '<name>'` outside the directories the matrix lists. A capability is a label; the grants are the barrier. An ordinary policy is one `CASE melarc.principal_type()` with an arm for each principal type it admits (`STAFF`, `VENDOR`, `RIDER`, `SYSTEM`) and `ELSE false`; a `SYSTEM` arm has a positive `melarc.task_capability() = '<capability>'` as a mandatory `AND` conjunct. The one other expression accepted is the scope probe policy `FOR SELECT` (`melarc.principal_type() = 'STAFF' AND <column> = melarc.scope_probe_id()`). The migration lint and `catalog-invariants.ts` refuse every other expression, whether it names `SYSTEM` or not (`true` and `melarc.principal_type() <> 'VENDOR'` admit `SYSTEM` too), judging each `USING` and `WITH CHECK` that is present for its command (`system-branch.ts`). `melarc.scope_probe_id` is written by `scope-probe.ts` (`existingRecordHub`) and nowhere else, and a context may not carry it. The probe holds its transaction while it runs (`transaction-gate.ts`: an overlapping statement or probe is refused), and its predicate lives in a separate `FOR SELECT` policy only: lint and catalogue refuse it in any policy for `ALL`, `UPDATE`, `DELETE` or `INSERT`. The audit's actor comes from `auditActorOf`, which maps `SYSTEM` to the null actor.
- Time is bounded and enforced, not raced ([plan §11.8](../../delivery/planning/SLICE-000-IMPLEMENTATION-PLAN.md#118-deadline-ownership-and-the-execution-budget)). Elapsed time in `src/platform/execution/` and `src/platform/database/` is the injected `Clock`'s monotonic reading (`architecture.test.ts` refuses `Date.now()`, `performance.now()` and `new Date()` there); a persisted expiry still takes the database's time. The pipeline makes a request's `ExecutionBudget` once the request is admitted and its body received (`src/platform/http/admission/request-budget.ts`; the describe composition has none) and sets it with `runWithBudget`; `transactionWithContext` runs under a child of it, and on expiry cancels the running statement from another connection, rolls back, destroys the connection and refuses every later statement of the work. A caller waits in the bounded `ConnectionQueue`, never in the driver's queue, and the wait and the connecting share one acquisition deadline (the acquire timeout, or what the request has left). `DatabaseService.check` takes its own deadline from the readiness registry, destroys its connection and gives its permit back when it passes; `PgStatementCanceller` and the clean-up after an expiry each have one bound for everything they do. A finished budget is closed, and so is every budget below it: it starts no effect and no child, and none can be constructed under it (`BudgetClosedError`, which is not expiry; an effect already in flight settles and is still recorded). A transaction already open under a request that is then finished refuses its next statement and is rolled back, never committed (a statement already running is not cancelled by that). Run an outbound call or an enqueue under `budget.effect(...)`, so a late one is refused or recorded. `CommitOutcomeUnknownError` means the commit may have happened: never call it a rollback and never retry it as if it had not. A COMMIT the server answers with the tag `ROLLBACK` (a statement failed and the work went on) is `TransactionRolledBackError`: nothing was kept, and it is never success. A time bound the database raised is a `DatabaseDeadlineError`, not a bare driver error. The platform answers these (`operational-failure.ts`, read through the `cause` chain): the budget's, the database's and the pool's failures are a code-less `503` with no `Retry-After`, a `CommitOutcomeUnknownError` is a `500` with its own text (the owner's decision of 11 October 2026), a definite rollback is an ordinary `500`, and a handler that heeds nothing is answered `503` by the pipeline `DISPOSAL_BOUND_MS` after its budget runs out.
- Policy coordination uses the transaction-scoped advisory locks of `src/platform/database/policy-lock/` ([SECURITY_DESIGN.md](../../architecture/SECURITY_DESIGN.md) §13.10a) and never a row lock (`FOR SHARE` needs `UPDATE`, which the runtime logins never hold). Classes and keys come from `lock-keys.ts` (pinned by tests); `planPolicyLocks` merges and orders; `acquirePolicyLocks` takes them once per transaction, first (only the security context may precede), after refusing any level but READ COMMITTED; `PolicyCoordinator` discovers, plans, locks, revalidates and acts, restarting at most `POLICY_MAX_ATTEMPTS` times inside one deadline, and never upgrades a lock (`PolicyRestartRequired` restarts with the stronger plan). `architecture.test.ts` refuses the session-level and `pg_try_` advisory functions anywhere in application code (the limiter's one try-lock, a cleanup election, was removed when its capacity lock, class `RATE_LIMIT_CAPACITY`, put every delete under one lock), and any advisory call outside `policy-lock/` and `platform/limiter/`. Exclusive acquisition is SQL: the change of a bundle or of a fixed policy after the seed is `melarc.change_role_bundle` / `melarc.change_fixed_policy` (migration `0017`, S0.27; executable by the migration login alone; the TypeScript door is `platform/authorization/policy-change/`), the seed takes its keys with `melarc.lock_policy_keys`, and the migration lint refuses a plain write of a policy table.
- The reference-data tables (`hub`, `permission`, `role_bundle`, `role_bundle_grant`, `fixed_permission_policy`, `setting`, `reason_code`; `src/platform/database/schema/reference-data.ts` and `migrations/0003_reference_data.sql`) are read by the API and written by a seed: the runtime holds `SELECT` only, and the three policy tables never more. A table is added to `SEED_ONLY_TABLES` (`src/test-support/registry-grants.ts`) until an operation writes it. They are written only by `melarc.initialize_reference_data` (and `melarc.add_reason_fixtures` for the test fixtures), `SECURITY DEFINER` functions in `migrations/0005_seed_initialization.sql` that only the provisioning login executes and that fill all seven tables once, in one statement, serialized, refusing unless all seven are empty (SQLSTATE `55000`); that login holds no privilege on the tables, so asserting the seed label reaches nothing. `runSeed` (`src/platform/database/seed/seed-helper.ts`) calls them in one transaction as `SYSTEM` under the `seed` capability over that login, its policy keys taken exclusive first by `melarc.lock_policy_keys`, a short insert rolled back; a function the posture check does not list in `APPROVED_DEFINER_EXECUTE` (`role-posture.ts`) is a finding. The data and plan are `src/tools/seed/` (each document-derived list has a test that reads its document), the command is `pnpm --filter @melarc/api run db:seed` (`DATABASE_SEED_URL`, forbidden in the API's environment, and `APP_ENV`), and test-only fixtures live in `src/tools/fixtures/` (named `FIXTURE_`, refused in production). A new table is classified in the registry in the same change; `registry-grants.db.test.ts` fails on a table the registry does not classify and on a grant it does not allow.
- Migrations only go forward: never edit one an environment may hold (the applied history of other environments is not known, so a fix to an earlier migration's function, policy or trigger is a new migration: `0021`, `0022`, `0023`), never `drizzle-kit push`. Declare tables in `src/platform/database/schema/`, run `pnpm --filter @melarc/api run db:generate`, then `db:check`. Read the SQL: a new table must, in the same migration, be owned by `melarc_owner` with row-level security enabled and forced, plus policies and grants ([architecture §5.1](../../architecture/MIGRATION_AND_SEEDING.md#51-roles-ownership-and-rls-at-migration-time)). Add what is missing by hand and classify the table in [data-scope-registry.md](../../contracts/data-scope-registry.md). `migration-lint.ts` reads each migration's text (owner, enable and force, a role in a policy, a grant to PUBLIC, default privileges) and cannot see an `EXECUTE`; `catalog-invariants.ts` asks the migrated database and is what holds. `runMigrations` refuses an applied migration that was edited or removed, and a new one dated before one that ran. A seed or backfill writes a forced-RLS table as the `SYSTEM` principal under an explicit seed task capability, with a `SYSTEM` branch in each table's policy (`migrations/0004_seed_policies.sql` is the pattern for the policy branches: a `_seed_read` and a `_seed_insert` policy per table; `0005` is the seed's only way in, a definer function). The lint also refuses `ON DELETE CASCADE`, `TRUNCATE` and a DELETE grant unless a comment on the statement says `-- allow-delete: <reason>`, and `CREATE ROLE`, `ALTER ROLE` and a role granted to a role unless it says `-- allow-role: <reason>`; it refuses a `SECURITY DEFINER` function that does not fix its `search_path`, is not revoked from `PUBLIC` and granted to a named role, or uses `EXECUTE`. The roles a process connects as are in `src/platform/database/technical-roles.ts`: `provisionRoles` creates them before any migration runs and a migration grants to them by name; the readiness check and `catalogViolations` ask the same posture question (`role-posture.ts`) of the connected login and of each named one, and a privilege counts when the login can reach it by becoming a role it is a member of (`SET ROLE`), not only when it inherits it ([architecture §5.1](../../architecture/MIGRATION_AND_SEEDING.md#51-roles-ownership-and-rls-at-migration-time)).
- Every failure is the contract's envelope with a request id, including a path or method no route answers (`not-found-fallback.ts`); routing is case-sensitive and strict. Transport admission (`platform/http/admission/`) runs before routing and guards: a body is `application/json` in UTF-8, not encoded, and within `HTTP_BODY_LIMIT_BYTES` counted as the bytes arrive; the head, the slot at the admission gate (a `GET` or `HEAD` of a probe path with no body is not queued; any other request to it is) and the body deadline are enforced there, and each refusal is code-less (`413`, `415`, `408`, `503`). A request that says `Expect: 100-continue` is invited to send its body only once its head is accepted and it holds a slot (`checkContinue`, `create-app.ts`), and a refusal that leaves the connection open reads the rest of the body off within bounds of bytes, time and connections (`refused-body.ts`). A body that is not valid JSON, or names `__proto__`, is marked and not refused there: the guards answer first and the validation step answers `VALIDATION_FAILED`; take a limiter's identifier from it with `boundedIdentifier`, and fingerprint a command with `fingerprintOfRequest`, which cannot forget the path parameters. Handlers are given parameters as sent: the validator refuses text that reads as another type (`0x10`, ` 5`, `1e1`) so `Number` and `parseInt` agree, but a single value for an array parameter stays a string.
- Key material is read (`Secret.reveal()`) in `src/platform/auth/crypto/held-keys.ts` only. The hash string, the token hash, the sealed-value envelope and its context are persisted formats whose file headers state them: hash a token through `TokenService.hash` only, build a sealed value's context with `sealedContext()` from the record, store `envelopeVersion` with the key version, nonce and ciphertext, and rewrite a credential hash only when the Hasher says `needsRehash` (forward-only).
- A Nest dependency-injection error while the application is created calls `process.abort()`, so a startup check belongs at `app.init()` (as `port-binding-check.ts` does), not in a factory.
- A port that works inside the caller's transaction receives a `TransactionHandle`; `src/platform/database/transaction-handle.ts` is the one bridge (`bindTransactionHandle(tx)` makes it, `transactionOf` and `securityContextOf` read it), and the context it holds is the one `DatabaseService` applied to the transaction, never a caller's. The audit writer (`src/platform/audit/`) takes the actor from `auditActorOf(context)`, refuses a code outside `audit-event-codes.ts` (audit.md §5, compared with the document by a test), holds each event to its tier and facts (`audit-classification.ts`; a before and after is required by the change the event records, not by its tier; `auth.mfa.reset` has an explicit shape in `audit-mfa-reset.ts`), screens every fact and note (a secret-named field is refused, so is an address or a number; a secret inside text is removed) and writes in the caller's transaction, so a failed write aborts the act; `audit_event` is append-only (no `UPDATE`, `DELETE` or `TRUNCATE` for any login, and a trigger for the rest), and `commitThenRefuse` commits an authentication refusal's bookkeeping and raises the refusal after the commit. `src/platform/idempotency/` keys a command by principal, operation and key with a request fingerprint, and replays a secret for `registerRiderDevice` alone (sealed; the window is judged on the database's clock); `src/platform/settings/` reads a setting with no default (`SETTING_MISSING`) and validates a reason (`REASON_REQUIRED`, `REASON_NOT_ACTIVE`) against a branch the use case derives, never the client's.
- `src/platform/limiter/`: the rate limiter decides on the database's clock in a short transaction of its own under the `rate_limit` capability (no caller transaction open), serialised per key by an advisory lock of class `RATE_LIMIT_KEY`, over the six buckets only; it fails closed (`LimiterUnavailableError`, also while a live row is under a key version it does not hold, checked again under the capacity lock just before the insert) and evicts no live row (the policy of `DELETE` admits only a row that has left the 60-second window). The in-memory limiter is for unit tests and a deployed environment refuses it. Hash admission bounds concurrent hashes (`HASH_ADMISSION_SLOTS`, the memory of the largest accepted profile, a reserved libuv thread): a refused request does no hash and counts nothing. `src/platform/metrics/` is a closed catalogue of bounded labels: development and test throw `LABEL_UNBOUNDED`, production drops the sample and counts it. None of these adapters is bound in the runtime composition until the task that consumes its port binds it (OB-38).
- `src/platform/delivery/`: the durable credential-delivery queue (`credential_delivery_job`, migration 0009) and its worker. `enqueue` and `cancel` run in the caller's transaction under `authentication`; `claim` and `recordOutcome` are `src/platform/delivery/worker/worker-job-store.ts`, which with the cleanup of `src/platform/delivery/retention/` is the only code that opens `credential_delivery` (the matrix lists the two directories), on the worker's own login with no transaction open during a send. A payload is sealed to its job, kind, principal and record (`delivery-payload.ts`, a persisted format) and erased when the job ends (a CHECK); a trigger keeps the state machine, and an outcome is written against the lease version (`LEASE_LOST`). The worker (`src/platform/delivery/worker/delivery-worker.ts`) is its own process: `src/delivery-worker-main.ts`, composition root `src/delivery-worker-runtime.ts`, settings `src/platform/delivery/worker/worker-config.ts` (`DATABASE_WORKER_URL` is forbidden in the API's environment). It holds the `credential_delivery` key only, sends through the capture adapter (a sink outside the checkout) and refuses a real provider (none is built, G3), logs a job's id and an outcome class and never a destination, link, token or error text, and reads a setup grant's or a recovery request's state and expiry on the database's clock before each send (`setup-grant-redemption-reader.ts`, S0.29; `recovery-request-redemption-reader.ts`, S0.50). **The notification lane** (S1.12; `src/platform/notifications/`, migrations `0055` to `0057`) runs in the same worker as a periodic task: the outbox envelope a business act writes in its own transaction (`outbox-writer.ts`; the table's insert guard checks its scope against the aggregate), the lane that relays it and sends the business texts (`notification-lane.ts` over `notification-store.ts`, the only code that opens the `notification` capability, whose context is built from the stored envelope; the aggregates are the pickup request and, since S1.21 (migration `0062`), the pickup manifest, whose one rider is texted once on dispatch; a message copies the envelope's payload members it declares (`carries`) into the notification's closed `parameters`, which the Vendor's skip notice uses for the reason and the requested action), the list of messages and their draft wording (`message-list.ts`, `templates.ts`), the port's adapters (`capture`, `hubtel`, and `guarded`, the owner's validation window) and the window's counter; the sender is composed in `src/notification-sender.ts`, also for `sms:smoke`. A notification holds no destination, no text and no code, and SMS or notification code never sits in `platform/delivery/`. The Ops read of it is `src/notifications/` (`listNotifications`, `notification.read`): newest first, paged by a position, the staff of a hub only and **only under that key** (row-level security tests the authorization key beside the hub scope), the columns of the log and not the count digest, the provider's reference or the lease, and a foreign hub audited as every staff read is.
- `src/platform/auth/setup-grants/` and `src/platform/auth/mfa/`: the stores of `setup_grant` and `mfa_factor` (migration 0018; the factor's schema is `src/staff/mfa-factor.schema.ts`). Each joins the caller's transaction under `authentication`, offers by-key lookups and no list or scan, and returns no hash and no secret; a token is shown once, a seed is sealed to its row (`sealedContext`). Time is the database's, and a lock and a time are read in two statements. The table's guards, not the store, hold the lineage (written at insert, never updated) and the state machines; the issuing operation writes the audit event. The bootstrap tools (S0.30) and the setup operations (S0.31) call them.
- `src/tools/bootstrap/` (S0.30, migration 0019): the bootstrap seed and the resume command, processes an operator starts as the provisioning login (`bootstrap:seed`, `bootstrap:resume`); nothing the API or the worker loads may import the folder (`bootstrap-isolation.test.ts`), and the `bootstrap` capability is opened only there. The tables are reached only through four definer functions (`melarc.bootstrap_status`, `seed_bootstrap_administrators`, `bootstrap_identity_state`, `resume_bootstrap_identity`) that fix the shape of the pair and judge §3.3a's conditions under the identity's row lock; a bundle holds a secret in clear, so it is created exclusively, made private, inspected and only then written (`custody-store.ts`), in a folder outside the checkout that was judged private before any file was made in it (mode and owner, or on Windows the folder's access list), and no output, log, failure message or audit event ever names a secret, an address or a path. Each bundle names the database it was written for (`target`), and the sweep of orphans removes only its own; the bundles are written inside the transaction (`BOOTSTRAP_DEADLINES`), and a write in flight when a run fails is waited for and removed; a file that a failed write could not remove is reported by its random name (`BootstrapCustodyError.residual`), and a commit of unknown outcome keeps the bundles and prints the run's correlation id: a missing audit event is unresolved and never a rollback, and the reconciliation is MIGRATION_AND_SEEDING.md §3.3b (pinned by `bootstrap-reconciliation.db.test.ts`). A committed resume also writes the enhanced summary `auth.bootstrap.resumed` (migration `0022`, `audit-bootstrap-resumed.ts`): `SYSTEM` with a null actor, the reserved actor as a named fact, and facts that the function derives from what it wrote and refuses a document that contradicts. The reserved system actor is `src/staff/reserved-system-actor.ts` (the same value as `melarc.reserved_system_actor_id()`); a rule that treats a bootstrap identity differently reads `origin`, never that actor.
- `src/platform/auth/staff/` (S0.31 to S0.33): the three setup routes (`StaffSetupService`), the staff sign-in (`StaffSignInService`) and its second step (`StaffMfaSignInService`), each absent without a database and local keys (then `503`). Setup: the principal comes from the grant alone; every grant refusal is one `SETUP_GRANT_INVALID`; an unusable or expired token costs no hash (liveness is judged on the database's clock, in the precheck and again under the locks); a grant that lapses during the act is a typed refusal answered after the rollback (`guardReasonIn`; any other `23514` is a `500`); a wrong code rolls back; no session. Sign-in: limiter (canonical address), then a hash slot, then one lookup and **one verification derivation** (real, or a dummy for an unknown, ineligible or locked identity; a correct password at an older cost adds one, the rehash); every refusal is one `INVALID_CREDENTIALS` and a lock is never announced; the count is one atomic conditional update committed before the refusal is answered (`commitThenRefuse`); a privileged identity gets a `202` challenge and no cookie; the session's view is built in the issuing transaction (`SessionIssuer`'s `project` hook), so a failure takes the session back. Second step: no hash; **identity locked first, challenge second** (the issue's order); a lock is announced (the password was proved); the proofs it spends commit with the session. A route states what it takes and gives in code (`*-schemas.ts`, `DescribeErrors`) and `contract:check` compares it with the contract. `appWith` leaves the product routes out (`productRoutes: false`). **The trusted browser** (staff-authentication.md §5.8; migration `0033`; `src/platform/auth/trusted-browsers/`, `src/staff/staff-trusted-browser-administration.*`): the one persistent cookie of the staff sign-in, `melarc_trusted_browser`, is 32 random bytes of which only the hash is stored (the runtime cannot select the column; `melarc.use_trusted_browser` and `trusted_browser_id_for` are its only readers), bound to the `ACTIVE` factor and the credential generation, lasting seven days from the database's clock (a constant, not a setting; at most five valid, a sixth replaces the oldest). It is read only after the password is proved (`StaffSignInService.#trustedSession`, which falls back to the ordinary `202` in silence), made only in the transaction that issues the session after an accepted code (`StaffMfaSignInService`), and ended by the person (`SELF`), by a Platform Admin (`staff.session.revoke` at tier P, with a reason of `revokeSession`'s domain), by a reset (`FACTOR_RESET`), by a new authenticator (`FACTOR_REPLACED`) or by the recovery that replaces the password (`CREDENTIAL_CHANGED`, S0.51). The use of it locks the credential's own row before it takes the instant it judges on (`melarc.use_trusted_browser`, migration `0039`: the identity's lock does not exclude a person's own removal), the administrator's removal takes an `Idempotency-Key` ("every valid browser" is not a fixed set), and the administrator's list is audited when it crosses a hub (the audit of 26 October 2026). **Vendor and recovery (S0.47 to S0.51)**: the vendor domain is `src/vendor/` (the reads and the two administrator acts; migrations `0034`, `0035`), the vendor's own credential acts are `src/platform/auth/vendor/` (setup, sign-in with the `VENDOR_DEVICE` limit partition, its browsers; a self act runs under the authentication capability through `OperationRunner.actAsAuthentication`, and its idempotency record is kept on its behalf, `ON_BEHALF_OPERATIONS`, `0036`), and recovery is `src/platform/auth/recovery/` (`recovery_request`, `0037`, whose guards hold eligibility, the registered channel and the cap of two live links for every writer; the self-service request answers every caller the same `202`; the completion locks the identity, then the request, and ends sessions, links, trusted browsers and, for a vendor, browsers; the administrator recoveries share `AdministratorRecoveries` and run under their keys, `0038`). The identity directory is the platform router over the staff and vendor adapters (`platform/auth/directory/`); a domain decides recovery eligibility (`recoveryEligible`). **Rider enrolment (S0.57)**: `completeRiderDeviceEnrolment` is `src/platform/auth/rider/` (`rider-enrolment.service.ts`, `rider-device-store.ts`), the one operation that calls the attestation verifier: a short look at the grant first (no evidence is read for a grant that cannot be used), the verifier **outside any transaction**, a hash of the PIN only after `VERIFIED`, then one transaction under the rider's lock that reads the grant, the rider's status and its devices again, consumes the grant, ends an `ACTIVE` device as `REPLACED` (its session `DEVICE_REPLACED`; a `REVOKED` one stays revoked), registers the new one and sets or replaces the PIN. A verdict is answered as the verifier gave it, after its event is committed (`auth.device.attestation_failed`); a verifier that cannot decide is `503 TRUST_DATA_UNAVAILABLE` and writes nothing; one that breaks its interface is a `500` (`AttestationInterfaceError`). No session is issued, and nothing in the files names the substitute or the environment (`production-refusals.test.ts` holds that). **Rider sign-in (S0.59)**: `requestRiderSignInChallenge` and `riderSignIn` (`rider-challenge*.ts`, `rider-sign-in*.ts`; migration `0041`, `rider_sign_in_challenge`, readable and writable by the authentication capability alone, with hashes of the nonce, the number and the device context as `bytea` and the audience `melarc-api/<APP_ENV>`) draw on one bucket, `rate_limit_rider_challenge`, keyed on the canonical number whether or not it is a rider's. The order is the contract's: the challenge (`CHALLENGE_UNUSABLE` for unknown, spent or bound to another number, service or purpose; `CHALLENGE_EXPIRED`; **any other presentation ends it**, in the transaction of its outcome, the identity locked first only where a count follows), then the signature over it against the sole `ACTIVE` device, which must be the device the challenge was issued for (`DEVICE_PROOF_INVALID`: the PIN is never looked at and nothing is counted), then, for a number with no device to ask, the PIN decides (`DEVICE_PROOF_INVALID` or `DEVICE_NOT_ENROLLED`, nothing counted), then the status, the lock and the count of a wrong PIN. Every request admitted to a hash slot makes **one** derivation (a dummy where the PIN does not decide), and the reads are the same statements on every branch (the nil identifier names no rider). A correct PIN issues the session through the issuer's one step (challenge, device, lock, rehash, count), the Rider fixed bundle at `BUILD_FIXED_POLICY` revision 1, no idle rule, one live session (`REPLACED_BY_NEW_SESSION`; the old handset gets a plain `401`).

## Tests

`pnpm --filter @melarc/api test` runs the unit and process projects, and `pnpm run test:db` the database projects against local PostgreSQL: `database`, several files at a time (`MELARC_DB_WORKERS`, 3 when unset), then `database-alone`, one file at a time with nothing beside it. Each file holds the server for its lifetime, shared or alone (`test/database/support/server-hold.ts`), so an alone file never runs beside another run's files: it waits ten seconds, then fails saying so. A database test that changes or watches what the whole server shares (a role, its password or memberships, another database, a server setting, every session's activity or locks), or whose time bounds or weight do not survive files beside it, goes in `test/database/alone/` with its reason on its first line (`// Runs alone: `); `src/database-test-isolation.test.ts` refuses such a statement elsewhere, and an alone file without a reason. `MELARC_TEST_WORKERS` (4) bounds the parallel projects, and `vitest.config.ts` refuses `VITEST_MAX_WORKERS`, which Vitest would apply to every project. While editing, `pnpm run test:affected` runs the tests a change reaches, the process tests only when start-up, configuration, shutdown, logging, probe or tool code changed or with `--with-process` ([the loop](../../DEVELOPMENT.md#the-development-loop-and-the-gate)). Process and database tests run the built `dist/`: `pnpm test` and `pnpm run test:db` rebuild it through Turbo, but a direct `--filter` command does not, so run `pnpm --filter @melarc/api run build` first. Test real registrations and a real database wherever persistence is involved: a database test makes its own disposable database (`createTestDatabase`) and, when it needs the application, starts `startIntegrationKit(database)` (`test/database/support/integration.ts`: the real app on a pool of one, a `TestClient` with cookie jar, CSRF echo and bearer, a `ManualClock` bound through `ports`, `admin()` to age rows, change a status or break writes, `observe()` as a read-only second connection, the capture reader, and `trace()` for statement shapes); assert what the application did from `observe()`, never from its own pool. `stop()` closes everything the kit opened, attempts every close, reports every failure and does nothing a second time; a start that fails part-way closes what it had opened (`src/test-support/cleanup.ts`). Nothing in the production tree imports `src/test-support/`, and no setting moves the application's time (`integration-kit.test.ts`). Never add a skip or weaken an assertion to get green. `spawnSync` needs a large `maxBuffer` when a run fails loudly, or the failure shows as `exit null`. Six tests under `test` and two under `test:db` need a real `SIGTERM` (the worker's among them) and skip on Windows, and one unit test of the capture sink's file modes skips there too, as do the POSIX mode checks of the custody bundle (`custody-node.test.ts`; its Windows access-list checks skip on Linux): a skip is not a pass, so run them in WSL2, Linux or CI. Stage 8 (S0.62 to S0.70) added: `test/support/policy-release.ts` compiles the tree again with a release's changes into the git-ignored `.policy-release/`, for the two-build proof (`test/database/alone/two-builds.db.test.ts`); `src/platform/metrics/` serves the private endpoints (a listener of its own, never a route of the API) and holds the alert rules to OBSERVABILITY_AND_RECOVERY.md section 3.2 (`alert-rules.ts`); and outside production `src/platform/contract/declared-refusals.ts` answers a refusal its operation's `x-error-codes` does not list as a `500`, the omissions awaiting the owner's decision named in `AWAITING_DECLARATION`.
