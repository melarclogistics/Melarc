# API (`apps/api`)

NestJS modular monolith. It holds the technical platform and no product route until a slice adds one: `src/tools/contract/implemented-scope.ts` lists the operations that exist. Run and test it as [DEVELOPMENT.md](../../DEVELOPMENT.md) says; what each bootstrap task left undone is in the runbook ([B0.2 and B0.3](../../delivery/planning/BOOTSTRAP_B0_RUNBOOK.md#carried-forward-from-b02-and-b03), [B0.6](../../delivery/planning/BOOTSTRAP_B0_RUNBOOK.md#carried-forward-from-b06)).

## Layout

- `src/platform/`: technical infrastructure (audit, auth, config, contract, database, delivery, execution, health, http, idempotency, lifecycle, limiter, logging, metrics, openapi, routes, settings). Its production files may import packages and each other, but no relative import may leave `src/platform/` (`src/architecture.test.ts` fails otherwise; test files are exempt).
- `src/platform/auth/ports/`: the ports `platform/auth` reaches domain data and I/O through ([architecture §5](../../architecture/SOLUTION_ARCHITECTURE.md#5-module-boundaries)), each an interface, a token and a descriptor. `src/app.module.ts` binds adapters to the tokens; an adapter (a `*.adapter.ts` file, or any file that implements a port) is imported only by the composition-root files `src/architecture.test.ts` lists, never by a module for being a module. A new adapter is also added to `ALLOWED_PORT_IMPLEMENTATIONS` and `ADAPTED_PORTS` there, and bound as a singleton with no `scope`.
- `src/platform/auth/crypto/` and `credentials/`: the S0.3 adapters (hashing, tokens, TOTP, sealed values), `randomUUIDv7` and the credential and work-email rules. They are not bound in the runtime composition until the task that consumes each port binds it ([plan §7.4](../../delivery/planning/SLICE-000-IMPLEMENTATION-PLAN.md#74-carried-from-s03)).
- `src/<domain>/`: one module per permission domain, siblings of `platform/` ([architecture §5](../../architecture/SOLUTION_ARCHITECTURE.md#5-module-boundaries)). A new domain needs a Product Owner decision. Domains depend on platform, never the reverse.
- `src/tools/`: command-line tools that run from `dist`. `migrations/`: the one canonical migration history (Drizzle). `test/`: process and database tests.

## Rules

- Keep layers apart: controller, application service, domain rules, persistence. A controller never calls another controller, and no business operation bypasses its service.
- Implement an operation contract-first ([plan §7](../../delivery/DEVELOPMENT_EXECUTION_PLAN.md#7-contract-first-implementation)). Each ships negative-access tests ([standards §3.1](../../standards/engineering-standards.md#31-negative-access-tests-are-mandatory-at-five-surfaces)) and tests of its own headers, cookies and status and error pairs ([B0.6 notes](../../delivery/planning/BOOTSTRAP_B0_RUNBOOK.md#carried-forward-from-b06)).
- An operation exists only when its `operationId` is in `IMPLEMENTED_OPERATIONS` and its handler carries `@ContractOperation(id)` (`src/platform/contract/contract-operation.ts`), in the same change; `pnpm run contract:check` fails on any disagreement. A DTO class cannot state `additionalProperties: false`, `if`/`then` or `allOf`: give an explicit schema with `@ApiBody({ schema })`. The description also states what a decorated class cannot (`src/platform/openapi/operation-statements.ts`, the implementation's own account, compared with the contract and never copied from it): credentials with `DescribeSecurity` (each argument an alternative, the schemes inside it all required; no argument is an explicit anonymous `security: []`, and an operation that states nothing inherits the default posture, a browser session with its CSRF token or a rider session), the cookies of a response with `DescribeCookies`, and a Rider operation's hosts with `DescribeServers(RIDER_SERVERS)`. Write a cookie only through `src/platform/auth/cookies/cookie-writer.ts` (`Max-Age=0` literally on expiry; the vendor device cookie is never expired). An error code and its status come from `ErrorCode` and `statusOf` (`src/platform/http/error-codes.ts`, all 121 codes); `SETTING_MISSING` and `SETTING_INVALID` have no decided status, and `ApiException` sets only the headers the contract declares on an error.
- Every route must declare how it is reached (`src/platform/routes/access-declaration.ts`): `@TechnicalEndpoint()` for probes only, never on a business route, or `@Anonymous(limit?)`, `@Self()` or `@RequiresPermission(key)`, each of which also states the same fact in the description. An undeclared route stops the API at start, and is refused `403` if one is ever served. The guards run in the order of `guard-chain.ts`: declaration, rate limit, authentication, CSRF and Origin, authorization. The rate-limit guard takes a bucket's identifier from the body with `boundedIdentifier` before anything is verified and fails closed (`503`) when the limiter cannot decide or none is composed; the runtime composition binds the PostgreSQL limiter only for `RATE_LIMITER=postgres` with a database and local key custody. A slot that is not built refuses (`401`, `403`) instead of serving.
- Sessions (`src/platform/auth/sessions/`): the `session` row is the whole mechanism; it is active while `terminated_at` is null and holds only `TokenService.hash` of its token. The authentication guard authenticates a `self` or `permission` route from `melarc_session` (staff, vendor) or a bearer credential (rider), never both and never the wrong one for the session (`session-credentials.ts`). `SessionAuthenticator` looks the session up by hash under the `authentication` capability and judges it on one fresh database time (`session-judgement.ts`: `now >= expires_at` ends it, and for a browser session `now - last_activity_at >= idle`; equality expires; a rider has no idle rule), records activity coalesced (`ACTIVITY_COALESCE_MS`) and refuses everything with the one `SESSION_INVALID` (`SESSION_SUPERSEDED` for a displaced vendor); it does not judge authority (S0.26, S0.27). A request context is built from a session only by `contextOfSession`, which always carries the session id. `SessionIssuer` is the §13.10a protocol on the S0.7 toolkit and the only way a session is created: discover, plan the shared bundle lock (and for a vendor and a rider the fixed one), lock, take the identity lock (`FOR NO KEY UPDATE`, which the runtime may take because it holds `UPDATE` on the two credential columns), revalidate, restart at most `POLICY_MAX_ATTEMPTS` times, then copy the bundle, take one database time, issue and audit in one transaction. The caller states the credential it verified by its generation (`verifiedCredentialGeneration`, the `credential_generation` it read) and the issuer refuses `CREDENTIAL_CHANGED` when the identity holds another under the lock; whoever replaces a credential raises the generation by one (a trigger holds it: only by one, never back, and `credential_established_at` changes only with a new generation and may repeat), and a rehash changes neither (OB-128). The issue is the sign-in's one transaction owner: it runs the request's `steps` (typed writes of identity proofs, such as spending a proof, before any session row is locked; database work by convention and review, not a sandbox) and ends a Vendor's or Rider's earlier session inside its transaction. The runtime has no `SELECT` on `credential_hash`: only the authentication capability reads it, through `melarc.staff_credential_hash`. Ending sessions is `SessionStore.terminate` (by session, principal or bundle, locks in id order); no code updates `session` or takes a policy lock of its own. A handle is made only by the unit of work or the coordinator (`architecture.test.ts` refuses `bindTransactionHandle` elsewhere). A raw statement returns an instant as text: read it with `timestampOf`.
- Configuration is validated at start and the process refuses to start on a bad value; [.env.example](.env.example) lists every key. Never log a credential, token or connection string. A secret value is a `Secret` (`src/platform/config/secret.ts`: it prints as `[REDACTED]`, and only `reveal()` returns it). A new setting goes in every place it belongs, and a test fails when one is missed: `config-settings.ts` (name, expected text, schema), `load-config.ts` (the field and any relation), `.env.example` and its form in `env-example.test.ts`, `scripts/setup-env.ts` if it holds key material, `e2e/harness/api-environment.ts`, and the table in [DEPLOYMENT_AND_ENVIRONMENTS.md](../../architecture/DEPLOYMENT_AND_ENVIRONMENTS.md) §12.5 (a deadline or limit also goes in its "Deadlines" map: a receipt limit does not bound a handler). A setting is validated at start and applied only by the task that owns it; do not call validation enforcement. `adapter-refusals.ts` says what each environment refuses; the describe composition (inert adapters) is for a local run and for tools only, and the runtime composition refuses an inert adapter. Every port binding is an application singleton: a request or transient one is refused, and `port-binding-check.ts` asks the container, before the app listens, about the effective scope of each bound port.
- The API connects only as `melarc_api_runtime` (not the owner, no row-level-security bypass); migrations run as `melarc_migration_elevated`. Run protected queries through `DatabaseService.transactionWithContext`, which sets the row-level-security context and owns the connection: never open a transaction inside another (it is refused) and never keep the transaction object past the work (it stops working). It is the only door: there is no `db` handle, no pool and no transaction without a context, and `src/architecture.test.ts` fails on `pg`, `drizzle-orm/node-postgres` or `DATABASE_POOL` outside `src/platform/database/` and `src/tools/`. Build driver settings with `postgresConnectionSettings(url)` (`src/platform/database/postgres-url.ts`): never give a driver a `connectionString` (lint refuses it) or a URL with a query string.
- A `SYSTEM` context carries one `taskCapability` of the closed list in `src/platform/database/task-capabilities.ts`, and no other principal does. `capability-access.ts` is the access matrix of [data-scope-registry §5.2](../../contracts/data-scope-registry.md) in code (a test reads the registry): the service refuses a capability whose identity is not the connection's `current_user`, and `architecture.test.ts` refuses `taskCapability: '<name>'` outside the directories the matrix lists. A capability is a label; the grants are the barrier. An ordinary policy is one `CASE melarc.principal_type()` with an arm for each principal type it admits (`STAFF`, `VENDOR`, `RIDER`, `SYSTEM`) and `ELSE false`; a `SYSTEM` arm has a positive `melarc.task_capability() = '<capability>'` as a mandatory `AND` conjunct. The one other expression accepted is the scope probe policy `FOR SELECT` (`melarc.principal_type() = 'STAFF' AND <column> = melarc.scope_probe_id()`). The migration lint and `catalog-invariants.ts` refuse every other expression, whether it names `SYSTEM` or not (`true` and `melarc.principal_type() <> 'VENDOR'` admit `SYSTEM` too), judging each `USING` and `WITH CHECK` that is present for its command (`system-branch.ts`). `melarc.scope_probe_id` is written by `scope-probe.ts` (`existingRecordHub`) and nowhere else, and a context may not carry it. The probe holds its transaction while it runs (`transaction-gate.ts`: an overlapping statement or probe is refused), and its predicate lives in a separate `FOR SELECT` policy only: lint and catalogue refuse it in any policy for `ALL`, `UPDATE`, `DELETE` or `INSERT`. The audit's actor comes from `auditActorOf`, which maps `SYSTEM` to the null actor.
- Time is bounded and enforced, not raced ([plan §11.8](../../delivery/planning/SLICE-000-IMPLEMENTATION-PLAN.md#118-deadline-ownership-and-the-execution-budget)). Elapsed time in `src/platform/execution/` and `src/platform/database/` is the injected `Clock`'s monotonic reading (`architecture.test.ts` refuses `Date.now()`, `performance.now()` and `new Date()` there); a persisted expiry still takes the database's time. The pipeline makes a request's `ExecutionBudget` once the request is admitted and its body received (`src/platform/http/admission/request-budget.ts`; the describe composition has none) and sets it with `runWithBudget`; `transactionWithContext` runs under a child of it, and on expiry cancels the running statement from another connection, rolls back, destroys the connection and refuses every later statement of the work. A caller waits in the bounded `ConnectionQueue`, never in the driver's queue, and the wait and the connecting share one acquisition deadline (the acquire timeout, or what the request has left). `DatabaseService.check` takes its own deadline from the readiness registry, destroys its connection and gives its permit back when it passes; `PgStatementCanceller` and the clean-up after an expiry each have one bound for everything they do. A finished budget is closed, and so is every budget below it: it starts no effect and no child, and none can be constructed under it (`BudgetClosedError`, which is not expiry; an effect already in flight settles and is still recorded). A transaction already open under a request that is then finished refuses its next statement and is rolled back, never committed (a statement already running is not cancelled by that). Run an outbound call or an enqueue under `budget.effect(...)`, so a late one is refused or recorded. `CommitOutcomeUnknownError` means the commit may have happened: never call it a rollback and never retry it as if it had not. A COMMIT the server answers with the tag `ROLLBACK` (a statement failed and the work went on) is `TransactionRolledBackError`: nothing was kept, and it is never success. A time bound the database raised is a `DatabaseDeadlineError`, not a bare driver error. The platform answers these (`operational-failure.ts`, read through the `cause` chain): the budget's, the database's and the pool's failures are a code-less `503` with no `Retry-After`, a `CommitOutcomeUnknownError` is a `500` with its own text (the owner's decision of 11 October 2026), a definite rollback is an ordinary `500`, and a handler that heeds nothing is answered `503` by the pipeline `DISPOSAL_BOUND_MS` after its budget runs out.
- Policy coordination uses the transaction-scoped advisory locks of `src/platform/database/policy-lock/` ([SECURITY_DESIGN.md](../../architecture/SECURITY_DESIGN.md) §13.10a) and never a row lock (`FOR SHARE` needs `UPDATE`, which the runtime logins never hold). Classes and keys come from `lock-keys.ts` (pinned by tests); `planPolicyLocks` merges and orders; `acquirePolicyLocks` takes them once per transaction, first (only the security context may precede), after refusing any level but READ COMMITTED; `PolicyCoordinator` discovers, plans, locks, revalidates and acts, restarting at most `POLICY_MAX_ATTEMPTS` times inside one deadline, and never upgrades a lock (`PolicyRestartRequired` restarts with the stronger plan). `architecture.test.ts` refuses the session-level and `pg_try_` advisory functions anywhere in application code (the limiter's one try-lock, a cleanup election, was removed when its capacity lock, class `RATE_LIMIT_CAPACITY`, put every delete under one lock), and any advisory call outside `policy-lock/` and `platform/limiter/`.
- The reference-data tables (`hub`, `permission`, `role_bundle`, `role_bundle_grant`, `fixed_permission_policy`, `setting`, `reason_code`; `src/platform/database/schema/reference-data.ts` and `migrations/0003_reference_data.sql`) are read by the API and written by a seed: the runtime holds `SELECT` only, and the three policy tables never more. A table is added to `SEED_ONLY_TABLES` (`src/test-support/registry-grants.ts`) until an operation writes it. They are written only by `melarc.initialize_reference_data` (and `melarc.add_reason_fixtures` for the test fixtures), `SECURITY DEFINER` functions in `migrations/0005_seed_initialization.sql` that only the provisioning login executes and that fill all seven tables once, in one statement, serialized, refusing unless all seven are empty (SQLSTATE `55000`); that login holds no privilege on the tables, so asserting the seed label reaches nothing. `runSeed` (`src/platform/database/seed/seed-helper.ts`) calls them in one transaction as `SYSTEM` under the `seed` capability over that login, every policy key taken exclusive first, a short insert rolled back; a function the posture check does not list in `APPROVED_DEFINER_EXECUTE` (`role-posture.ts`) is a finding. The data and plan are `src/tools/seed/` (each document-derived list has a test that reads its document), the command is `pnpm --filter @melarc/api run db:seed` (`DATABASE_SEED_URL`, forbidden in the API's environment, and `APP_ENV`), and test-only fixtures live in `src/tools/fixtures/` (named `FIXTURE_`, refused in production). A new table is classified in the registry in the same change; `registry-grants.db.test.ts` fails on a table the registry does not classify and on a grant it does not allow.
- Migrations only go forward: never edit an applied one, never `drizzle-kit push`. Declare tables in `src/platform/database/schema/`, run `pnpm --filter @melarc/api run db:generate`, then `db:check`. Read the SQL: a new table must, in the same migration, be owned by `melarc_owner` with row-level security enabled and forced, plus policies and grants ([architecture §5.1](../../architecture/MIGRATION_AND_SEEDING.md#51-roles-ownership-and-rls-at-migration-time)). Add what is missing by hand and classify the table in [data-scope-registry.md](../../contracts/data-scope-registry.md). `migration-lint.ts` reads each migration's text (owner, enable and force, a role in a policy, a grant to PUBLIC, default privileges) and cannot see an `EXECUTE`; `catalog-invariants.ts` asks the migrated database and is what holds. `runMigrations` refuses an applied migration that was edited or removed, and a new one dated before one that ran. A seed or backfill writes a forced-RLS table as the `SYSTEM` principal under an explicit seed task capability, with a `SYSTEM` branch in each table's policy (`migrations/0004_seed_policies.sql` is the pattern for the policy branches: a `_seed_read` and a `_seed_insert` policy per table; `0005` is the seed's only way in, a definer function). The lint also refuses `ON DELETE CASCADE`, `TRUNCATE` and a DELETE grant unless a comment on the statement says `-- allow-delete: <reason>`, and `CREATE ROLE`, `ALTER ROLE` and a role granted to a role unless it says `-- allow-role: <reason>`; it refuses a `SECURITY DEFINER` function that does not fix its `search_path`, is not revoked from `PUBLIC` and granted to a named role, or uses `EXECUTE`. The roles a process connects as are in `src/platform/database/technical-roles.ts`: `provisionRoles` creates them before any migration runs and a migration grants to them by name; the readiness check and `catalogViolations` ask the same posture question (`role-posture.ts`) of the connected login and of each named one, and a privilege counts when the login can reach it by becoming a role it is a member of (`SET ROLE`), not only when it inherits it ([architecture §5.1](../../architecture/MIGRATION_AND_SEEDING.md#51-roles-ownership-and-rls-at-migration-time)).
- Every failure is the contract's envelope with a request id, including a path or method no route answers (`not-found-fallback.ts`); routing is case-sensitive and strict. Transport admission (`platform/http/admission/`) runs before routing and guards: a body is `application/json` in UTF-8, not encoded, and within `HTTP_BODY_LIMIT_BYTES` counted as the bytes arrive; the head, the slot at the admission gate (a `GET` or `HEAD` of a probe path with no body is not queued; any other request to it is) and the body deadline are enforced there, and each refusal is code-less (`413`, `415`, `408`, `503`). A request that says `Expect: 100-continue` is invited to send its body only once its head is accepted and it holds a slot (`checkContinue`, `create-app.ts`), and a refusal that leaves the connection open reads the rest of the body off within bounds of bytes, time and connections (`refused-body.ts`). A body that is not valid JSON, or names `__proto__`, is marked and not refused there: the guards answer first and the validation step answers `VALIDATION_FAILED`; take a limiter's identifier from it with `boundedIdentifier`, and fingerprint a command with `fingerprintOfRequest`, which cannot forget the path parameters. Handlers are given parameters as sent: the validator refuses text that reads as another type (`0x10`, ` 5`, `1e1`) so `Number` and `parseInt` agree, but a single value for an array parameter stays a string.
- Key material is read (`Secret.reveal()`) in `src/platform/auth/crypto/held-keys.ts` only. The hash string, the token hash, the sealed-value envelope and its context are persisted formats whose file headers state them: hash a token through `TokenService.hash` only, build a sealed value's context with `sealedContext()` from the record, store `envelopeVersion` with the key version, nonce and ciphertext, and rewrite a credential hash only when the Hasher says `needsRehash` (forward-only).
- A Nest dependency-injection error while the application is created calls `process.abort()`, so a startup check belongs at `app.init()` (as `port-binding-check.ts` does), not in a factory.
- A port that works inside the caller's transaction receives a `TransactionHandle`; `src/platform/database/transaction-handle.ts` is the one bridge (`bindTransactionHandle(tx)` makes it, `transactionOf` and `securityContextOf` read it), and the context it holds is the one `DatabaseService` applied to the transaction, never a caller's. The audit writer (`src/platform/audit/`) takes the actor from `auditActorOf(context)`, refuses a code outside `audit-event-codes.ts` (audit.md §5, compared with the document by a test), holds each event to its tier and facts (`audit-classification.ts`; a before and after is required by the change the event records, not by its tier; `auth.mfa.reset` has an explicit shape in `audit-mfa-reset.ts`), screens every fact and note (a secret-named field is refused, so is an address or a number; a secret inside text is removed) and writes in the caller's transaction, so a failed write aborts the act; `audit_event` is append-only (no `UPDATE`, `DELETE` or `TRUNCATE` for any login, and a trigger for the rest), and `commitThenRefuse` commits an authentication refusal's bookkeeping and raises the refusal after the commit. `src/platform/idempotency/` keys a command by principal, operation and key with a request fingerprint, and replays a secret for `registerRiderDevice` alone (sealed; the window is judged on the database's clock); `src/platform/settings/` reads a setting with no default (`SETTING_MISSING`) and validates a reason (`REASON_REQUIRED`, `REASON_NOT_ACTIVE`) against a branch the use case derives, never the client's.
- `src/platform/limiter/`: the rate limiter decides on the database's clock in a short transaction of its own under the `rate_limit` capability (no caller transaction open), serialised per key by an advisory lock of class `RATE_LIMIT_KEY`, over the six buckets only; it fails closed (`LimiterUnavailableError`, also while a live row is under a key version it does not hold, checked again under the capacity lock just before the insert) and evicts no live row (the policy of `DELETE` admits only a row that has left the 60-second window). The in-memory limiter is for unit tests and a deployed environment refuses it. Hash admission bounds concurrent hashes (`HASH_ADMISSION_SLOTS`, the memory of the largest accepted profile, a reserved libuv thread): a refused request does no hash and counts nothing. `src/platform/metrics/` is a closed catalogue of bounded labels: development and test throw `LABEL_UNBOUNDED`, production drops the sample and counts it. None of these adapters is bound in the runtime composition until the task that consumes its port binds it (OB-38).
- `src/platform/delivery/`: the durable credential-delivery queue (`credential_delivery_job`, migration 0009) and its worker. `enqueue` and `cancel` run in the caller's transaction under `authentication`; `claim` and `recordOutcome` are `src/platform/delivery/worker/worker-job-store.ts`, which with the cleanup of `src/platform/delivery/retention/` is the only code that opens `credential_delivery` (the matrix lists the two directories), on the worker's own login with no transaction open during a send. A payload is sealed to its job, kind, principal and record (`delivery-payload.ts`, a persisted format) and erased when the job ends (a CHECK); a trigger keeps the state machine, and an outcome is written against the lease version (`LEASE_LOST`). The worker (`src/platform/delivery/worker/delivery-worker.ts`) is its own process: `src/delivery-worker-main.ts`, composition root `src/delivery-worker-runtime.ts`, settings `src/platform/delivery/worker/worker-config.ts` (`DATABASE_WORKER_URL` is forbidden in the API's environment). It holds the `credential_delivery` key only, sends through the capture adapter (a sink outside the checkout) and refuses a real provider (none is built, G3), logs a job's id and an outcome class and never a destination, link, token or error text, and confirms no redemption record until S0.29 and S0.50 (`UNBUILT_REDEMPTION_READER`: it sends nothing).
- Never hard-delete operational data or rely on cascade defaults. Required audit writes happen in the same transaction as the business change.

## Tests

`pnpm --filter @melarc/api test` runs the unit and process projects, and `pnpm run test:db` the database project against local PostgreSQL. Process and database tests run the built `dist/`: `pnpm test` and `pnpm run test:db` rebuild it through Turbo, but a direct `--filter` command does not, so run `pnpm --filter @melarc/api run build` first. Test real registrations and a real database wherever persistence is involved: a database test makes its own disposable database (`createTestDatabase`) and, when it needs the application, starts `startIntegrationKit(database)` (`test/database/support/integration.ts`: the real app on a pool of one, a `TestClient` with cookie jar, CSRF echo and bearer, a `ManualClock` bound through `ports`, `admin()` to age rows, change a status or break writes, `observe()` as a read-only second connection, the capture reader, and `trace()` for statement shapes); assert what the application did from `observe()`, never from its own pool. `stop()` closes everything the kit opened, attempts every close, reports every failure and does nothing a second time; a start that fails part-way closes what it had opened (`src/test-support/cleanup.ts`). Nothing in the production tree imports `src/test-support/`, and no setting moves the application's time (`integration-kit.test.ts`). Never add a skip or weaken an assertion to get green. `spawnSync` needs a large `maxBuffer` when a run fails loudly, or the failure shows as `exit null`. Six tests under `test` and two under `test:db` need a real `SIGTERM` (the worker's among them) and skip on Windows, and one unit test of the capture sink's file modes skips there too (a skip is not a pass): run them in WSL2, Linux or CI.
