# Ops Portal (`apps/ops-web`)

React, Vite, TanStack Query and React Router. It is the application shell, the session foundation (S0.38) and the UI foundation until the slices add screens. Requirements are in [surfaces/ops-portal.md](../../surfaces/ops-portal.md) and [surfaces/overview.md](../../surfaces/overview.md). Run it as [DEVELOPMENT.md](../../DEVELOPMENT.md) says; what B0.3 and B0.5 left undone is in the runbook ([B0.2 and B0.3](../../delivery/planning/BOOTSTRAP_B0_RUNBOOK.md#carried-forward-from-b02-and-b03), [B0.5](../../delivery/planning/BOOTSTRAP_B0_RUNBOOK.md#carried-forward-from-b05)).

## Layout

- `src/app/`: routes (`createAppRoutes` in `routes.tsx`: the signed-in routes are the registry's, `src/app/navigation/route-registry.tsx`, the children of `AuthenticatedOpsShell` under `RequireSession`; the seven pre-sign-in screens, `src/app/pages/pre-sign-in/` (`PRE_SIGN_IN_ROUTES`, the two recovery screens of S0.52 among them), are siblings of the guard; the six signed-in identity screens are the landing, `src/app/pages/LandingPage.tsx`, and `src/app/pages/staff/`; the two vendor screens of S0.52 are `src/app/pages/vendors/`, reading through `src/platform/vendor/`; the four rider screens of S0.60 are `src/app/pages/riders/`, reading through `src/platform/rider/`), pages and providers. `src/components/`: structural components, `PageHeader`, `PrimaryNavigation`, `side-menu/` (the `SideMenu` of the signed-in shell), `brand/` (`BrandLockup`) and `auth-art/` (the split screen's decorative panel); `src/components/ui/<name>/`: the UI primitives (Icon and IconButton, Button and ButtonLink, Link, Alert, Field, Input, Textarea, Select, Checkbox, PasswordInput, CodeInput, OneTimeSecret, QrCode, loading, Skeleton, EmptyState, ForbiddenState, StatusBadge, Table, ReadState, Dialog and AlertDialog, ReasonSelect, ReasonConfirmationDialog, ConfirmationDialog, and `form/use-submission`), each with its CSS and tests.
- `src/styles/`: `tokens.css` is the one token source, `base.css` the frame and element defaults, and `fonts.css` the self-hosted Inter (files and licence record in `src/assets/fonts/`, licence text in `public/licenses/`; never a CDN, never inlined). `src/assets/brand/` holds the runtime copy of the logo, copied byte for byte from [design/assets/brand/](../../design/assets/brand/README.md) (`test/logo.test.ts`); import it with `?no-inline`, or Vite inlines it as a `data:` URI. `public/favicon.svg` is the runtime copy of the approved symbol: the browser-tab icon, and the mark of `BrandLockup` in the side menu and the split screen (`test/favicon.test.ts`, 25 October 2026). `src/assets/auth/` holds the web-sized copies of the Product Owner's photographs (`design/images`) for the split screen, with their record ([README](src/assets/auth/README.md), `test/auth-art.test.ts`). `src/showcase/`: the development-only component showcase; nothing may import it, and the production build holds no trace of it.
- `src/platform/api/`: the client provider (`useApiClient()`), `answerOf` (status, `ETag`, declared violations) and `useCommandKeySlot` (`Idempotency-Key`, bound to the session). `src/platform/session/`: the session store, `SessionBoundary`, guards and `useSignOut`. `src/platform/problem/`: a failure read as a kind and worded by operation, context and code. `src/platform/reasons/`: the reason catalogue query. `src/platform/secrets/`: transient credentials. `src/platform/auth/`: the grant a link carries (`tokenFromHash`, `useGrantToken`), the password rule and the judgement of the pre-sign-in answers. `src/platform/staff/`: the identity screens' reads (`use-staff-queries.ts`), commands (`staff-commands.ts`) and the judgement of their answers (`staff-shape.ts`). `src/platform/time/`: `formatInstant`. `src/platform/query/`: query setup. `src/test-support/`: test helpers, never imported by application code.
- `config/`: the development proxy and the client-environment guard, both used by Vite. `test/`: guard tests and the browser tests.

## Rules

- API types come only from `@melarc/api-client` (its schema types and operations; the transport from `@melarc/api-client/browser`). Never hand-write a request or response type. `test/no-duplicate-wire-types.test.ts` catches only a type named like a contract schema and an import from any other path, and pins which files may import the browser client: a copy under another name passes it, so this rule rests on review. UI-only form and presentation models are fine.
- The browser talks only to its own origin, `/api/v1`, which the dev server proxies to the API (`config/dev-proxy.ts`). The dev server listens on `http://127.0.0.1:5172` and on no other port, the one origin the API allows (`OPS_ORIGIN`, `test/dev-server-origin.test.ts`): open that address, because `localhost` can lead elsewhere and a sign-in from any other origin is refused with 403. It is not Vite's default 5173, which other projects on the machine take. The API's probes are not reachable from it. Only `VITE_` variables reach the bundle, and the build refuses names that look like secrets. Never put a secret in the browser; [.env.example](.env.example) lists the settings.
- UI follows the [design system](../../design/DESIGN_SYSTEM.md) and [component patterns](../../design/COMPONENT_PATTERNS.md). Use the components in `components/ui/` before writing markup, and take every colour, size and space from `tokens.css`. Icons come from `src/components/ui/icon/icons.ts`, the one file that imports `lucide-react` (a test and a lint rule say so): name an icon by its meaning, draw it with `<Icon>`, make an icon-only control an `IconButton` with its required `label`, and never hand-draw an `<svg>`. `scripts/design-tokens.test.ts` fails on a colour written anywhere else and on a focus rule without an outline. Add a component only when a pattern names it or the task needs it, and record it in the patterns. A missing or contested value is surfaced, never invented. The logo identifies and is never a link; take no variant of it that [the brand README](../../design/assets/brand/README.md) does not record as approved.
- The session is an `HttpOnly` cookie the page cannot read: `GET /auth/session` is the only source of who is signed in, read once (`useEnsureSession`, from `RequireSession`), never polled or refetched on focus (every accepted request counts as activity). `SessionBoundary` scopes the one API client, so it judges every call the page makes, direct ones outside a cache included: an answer to a request sent for a session that has ended or been replaced is refused as `StaleSessionError` (a late error cannot end the next session, a late success cannot show or cache anything for it), and a session-ending answer (`SESSION_INVALID`/`SESSION_SUPERSEDED`) to a current request ends it once: cache cleared, person forgotten, landing, whose guard goes to sign-in; `AppProviders` wires it. Clearing the cache does not stop a running mutation, so nothing relies on it. A guard is the screen's half only: `RequirePermission` names a permission key, never a role, and the server checks every request. The frame has three layouts, chosen by the route tree and never by a page (`useFrameLayout`): neutral, sidebar and split. The neutral frame shows no navigation, user menu or sign-out; `AuthenticatedOpsShell` draws its side menu into the frame (the sidebar layout: no banner, the menu names the product) for the signed-in routes only, collapsible on a wide screen and sliding in over an inert page on a narrow one, its state in memory and never in web storage, and signs out through `useEndSession`, the one action that ends a session.
- A screen implements the [nine interface states](../../surfaces/ops-portal.md#8-the-nine-interface-states), and its test says which test shows each or why it does not apply (`describeInterfaceStates`): the error state maps the machine `code` to copy (`problemOf`) and never shows `message`; a read is a `ReadState`. Read every call with `answerOf(result)` (or `unwrap`), never `if (error)`: a 403 with an empty body has no `error`. A failure is an `ApiError` (kind, status, code, requestId; an `OperationFailure` adds the `violations`, place and rule only, never a value); its message never holds server text. A command sends its `Idempotency-Key` through `useCommandKeySlot().run(command, send)`: a new key for each command, the same one only while the outcome is unknown and the command unchanged. A command that asks for a reason and a confirmation is a `ReasonConfirmationDialog` over `useConfirmedCommand`: a retry is offered only for an act that takes a key or is idempotent by its nature (the reason operations take no key: they offer the record, except `revokeSession`, which ends an ended session as done and offers both, and `revokeStaffTrustedBrowsers`, which takes an `Idempotency-Key` because "every valid browser" is not a fixed set, and so offers both). A route loader cannot reach the client (the router is built before the providers): fetch in the page. ESLint refuses `fetch`, XHR, web storage, `window.open`, `dangerouslySetInnerHTML` and `eval` in application code.
- The pre-sign-in screens (`/sign-in`, `/sign-in/mfa`, `/setup/credential`, `/setup/mfa`, `/setup/mfa/complete`, `/recovery`, `/recovery/complete`) draw no shell in any state and ask for no session (`pre-sign-in-neutral-frame.test.tsx`); they sit in the frame's split-screen layout (`AuthSplitLayout`: decorative photography beside the form from 64rem, in a column of at most 30rem). The password step has one refusal and no locked state; the lock is told at the second step alone. A link page reads its grant once from the fragment with `useGrantToken` (the entry is replaced, opening the page redeems nothing, the token goes only in the body of the one request that redeems it) and has one error for a grant that cannot be used (`GrantProblem`). What two screens hand each other (the sign-in challenge; the authenticator's material and continuation grant) lives in memory in `PreSignInFlowLayout`, never in the address, the history state or a storage. A page that returns from a call empties the password or code it sent (`emptyField`). The second step offers one choice, _Remember this browser for N days_ (`Checkbox`, off unless the person turns it on; N is the challenge's `trusted_browser_days` and never the page's own; sent as `trust_browser` only when ticked), and no page ever sees the credential it asks for: the cookie is `HttpOnly`, and a `200` at `/sign-in` for a privileged person is a remembered browser, handled as any `200`.
- The six signed-in identity screens (`/`, `/admin/staff`, `/admin/staff/new`, `/admin/staff/{id}`, `/admin/staff/{id}/mfa/reset`, `/admin/sessions`) read through `platform/staff/`, and what they believe of an answer is what `staff-shape.ts` judged: a field it does not read goes nowhere, so no credential has a way onto them (`test/staff-no-credential-display.test.ts` fails on any import or name that draws, holds or reads one, and each screen's test plants one in the answer). A page about one profile is a `WithProfile` and acts on the version it read (`If-Match` exactly as sent); it does not read the profile again, because a version read twice changes under the person's hand. The acts offered follow the status, the held keys and what the record says and decide nothing (a new first setup link only for a profile with no authenticator, since a password already set is refused; the maker of a profile is offered its approve and reject acts too, because the session lists keys and no tiers, so the page cannot tell a Platform Admin, who may decide what they made, from another maker, whom the server refuses with `SELF_APPROVAL_FORBIDDEN`); an active or suspended profile offers _Start password recovery_ to a holder of `staff.credential.recover` (S0.52), whose answer says where the link went and never carries it. `/recovery` has one success for every address and no destination field; `/recovery/complete` reads its token as a setup link does and has one error for every dead link. `/admin/vendors` and `/admin/vendors/{id}` show a vendor's authentication status and browsers as facts only (`test/staff-no-credential-display.test.ts` scans them too), attribute a browser the shared account registered to the organisation (AC-15), and offer a re-issue for an account with no secret and a recovery for one with a secret, each to its own key. The trusted browsers (staff-authentication.md §5.8) are `/account/trusted-browsers` (any signed-in session; `listTrustedBrowsers`; a `ConfirmationDialog` removes one; the menu offers it to every session because the session lists no second-factor fact) and a section of an enrolled profile for a holder of `staff.session.revoke` (`TrustedBrowsersSection`: `listStaffTrustedBrowsers`, and one reason dialog that offers the reasons of `revokeSession` and words a failure for `revokeStaffTrustedBrowsers` through `copyOperation`); `parseTrustedBrowser` reads six fields and has no place for a credential. Approving is a `ConfirmationDialog` (primary confirm), the acts that need a reason are `ReasonConfirmationDialog`s with the `operation` and the `branch` the record names. Times are `formatInstant` (24-hour, Accra); a role or a hub is shown by name or not at all, never by id.
- The four rider screens (S0.60: `/admin/riders`, `/admin/riders/{id}`, `/admin/riders/{id}/device/register`, `/admin/riders/{id}/device`) read through `platform/rider/` (`rider-shape.ts` judges every answer; `test/rider-contract.test.ts` holds the guards to the contract) and show a rider's identity and readiness only: never a PIN, a hash or a key, which no answer carries and no page has a field for. **The enrolment code is the one credential they draw.** `EnrolmentCode` is the only place that draws it (the S0.39c `QrCode`, as modules: never as text, a link or an attribute, and no copy button) and `use-enrolment-code.ts` the only place that holds it (`useTransientSecret`: gone on navigation, expiry, completion, `pagehide` and a session end, and refused when its answer arrives late); `test/rider-no-credential-display.test.ts` reads the syntax tree and fails on a second place. The first binding sends an `Idempotency-Key` and no version (a lost answer is tried again under the same key); a replacement sends the version read, a reason and a one-line verification note (`Textarea`) and no key (a lost answer offers only a look at the rider, because a new code ends the old one); the report of a loss is a `ReasonConfirmationDialog` with `withNote={false}` and sends a reason alone. What a page offers follows the held keys (`staff.device.register`, `staff.device.reregister`, `staff.device.revoke`) and the rider's status and decides nothing: the server checks every request.
- A form uses `useSubmission` (pending, no duplicate submit, focus on the first invalid field) and `PasswordInput`/`CodeInput`, and never echoes a value in a message. A secret (a password, a TOTP seed, a QR payload) is read from the form at submit time and held with `useTransientSecret` (`begin()` a flow before the request, send with `flow.signal`, then `hold(flow, secret, lifetime)`: an answer to a flow that navigation, completion, a session end, `pagehide` or unmount has called off is refused; the lifetime is the lesser of the server's, `lifetimeFromExpiry`, and the provisional 15 minutes), never in a query, a mutation (mutations are collected at once, but a result still lives while the screen holds it), storage, a log, the address or an attribute; it has no copy button and no `name`; the `secret-hygiene` sentinel test is the pattern to copy. `uqr` (the encoder, behind `qr-matrix.ts` alone) and `jsqr` (the test-only decoder) are the QR dependencies.
- A generic component never decides business policy, and the server stays authoritative (patterns sections 24 and 25). A new interactive component is tested by keyboard in jsdom and driven in the showcase in a real browser (keyboard, 320 px, enlarged text, forced colours, reduced motion, axe with WCAG 2.2). A signed-in screen is added to `SIGNED_IN_ROUTES` and to nothing else: its path, its element, its permission key (or `ANY_SIGNED_IN_SESSION`) and its menu entry (or `null`); navigation and guards name a permission key and never a role (`test/navigation-no-roles.test.ts`). jsdom has no `showModal()`: `test/setup-components.ts` stands in for it, and the inertness of the page behind a dialog is proved in the browser.

## Tests

While editing, `pnpm run test:affected` runs the unit tests and browser specs a change reaches, each spec against the production build (the development-server projects are the gate's, or `--with-dev-browser`) ([the loop](../../DEVELOPMENT.md#the-development-loop-and-the-gate)): a spec does not import its pages, so `SPEC_AREAS` in `scripts/affected.ts` gives each spec its page folders, and a new page folder or spec goes there in the same change. `pnpm --filter @melarc/ops-web test` runs Vitest with Testing Library; a test of the application replaces only the network (`src/test-support/fake-api.ts`), so the real client, router and providers run. `pnpm run test:browser` runs Playwright and needs Chromium: the shell against a fresh production build (the session read is answered by `test/browser/support/api.ts`), the components against the development server, and the pre-sign-in screens against both (`pre-sign-in.spec.ts`: the five operations are answered by `test/browser/support/pre-sign-in-api.ts`, and the development server's strict mode runs every effect twice, which is what a page that reads a grant from the address must survive). The six signed-in identity screens run the same two ways (`staff.spec.ts`, against the stateful stand-in `test/browser/support/staff-api.ts`, which plants a credential in answers that never carry one), and so do the two recovery screens (`recovery.spec.ts`, answered by `pre-sign-in-api.ts`) and the four rider screens (`riders.spec.ts`, against the stateful stand-in `test/browser/support/rider-api.ts`, which plants a PIN hash, a key and an attestation in answers that never carry them and hands out sentinel enrolment codes: the painted code is decoded by the independent decoder and looked for in every place it could be left). CI sets `MELARC_BROWSERS=chromium,firefox,webkit`; install Firefox and WebKit ([DEVELOPMENT.md](../../DEVELOPMENT.md)) to do the same locally. The showcase's secret demo has a request fixture (`Ask the server for a demo setup key`) that `secrets.spec.ts` answers itself and holds, to prove a late answer is never drawn. Playwright keeps a trace of a failed test: that is accepted because these pages are the synthetic showcase and stubbed shell, and is no authorization for a test that types or receives a real credential (S0.43): it turns tracing, screenshots and video off for its own context.
