# Ops Portal (`apps/ops-web`)

React, Vite, TanStack Query and React Router. It is the application shell, the session foundation (S0.38) and the UI foundation until the slices add screens. Requirements are in [surfaces/ops-portal.md](../../surfaces/ops-portal.md) and [surfaces/overview.md](../../surfaces/overview.md). Run it as [DEVELOPMENT.md](../../DEVELOPMENT.md) says; what B0.3 and B0.5 left undone is in the runbook ([B0.2 and B0.3](../../delivery/planning/BOOTSTRAP_B0_RUNBOOK.md#carried-forward-from-b02-and-b03), [B0.5](../../delivery/planning/BOOTSTRAP_B0_RUNBOOK.md#carried-forward-from-b05)).

## Rules

- API types come only from `@melarc/api-client` (its schema types and operations; the transport from `@melarc/api-client/browser`). Never hand-write a request or response type. `test/no-duplicate-wire-types.test.ts` catches only a type named like a contract schema and an import from any other path, and pins which files may import the browser client: a copy under another name passes it, so this rule rests on review. UI-only form and presentation models are fine.
- The browser talks only to its own origin, `/api/v1`, which the dev server proxies to the API (`config/dev-proxy.ts`). The dev server listens on `http://127.0.0.1:5172` and on no other port, the one origin the API allows (`OPS_ORIGIN`, `test/dev-server-origin.test.ts`): open that address, because `localhost` can lead elsewhere and a sign-in from any other origin is refused with 403. It is not Vite's default 5173, which other projects on the machine take. The API's probes are not reachable from it. Only `VITE_` variables reach the bundle, and the build refuses names that look like secrets. Never put a secret in the browser; [.env.example](.env.example) lists the settings.
- UI follows the [product design direction](../../design/PRODUCT_DESIGN_DIRECTION.md), the [design system](../../design/DESIGN_SYSTEM.md) and [component patterns](../../design/COMPONENT_PATTERNS.md). Read the direction before changing a screen: its four page templates (queue workspace, record, task form, builder) and the redesign it records (5 November 2026; steps R1 to R7 of [the plan](../../delivery/IMPLEMENTATION_PLAN.md#3a-the-ops-portal-redesign)) are approved direction; the templates are built in `components/ui/templates/` (step R6, ACTIVE: a screen is composed from one and passes in its data, acts and words, and the template decides none of them) and a screen is claimed to follow one only once it uses it: the tokens and the two themes are step R2's and are built, the library foundation is step R3's and is built, the shell (the sidebar, the top bar, the palette, the theme control and My work) is step R4's and is built, and the other components and the screens are as built. A page asks a table or the queue workspace to put focus on a row through its handle (`DataTableHandle`, `QueueWorkspaceHandle`) and never names a class of the kit in a string: `test/pages-no-kit-classes.test.ts` fails if a file of `src/app/` does (no file is exempt: the manifest list, the last that knew the old table's markup, moved in R7a). Say which reference pattern a change adapts, keep a presentation change apart from a behavior change, and raise a change of business rule or technical foundation before building it. Use the components in `components/ui/` before writing markup, and take every colour, size and space from `tokens.css`. Icons come from `src/components/ui/icon/icons.ts`, the one file that imports `lucide-react` but for the primitives (a test and a lint rule say so): name an icon by its meaning, draw it with `<Icon>`, make an icon-only control an `IconButton` with its required `label`, and never hand-draw an `<svg>`. `scripts/design-tokens.test.ts` fails on a colour written anywhere else and on a focus rule without an outline. Add a component only when a pattern names it or the task needs it, and record it in the patterns. A missing or contested value is surfaced, never invented. A refusal is worded as the capability in plain words, never a raw permission key or a role ([PRODUCT_DESIGN_DIRECTION §6.5](../../design/PRODUCT_DESIGN_DIRECTION.md#65-on-screen-language)): the words are one table, `src/platform/problem/capability-words.ts` (`cannotText`, `capabilityOf`, and `refusalText`, the one function that tells every kind of refusal: a missing key, a higher authority, a hub, a different approver), which `ForbiddenState`, the copy files and the pages draw, and a test holds every key a screen can ask for to a sentence; a new permission key a screen asks for gets its words there, and a page passes the kind of the refusal and what it holds (`refusalText(problem.forbidden, 'dispatch.read', { of: 'riders' })`) and writes no sentence of one (`test/refusal-words-one-table.test.ts` reads every file of `src/app/`). A page that reads something else with the same key passes words of the same table to the same sentence (`cannotText(key, 'see pickup runs')`, the `capability` of `ForbiddenPage` and `ReadState`: a `CapabilityWords`, a value of the table, so free text does not compile) and makes no sentence of its own. **A key is on no screen, held by two guards:** `test/no-permission-key-on-screen.test.ts` reads the syntax tree (the table of words included) and fails on a key written where a screen could show it, put together from parts, or held by a constant under any name, and lets one through only as the first argument of `holds(`/`cannotText(`, as the `permission`/`decidedBy` of the kit components it lists, in a route's `access` and as a key of the table; and the runtime half catches what reading cannot: the render helpers of the page tests (`renderApp`, `renderWithProviders`: `src/test-support/permission-keys.ts`) and `watchPage` of the browser tests fail when a key of the catalogue (`contracts/permissions.md`) is drawn as text or in an attribute, at any moment. The logo identifies and is never a link; take no variant of it that [the brand README](../../design/assets/brand/README.md) does not record as approved. The Overview has a delivery brief, [design/OVERVIEW_DASHBOARD_DESIGN.md](../../design/OVERVIEW_DASHBOARD_DESIGN.md) (the landing `/` becomes My work and the Overview's place is the Today group; the reference's look is superseded): reference only, so build no dashboard section, placeholder route, timer or panel of sample figures unless a bounded task connects one, and never draw a sample or a missing figure as a result or as zero. Its sections follow [the Ops surface matrix](../../surfaces/ops-portal.md#the-overview-section-authorization-and-destinations), and its refresh rules (automatic while visible, background activity, no keep-alive) are the brief's, for the Overview only.
- New behaviour no native element has (a calendar, a menu, a searchable list) comes from the shadcn/ui primitives, through a component of `src/components/ui/` and never from a page ([design system §29.2](../../design/DESIGN_SYSTEM.md#292-the-component-foundation)): Radix UI (`radix-ui`, `@radix-ui/*`), cmdk, vaul, sonner and react-day-picker are imported only under `src/components/primitives/`, by import, dynamic import or require (an ESLint rule and `test/primitives-door.test.ts`), and a primitive is imported only by `src/components/ui/`, the showcase and another primitive. React Aria Components was removed on 6 November 2026 ([COMPONENT_PATTERNS §37](../../design/COMPONENT_PATTERNS.md#phasing-out-react-aria-components)): nothing imports it. Motion (`motion`, a pinned dependency) is imported only under `src/components/ui/`, through `src/components/ui/motion/motion.ts` (an ESLint rule and `test/motion-door.test.ts`): a component never writes a duration or an easing, `useMotion()` reads them from the motion tokens and makes everything instant under `prefers-reduced-motion: reduce`, and what a stylesheet can do on the tokens is left to it ([design system §24a](../../design/DESIGN_SYSTEM.md#24a-interaction-primitives)). A page names a component and never a library type or date object, and takes today as text from `todayText` (`platform/time`), never from the date helpers (`date-value.ts`, `day-first.ts`). `DatePicker` takes and gives `YYYY-MM-DD` text, is one field typed as `DD/MM/YYYY` and read strictly, correcting nothing (only a whole, real date is given; a day its month does not have is refused as `There is no 30 February` and a year in fewer than four digits or below 1900 as `Enter the year in full, for example 2026`, by the Product Owner's decisions of 7 November 2026; the page keeps its date until the person leaves, and Enter in the field, with a text that is not a date, settles it as leaving does and does not send the form), is fixed to day-month-year, Monday first and English (`DATE_LOCALE`, not the browser's), and takes "today" in Accra; no page draws `<input type="date">`. No project-wide move to Ant Design, MUI or another UI framework. TanStack Table (the queue grid, imported only under `src/components/ui/data-table/`: an ESLint rule and `test/tanstack-door.test.ts`) and Motion are pinned dependencies, the older `QueueTable`, `Table` and `components/PageHeader` are gone (run 5, Stage 4: every screen is composed from a template and the kit's `DataTable` and `PageHeader`; the paging hook `src/components/ui/queue-table/use-queue-paging.ts` stays), and advanced grid behavior is not built by hand ([design system §23, §24a](../../design/DESIGN_SYSTEM.md#24a-interaction-primitives)).
- Adding a component: through the shadcn MCP server (`.mcp.json` runs the pinned `shadcn` installed here, and the official registry only: `components.json` has `registries: {}`) or the CLI (`pnpm --filter @melarc/ops-web exec shadcn add <name>`), which writes into `src/components/primitives/`. Restyle it through the mapped tokens only (no raw colour, no Tailwind palette colour, no px a token owns: `test/primitives-tokens.test.ts`) and review every generated file: the CLI leaves `import { cn } from "cn"` (use `@/lib/utils`) and may add `next-themes` (use `useResolvedTheme`), and both are wrong. Then wrap or compose it in `src/components/ui/`, add it to the showcase (`src/showcase/PrimitivesShowcase.tsx`) in real Melarc copy, and add its tests and its package's licence (`test/shadcn-licences.test.ts`, `test/primitives-door.test.ts`, `test/browser/primitives.spec.ts` and `test/browser/primitives-policy.spec.ts` hold what exists). Never paste from an unvetted registry or a URL.
- The session is an `HttpOnly` cookie the page cannot read: `GET /auth/session` is the only source of who is signed in, read once (`useEnsureSession`, from `RequireSession`), never polled or refetched on focus (its permission keys are fixed for the life of the session, and the read is `background`: only a `qualifying` route extends the idle lifetime). `SessionBoundary` scopes the one API client, so it judges every call the page makes, direct ones outside a cache included: an answer to a request sent for a session that has ended or been replaced is refused as `StaleSessionError` (a late error cannot end the next session, a late success cannot show or cache anything for it), and a session-ending answer (`SESSION_INVALID`/`SESSION_SUPERSEDED`) to a current request ends it once: cache cleared, person forgotten, landing, whose guard goes to sign-in; `AppProviders` wires it. Clearing the cache does not stop a running mutation, so nothing relies on it. A guard is the screen's half only: `RequirePermission` names a permission key, never a role, and the server checks every request. The frame has three layouts, chosen by the route tree and never by a page (`useFrameLayout`): neutral, sidebar and split. The neutral frame shows no navigation, user menu or sign-out; `AuthenticatedOpsShell` draws its sidebar and its top bar into the frame (the sidebar layout: the top bar is the banner, the sidebar names the product) for the signed-in routes only, the sidebar a rail below 1280px and a sheet under 768px, its state in memory and never in web storage (the one thing kept in the browser is the choice of theme, in the one module that is the exception to the rule, named in `eslint.config.mjs`), and signs out through `useEndSession`, the one action that ends a session.
- A screen implements the [nine interface states](../../surfaces/ops-portal.md#8-the-nine-interface-states), and its test says which test shows each or why it does not apply (`describeInterfaceStates`): the error state maps the machine `code` to copy (`problemOf`) and never shows `message`; a read is a `ReadState`. Read every call with `answerOf(result)` (or `unwrap`), never `if (error)`: a 403 with an empty body has no `error`. A failure is an `ApiError` (kind, status, code, requestId; an `OperationFailure` adds the `violations`, place and rule only, never a value); its message never holds server text. A command sends its `Idempotency-Key` through `useCommandKeySlot().run(command, send)`: a new key for each command, the same one only while the outcome is unknown and the command unchanged. A command that asks for a reason and a confirmation is a `ReasonConfirmationDialog` over `useConfirmedCommand`: a retry is offered only for an act that takes a key or is idempotent by its nature (the reason operations take no key: they offer the record, except `revokeSession`, which ends an ended session as done and offers both, and `revokeStaffTrustedBrowsers`, which takes an `Idempotency-Key` because "every valid browser" is not a fixed set, and so offers both). A route loader cannot reach the client (the router is built before the providers): fetch in the page. ESLint refuses `fetch`, XHR, web storage, `window.open`, `dangerouslySetInnerHTML` and `eval` in application code (web storage has one exception, `src/platform/theme/theme-choice.ts`, named in the ESLint configuration: the choice of theme, a non-sensitive preference, [PRODUCT_DESIGN_DIRECTION §7](../../design/PRODUCT_DESIGN_DIRECTION.md#7-when-a-proposal-needs-a-product-decision)).
- The pre-sign-in screens (`/sign-in`, `/sign-in/mfa`, `/setup/credential`, `/setup/mfa`, `/setup/mfa/complete`, `/recovery`, `/recovery/complete`) draw no shell in any state and ask for no session (`pre-sign-in-neutral-frame.test.tsx`); they sit in the frame's split-screen layout (`AuthSplitLayout`: decorative photography beside the form from 64rem, in a column of at most 30rem). The password step has one refusal and no locked state; the lock is told at the second step alone. A link page reads its grant once from the fragment with `useGrantToken` (the entry is replaced, opening the page redeems nothing, the token goes only in the body of the one request that redeems it) and has one error for a grant that cannot be used (`GrantProblem`). What two screens hand each other (the sign-in challenge; the authenticator's material and continuation grant) lives in memory in `PreSignInFlowLayout`, never in the address, the history state or a storage. A page that returns from a call empties the password or code it sent (`emptyField`). The second step offers one choice, _Remember this browser for N days_ (`Checkbox`, off unless the person turns it on; N is the challenge's `trusted_browser_days` and never the page's own; sent as `trust_browser` only when ticked), and no page ever sees the credential it asks for: the cookie is `HttpOnly`, and a `200` at `/sign-in` for a privileged person is a remembered browser, handled as any `200`.
- The six signed-in identity screens (`/`, `/admin/staff`, `/admin/staff/new`, `/admin/staff/{id}`, `/admin/staff/{id}/mfa/reset`, `/admin/sessions`) read through `platform/staff/`, and what they believe of an answer is what `staff-shape.ts` judged: a field it does not read goes nowhere, so no credential has a way onto them (`test/staff-no-credential-display.test.ts` fails on any import or name that draws, holds or reads one, and each screen's test plants one in the answer). A page about one profile is a `WithProfile` and acts on the version it read (`If-Match` exactly as sent); it does not read the profile again, because a version read twice changes under the person's hand. The acts offered follow the status, the held keys and what the record says and decide nothing (a new first setup link only for a profile with no authenticator, since a password already set is refused; the maker of a profile is offered its approve and reject acts too, because the session lists keys and no tiers, so the page cannot tell a Platform Admin, who may decide what they made, from another maker, whom the server refuses with `SELF_APPROVAL_FORBIDDEN`); an active or suspended profile offers _Start password recovery_ to a holder of `staff.credential.recover` (S0.52), whose answer says where the link went and never carries it. `/recovery` has one success for every address and no destination field; `/recovery/complete` reads its token as a setup link does and has one error for every dead link. `/admin/vendors` and `/admin/vendors/{id}` show a vendor's authentication status and browsers as facts only (`test/staff-no-credential-display.test.ts` scans them too), attribute a browser the shared account registered to the organisation (AC-15), and offer a re-issue for an account with no secret and a recovery for one with a secret, each to its own key. The trusted browsers (staff-authentication.md §5.8) are `/account/trusted-browsers` (any signed-in session; `listTrustedBrowsers`; a `ConfirmationDialog` removes one; the menu offers it to every session because the session lists no second-factor fact) and a section of an enrolled profile for a holder of `staff.session.revoke` (`TrustedBrowsersSection`: `listStaffTrustedBrowsers`, and one reason dialog that offers the reasons of `revokeSession` and words a failure for `revokeStaffTrustedBrowsers` through `copyOperation`); `parseTrustedBrowser` reads six fields and has no place for a credential. Approving is a `ConfirmationDialog` (primary confirm), the acts that need a reason are `ReasonConfirmationDialog`s with the `operation` and the `branch` the record names. Times are `formatInstant` (24-hour, Accra); a role or a hub is shown by name or not at all, never by id.
- The four rider screens (S0.60: `/admin/riders`, `/admin/riders/{id}`, `/admin/riders/{id}/device/register`, `/admin/riders/{id}/device`) read through `platform/rider/` (`rider-shape.ts` judges every answer; `test/rider-contract.test.ts` holds the guards to the contract) and show a rider's identity and readiness only: never a PIN, a hash or a key, which no answer carries and no page has a field for. **The enrolment code is the one credential they draw.** `EnrolmentCode` is the only place that draws it (the S0.39c `QrCode`, as modules: never as text, a link or an attribute, and no copy button) and `use-enrolment-code.ts` the only place that holds it (`useTransientSecret`: gone on navigation, expiry, completion, `pagehide`, a session end and the asking for another code, which lets go of the held one before the request because a lost answer may mean it was already replaced, so no code is on the screen while a request is under way or in doubt and the page shows the command's own state, with a note that the earlier code is no longer shown, which ends nothing; and refused when its answer arrives late); `test/rider-no-credential-display.test.ts` reads the syntax tree and fails on a second place. The first binding sends an `Idempotency-Key` and no version (a lost answer is tried again under the same key); a replacement sends the version read, a reason and a one-line verification note (`Textarea`) and no key (a lost answer offers only a look at the rider, because a new code ends the old one); the report of a loss is a `ReasonConfirmationDialog` with `withNote={false}` and sends a reason alone. What a page offers follows the held keys (`staff.device.register`, `staff.device.reregister`, `staff.device.revoke`) and the rider's status and decides nothing: the server checks every request. What these screens still lack, the focus transitions and the lapse alert's styling among it, is in [the plan's §7.47](../../delivery/planning/SLICE-000-IMPLEMENTATION-PLAN.md#747-carried-from-s053-to-s060-27-october-2026).
- The pickup screens (S1.19: `/pickup-requests`, `/pickup-requests/new`, `/pickup-requests/{id}`, `/pickup-requests/{id}/exception`, `/approvals`) compute no price, total, fee or zone: money stays an integer of pesewas from the wire to `MoneyAmount`, the estimate is the server's and is told as indicative and provisional (never a price or a total), and a fee is drawn only as the server snapshotted it. Cancellation reasons come from the `PICKUP_CANCELLATION` catalogue and no code is written in the page (an empty catalogue is said in plain words, as the rule above asks); an escalation, an extension, a waiver and a late booking's decision take a mandatory note instead. Every act sends the version read (`If-Match`) and, only where its operation declares one, a fresh `Idempotency-Key` (`pickup-commands.ts` says which); the charge decision of a cancellation is asked, with nothing chosen, only when the read says a rider holds the run (`rider_assigned`). What a page offers follows the record and the held keys and decides nothing: the one-package exception's maker-checker rule is the server's (`SELF_APPROVAL_FORBIDDEN` is told as the rule, in plain words of the capability of whoever approves instead), and no wording names a role (`pickup-copy.test.ts`). The queue draws each request twice, as a table row and as a card, from one facts model (`pickup-queue-view.tsx`, [patterns §22f](../../design/COMPONENT_PATTERNS.md#22f-queuetable)): a fact is added to both, and a unit test reads one of them (jsdom applies no CSS), the browser spec proves only one is shown. The queue's place (cursors, scroll, the request opened) is kept for one visit to that request, in `QueueContinuityScope`'s memory only: never the address, a storage or a row of a response, and `listPickupRequests` is always asked again on the way back. ## Tests

While editing, `pnpm run test:affected` runs the unit tests and browser specs a change reaches, each spec against the production build (the development-server projects are the gate's, or `--with-dev-browser`) ([the loop](../../DEVELOPMENT.md#the-development-loop-and-the-gate)): a spec does not import its pages, so `SPEC_AREAS` in `scripts/affected.ts` gives each spec its page folders, and a new page folder or spec goes there in the same change. `pnpm --filter @melarc/ops-web test` runs Vitest with Testing Library; a test of the application replaces only the network (`src/test-support/fake-api.ts`), so the real client, router and providers run. `pnpm run test:browser` runs Playwright and needs Chromium: the shell against a fresh production build (the session read is answered by `test/browser/support/api.ts`), the components against the development server, and the pre-sign-in screens against both (`pre-sign-in.spec.ts`: the five operations are answered by `test/browser/support/pre-sign-in-api.ts`, and the development server's strict mode runs every effect twice, which is what a page that reads a grant from the address must survive). The six signed-in identity screens run the same two ways (`staff.spec.ts`, against the stateful stand-in `test/browser/support/staff-api.ts`, which plants a credential in answers that never carry one), and so do the two recovery screens (`recovery.spec.ts`, answered by `pre-sign-in-api.ts`) and the four rider screens (`riders.spec.ts`, against the stateful stand-in `test/browser/support/rider-api.ts`, which plants a PIN hash, a key and an attestation in answers that never carry them and hands out sentinel enrolment codes: the painted code is decoded by the independent decoder and looked for in every place it could be left), and the five pickup screens (`pickup.spec.ts`, against the stateful stand-in `test/browser/support/pickup-api.ts`, which plants a price in answers that never carry one), and the four manifest screens (`manifests.spec.ts`, against the stateful stand-in `test/browser/support/manifest-api.ts`, which answers the custody operations from the contract and plants a count of the hub's in every custody answer), and the message log (`messages.spec.ts`, against the stand-in `test/browser/support/messages-api.ts`, which plants a number in clear, a text and a code in answers that never carry them). The shadcn/ui primitives run the same two ways (`primitives.spec.ts`: WCAG 2.2 in both themes with each overlay open, and every overlay from the keyboard; `primitives-policy.spec.ts`: the production showcase under the strict policy). The shadcn/ui primitives have `primitives.spec.ts` (the development server: axe in both themes with each overlay open, and every overlay by keyboard) and `primitives-policy.spec.ts` (the production showcase under the strict policy), and the sign-in logo has `logo.spec.ts` (the production build: the white lockup on a dark ground, read back from the pixels).
