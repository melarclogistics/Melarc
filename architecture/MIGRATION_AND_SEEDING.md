# Migration and data seeding

> **Status:** ACTIVE SPECIFICATION — implementation status is stated separately
> **Version:** 0.16 (cleaned edition)
> **Date:** 4 October 2026
> **Owns:** how a Melarc environment comes into existence with the data it cannot function without, and how existing data and code are migrated
> **Governed by:** [PROJECT_MASTER_SPECIFICATION.md](../PROJECT_MASTER_SPECIFICATION.md) §42.6, §42.7, §46.3, §33.1, §45.4, §45.6
> **Authority:** Technical design implements the retained product requirements; it does not redefine product behavior.

## 1. Scope

Three things: what a new environment must be **seeded** with before it can function, how **schema and data migrations** are managed, and how **existing Melarc code and data** are brought across (§46.3).

**It carries no product authority**, and §3 is where that matters most: the bootstrap grants the highest authority in the system, so it is described here and **approved by the Product Owner**, not settled by an architecture document.

## 2. Why seeding is a first-class concern here

Most systems seed for convenience. Melarc has **two hard bootstrap dependencies** where the product does not function at all without seeded data, and both were found by asking who does the first act.

| Dependency| Without it|
|---|---|
| **The first two Platform Admins**| **Nobody can sign in.** No staff record can be created, because creating one requires an authenticated actor holding `staff.identity.create`. **The seed creates two administrators**, one for each of two custodians (`MSC-DEC-440`). Until 25 October 2026 that was also because with one nobody could approve the first profile; a Platform Admin now approves a profile they made ([permissions.md](../contracts/permissions.md) §6), but no administrator resets their own authenticator, so a lone administrator whose factor was lost could not be recovered|
| **The hub default zone**| §33.1 mandates a default that §33.3–4 forbid using at resolution time; `CONFLICT-023` reclassified it as **a hub-creation bootstrap seed**. A hub is created without a zone and takes no zone-dependent work until its zone catalogue is seeded: `SLICE-000` seeds the Accra hub without one, and `SLICE-001` seeds the launch hub's zones and fees (the Product Owner's decision of 29 October 2026)|

## 3. The bootstrap Platform Admins

### 3.1 The problem, stated exactly

`MSC-DEC-247` applied §30.8: a staff identity is created by a holder of `staff.identity.create` and activated by a **different** holder of `staff.identity.approve`. Both are authenticated acts requiring a session, and a session requires an `ACTIVE` staff identity ([state-machines.md](../contracts/state-machines.md) §13).

**At first boot, no identity exists. The maker-checker cannot start itself.** This is not a defect in §30.8 — it is a property of every maker-checker system, and the only question is whether the escape is deliberate and audited or improvised on a deployment call.

### 3.2 What the seed does, and what it deliberately cannot

**Approved by the Product Owner on 26 August, closing `OQ-088`.** The constraints below stand, each for both identities; **two things changed since**: the identity count, which `MSC-DEC-440` supersedes (*exactly one* became *exactly two*), and the credential constraint, which `MSC-DEC-260` corrected.

The seed creates **exactly two** `StaffIdentity` records, each `ACTIVE` with a Platform Admin bundle, outside the API, as part of environment provisioning (`MSC-DEC-440`, which supersedes `MSC-DEC-253`'s *exactly one*) — **each with its own unique work email, no permanent password, no MFA factor, and its own single-use bootstrap setup secret stored only as a hash**. **The pair is created in one transaction, so the staff table is never left holding one** *(derived: a failure between two inserts would leave one identity, and the empty-table guard would then refuse a re-run)*; the seed then refuses to run again, because the table is no longer empty. **Hub reach — decided 6 October 2026: each of the two holds an explicit all-hub grant**, written by the seed, so both reach every hub; **refined 8 October 2026: it is the explicit all-hub scope of each grant of the Platform Admin bundle that is meant to reach every hub, not an identity-level flag**, so the scope of the grant being exercised decides, a hub-limited grant held beside it is never widened, and mixed-scope bundles are tested. It is **never inferred from the Platform Admin bundle's name or from the absence of a hub** ([SECURITY_DESIGN.md](SECURITY_DESIGN.md) §14.2). `staff.identity.create` and `staff.identity.approve` are own-hub keys for every other holder, and the seeded grant is what lets one bootstrap administrator create the first profile, and the other approve it, at whichever hub it names.

**Two custodians, not one person.** **Production requires two distinct designated human custodians**, one for each identity. The pair is **not** two identities that one person controls: such a pair defeats the separation of custody this section exists for (no one person holds every way in, and each administrator's authenticator is reset by the other) and is not the bootstrap this section describes. Who the custodians are is a deployment input, and **the repository cannot verify that two identities belong to two people**, so this is a rule on the deployment and not a mechanical one.

**How the secrets reach the custodians** (Product decision, 8 October 2026). The provisioning step writes each custodian's bundle with exclusive creation, outside any checkout the process runs from, and never prints a secret. On POSIX it sets the mode of each file and refuses a folder or a file that another user owns or can reach; on Windows it reads the access control list of the folder before any file is made in it (a file takes its first list from its folder, and a handle that another account opened before the file was made private keeps its access) and refuses broad or foreign access there, and it reads the list of each file back after making it private and refuses broad or inherited access, because a POSIX mode alone is not access control there. The two bundles are separate and each names only the custodian it belongs to. **The provisioning step checks that the two custodians are distinct identifiers** — two different canonical work emails, refusing a pair that collapses to one — which is as far as a repository can go: that the identifiers belong to two people stays a rule on the deployment. The bundle file is deleted after handoff and the deletion recorded, and handover is documented. Each bundle is written **before the pair is committed**, and a bundle whose pair did not commit is removed on the next run against the same database, so an interrupted run leaves no pair, or a pair with its bundles; a crash between the file write and the commit can leave an orphan bundle, which the next run removes before it does anything else and which holds a secret for nobody, because no pair exists to redeem it. **Each bundle records which database it was written for** (a digest of the host, the port and the name of the database, never a credential), and a run removes only the bundles that name its own: a bundle of another database in the same folder belongs to a pair that did commit and is the only copy of a secret still to be handed over, so it is left alone and counted in what the command prints. One folder for each environment is still the rule. A secret lost before its password is set, and an MFA enrolment that lapsed, are recovered by §3.3a and never by a second seed, and neither creates another privileged identity or resets an MFA enrolment that has completed.

**As built (S0.30).** The seed is `pnpm --filter @melarc/api run bootstrap:seed -- --custodian "Full Name <work@email>" --custodian "Full Name <work@email>"`, run by an operator as the provisioning login (`DATABASE_SEED_URL` and `APP_ENV`, as for `db:seed`; the API refuses to start with either), after the reference seed. `BOOTSTRAP_CUSTODY_DIRECTORY` names the folder of the bundles: an absolute path outside any checkout (links and junctions are followed, so a folder that leads into one is refused), private to the user, one for each environment, with no default; the scripts read no `.env` file for it. The command judges its input first (exactly two custodians, two distinct canonical work emails: a pair that collapses to one creates nothing), then runs in **one transaction**: `melarc.bootstrap_status` locks the staff table against any other seed and the command refuses a table that holds an identity; it removes the bundles of an earlier run that did not commit (a file named and begun as a bundle that names this database's target, and nothing else, and only from an empty table; any other bundle is counted and left); `melarc.seed_bootstrap_administrators` ([migration 0019](../apps/api/migrations/0019_bootstrap_seed.sql)) writes both identities, their grants and their six events in one statement, with the shape fixed by the function and not by the caller; and each custodian's bundle is written, before the commit, in the order that keeps the secret off any file that is not private: created exclusively, made private to the user, **inspected**, and only then written. On POSIX the inspection reads the mode, the owner and the link count; on Windows it reads the access list back as a security descriptor, which must be protected, hold nothing inherited, nobody broad and nobody but the user, the local system and the administrators. A commit whose outcome is unknown removes nothing (if the pair did commit, the bundles are the only copies of its secrets), prints the run's correlation id and **does not infer a rollback from a missing audit event**: the transaction may still be finishing, and a read may be of a replica or by a role that cannot see the rows. The seed is its own reconciliation (a second run takes the same table lock first, so it waits for the original transaction, refuses a staff table that holds the pair, and sweeps this database's bundles only from an empty one), and a bundle is handed over only while its grant is still the current one: [§3.3b](#33b-an-outcome-that-is-not-known-reconciling-a-bootstrap-command) says how that is read; a refused commit removes the bundles, and so does any other failure of the run, including a bundle that was still being written when the run was judged failed (that write is waited for, its file is removed, and no further file is begun). **A file that a failed write could not remove is reported, by its random name alone**: the write that fails removes its file, and one whose removal fails may leave the secret in it, whole or in part, for a pair that will never be made, so the failed attempts are tracked with the written ones and the operator is told which files to delete, beside the rule that was broken first (the audit of 21 October 2026, A05). The bundles are written inside the transaction, so the commands open their connection with longer deadlines than the API's (120 seconds idle in a transaction and 180 in all, sized to the programs a Windows run waits for: `BOOTSTRAP_DEADLINES`). The command prints counts and the name of each bundle (random, naming no one) and never a secret, a work email or a path; a failure of the database that is not the server's own words (a connection lost while a statement ran) is printed as its kind alone, because the driver's message ends with the statement's bound values, which are the document of the seed.

**The bootstrap credential is a setup secret, not the administrator's password.** It grants **no business API authority**, cannot be presented as a session credential, and can invoke bootstrap setup and nothing else.

**Six constraints, each closing a specific way this becomes a permanent back door:**

| Constraint| The failure it prevents|
|---|---|
| **The seed runs only when the staff table is empty** *(checked once for the pair, before either insert)*| It becomes a standing mechanism for creating admins that bypasses §30.8 entirely|
| **No API operation can do this**| `createStaffIdentity` has no `status` field ([openapi.yaml](../contracts/openapi.yaml)), so nothing reachable over the network can create an `ACTIVE` identity. **The bypass is structurally unavailable to a caller**, not merely forbidden|
| **The credential is a single-use setup secret, consumed when the password is established, and never signs in** (`MSC-DEC-260`, replacing *changed at first sign-in*)| A provisioning secret becomes a shared permanent password|
| **`created_by` and `approved_by` both record a reserved system actor**| The record is indistinguishable from one that passed maker-checker, making §30.8's exclusion unverifiable afterwards|
| **The seed emits `staff.identity.created` and `staff.identity.approved` with `enhanced = true`**| The single most privileged act in the product's life leaves no trace. §38.5 category 6 covers account role administration and does not exempt provisioning|
| **The seed sets no password and no MFA factor**| The seeded credential becoming a permanent admin password, and — the defect this replaces — a seed asserting `mfa_enrolled = true` for a factor that does not exist|

**Each of the two records is written with `origin` `BOOTSTRAP`** (Product decision, 8 October 2026): an immutable `StaffIdentity` column that the API runtime cannot write, that no operation can change and that `createStaffIdentity` always sets to `MAKER_CHECKER`. Everything that treats a bootstrap administrator differently — the resume command, `resetStaffMfa`, `reissueStaffCredentialSetup`, succession — reads this column and never infers the status from the reserved actor, an email address or a count. **Every constraint above applies to each of the two identities and to the pair.** The reserved system actor is recorded as `created_by` and `approved_by` of **both**, and the seed emits `staff.identity.created` and `staff.identity.approved` as enhanced events for **each**.

**The seed writes as `SYSTEM`**, under an explicit task capability — `seed` for the reference data and `bootstrap` for the two administrators and their grants, each bounded as [data-scope-registry.md](../contracts/data-scope-registry.md) §5.2 says — which is how it writes a table whose row-level security is forced (§5.1). It runs as the **provisioning identity**, never as the API runtime and never as the migration login ([data-scope-registry.md](../contracts/data-scope-registry.md) §5.2).

**The fourth constraint is the one that would be dropped.** Writing a real-looking actor into `created_by` is the path of least resistance — it satisfies the non-null constraint and nothing complains. **It also makes every later audit of "was the same-actor rule ever bypassed?" return a false negative**, because the seeded record looks exactly like a compliant one. A reserved actor id makes the bootstrap **visible forever**, which is the point.

### 3.3 What happens immediately afterwards

**Corrected 26 August by `MSC-DEC-260`.** The sequence below previously read: *seed `mfa_enrolled = true`, sign in, then enrol MFA* — which asserts that the factor **both exists before login and is created after it**. That is not a hard ordering constraint; it is an impossible one, and it could only ever have been satisfied by a boolean standing in for a factor that did not exist.

**Each of the two administrators walks steps 1 to 5 separately, with their own secret**; neither depends on the other until step 6.

1. The administrator presents the **single-use bootstrap setup secret** and **establishes their permanent password** (`completeStaffCredentialSetup`). **The password is held to the one credential rule** — 12 to 128 characters, spaces permitted, no composition rule (`MSC-DEC-431`, [SECURITY_DESIGN.md](SECURITY_DESIGN.md) §13.4a) — and **the bootstrap secret is not subject to it**: a provisioning step generates the secret, no person chooses it, and it can only start this one act.
2. **The bootstrap secret is consumed at that moment** and can never be used again. A **`PENDING` `MfaFactor`** is created and a **separate short-lived `MFA_ENROLMENT` continuation grant** is issued.
3. They provision the authenticator and **successfully prove a code** (`completeMfaEnrolment`). The factor becomes `ACTIVE`; a provisioned-but-unproven factor is `PENDING` and is not MFA. **`auth.bootstrap.completed` is written once for this identity**, as an enhanced record.
4. The identity becomes **authentication-ready**.
5. All subsequent access is **ordinary privileged sign-in** — email, password, TOTP.
6. **When both administrators have completed steps 1 to 5**, one of them — signed in through the ordinary privileged sign-in — creates the first real staff profile through §30.8's maker-checker (`createStaffIdentity`, naming a bundle from `listAssignableStaffRoleBundles`), **and approves it themselves, or the other approves it** (`approveStaffIdentity`). **A Platform Admin needs no second person** (decided 25 October 2026, [permissions.md](../contracts/permissions.md) §6): the exception is the tier of the grant exercised, so it is no bootstrap-only rule and gives nothing to anyone below Platform Admin, and the audit event names the one identity as both creator and approver.

**For either administrator, no privileged session exists before step 3 completes.** The setup secret authorises setup and never authenticates, so there is no window in which a bootstrap identity is usable without its factor.

**Who approves the first profile — decided** (`MSC-DEC-440`, closing `PDA-69`). §30.8 gave the checker's act to someone other than the maker, and with one seeded identity nobody could approve anything the bootstrap administrator created. **The seed therefore creates a pair**, and step 6 had one create and the other approve, with no exception to maker-checker. A one-time audited rule letting only the bootstrap identity approve the first profile it creates was considered and **not taken**. **Superseded on this point by the Product Owner's decision of 25 October 2026**: a Platform Admin, bootstrap or not, approves or rejects what they made ([permissions.md](../contracts/permissions.md) §6), so the first administrator to complete steps 1 to 5 can approve the first profile, and the pair stays for the custody and recovery reasons above. A non-production fixture as the whole answer was not taken either, because it would have left production with no approver. **Until at least one administrator is authentication-ready nobody can approve anything**, so `SLICE-000`'s rows 1, 2 and 12 begin only after an administrator has completed steps 1 to 5.

**Why the secret is consumed at step 2 rather than step 3**. `MSC-DEC-260` consumed it after TOTP proof, while the contract required a grant at **both** password establishment and MFA enrolment — so a **single-use** secret would have had to be presented twice, which is the one thing a single-use grant cannot do. **Moving the consumption point weakens nothing**: the gate is the factor, not the secret, and `MSC-DEC-259` already put it there.

### 3.3a If the continuation grant expires — the lockout, and how it is closed

**This section said the opposite until 27 August, and the reassurance was false when it was written.** R1 recorded: *"If the continuation grant expires, provisioning is not stranded. The identity holds a password and a `PENDING` factor; a fresh `MFA_ENROLMENT` grant re-enters at step 3."*

**No operation could issue that fresh grant.** `MFA_ENROLMENT` is produced by exactly two operations:

| Operation| What it needs| Available to the stranded bootstrap admin?|
|---|---|---|
| `completeStaffCredentialSetup`| the **`BOOTSTRAP_SETUP`** secret| **No** — single-use, consumed at step 1|
| `beginMfaReenrolment`| an **`MFA_REENROLMENT`** grant, issued only by `resetStaffMfa`| **Not by the stranded administrator** — `resetStaffMfa` is **Platform Admin only**, and a stranded bootstrap administrator cannot authenticate to use it. **Nor by the other bootstrap administrator for a stranded one**: `resetStaffMfa` does not act on a stranded bootstrap identity, whose work email no approval ever accepted, so the provisioning command (below) is the route|

**The result was a permanently unusable environment, reached by thirty minutes passing** — in the one lifecycle whose entire purpose is to make an empty environment usable. Every mechanical check passed over it, because each operation existed and each grant resolved; what did not exist was a path between them.

**`MSC-DEC-272` closes it with a provisioning-only mechanism.** Not an Ops Portal endpoint — a management or deployment action, on the same controlled channel that delivered the bootstrap secret. **Under `MSC-DEC-440` there are two bootstrap identities and either can be stranded, so the mechanism is unchanged, and its conditions are evaluated for each identity on its own.**

**Its re-enrolment path runs only when all six conditions hold** (the lost-bundle case below is a second path with its own conditions):

1. the target's immutable **`origin` is `BOOTSTRAP`** (one of the two seeded Platform Admins) — read from the column, never inferred from the reserved actor in `created_by`, an email address or a count;
2. that identity is **not offboarded**;
3. a **permanent password is already established**;
4. **no `ACTIVE` `MfaFactor` exists**;
5. **no privileged session can currently be issued**;
6. bootstrap authentication setup remains **incomplete**.

**Nothing in these conditions depends on the other bootstrap administrator** (decided 6 October 2026). The command works for a stranded identity for as long as that identity itself holds no `ACTIVE` factor, whether or not the other administrator is ready, and it refuses by itself once the identity's factor is `ACTIVE`, so it is never a standing way in. **A bootstrap administrator whose `ACTIVE` factor was reset by the other administrator, and whose re-enrolment grant then lapsed, holds no `ACTIVE` factor**, so conditions 4 and 6 hold for it and it is resumed here as well.

**What it does:** revokes or supersedes stale `PENDING` factor state and grants, issues a fresh short-lived **`MFA_REENROLMENT`** authorisation, delivers it through the **controlled provisioning channel**, and writes an **enhanced** audit record under the reserved system actor.

**That transport is the exception, and it is the only one.** `MFA_REENROLMENT` normally reaches the affected privileged principal by **verified work email**; here the stranded identity is a bootstrap identity, which `resetStaffMfa` does not act on, and its work email was seeded and never accepted by an approval, so an ordinary grant would go to an address nobody verified. The same channel that carried the bootstrap secret therefore carries the re-enrolment authorisation. **It does not wait for the other bootstrap administrator and does not stop for them** (decided 6 October 2026); the other administrator uses `resetStaffMfa` only for an identity whose factor is `ACTIVE`. **The purpose is unchanged** — begin MFA re-enrolment — because purpose describes what a credential may authorise, not how it travels.

**`reissueStaffCredentialSetup` refuses a bootstrap identity** (`STATE_CONFLICT`; decided 6 October 2026). Once one administrator is authentication-ready they hold `staff.identity.approve`, and that operation's guard is a null credential — which the other identity has until step 1 — so it would issue a fresh 30-minute `STAFF_CREDENTIAL_SETUP` grant to an address nobody verified, beside the unconsumed `BOOTSTRAP_SETUP` secret. **It does not.** The unconsumed secret stays the only way in for an administrator who has not yet set a password.

**What it does not do — and this is why it is not an MFA bypass:**

- **it grants no session**, business or otherwise;
- **it activates no factor** — the administrator still proves a TOTP code at `completeMfaEnrolment`;
- **it neither resets nor reveals the permanent password**;
- **it does not resurrect `BOOTSTRAP_SETUP`.** A single-use credential that can be revived is not single-use, so a *different* purpose is issued.

The administrator then walks the ordinary path — `beginMfaReenrolment` → provisioning → `MFA_ENROLMENT` → **proven** code → `ACTIVE` factor → normal privileged sign-in.

**A bundle lost, or never delivered, before a password exists** (Product decision, 8 October 2026). The same provisioning-only command may supersede that identity's **unconsumed** `BOOTSTRAP_SETUP` secret with a new one, on the same controlled channel, under conditions 1, 2 and 6 and with **no** permanent password yet established. Nothing is revived: a *consumed* secret is never presented again, and an unconsumed one carries no history. It creates no other privileged identity and resets no MFA enrolment that has completed.

**It stops working as soon as it is no longer needed.** It refuses **for an identity** the moment that identity holds an `ACTIVE` factor (conditions 4 and 6), and in any case once **that** bootstrap identity is offboarded, which requires **two** proven non-bootstrap Platform Admins (§3.4). **A recovery mechanism that outlives its emergency is an attack surface.**

**As built (S0.30).** The resume is `pnpm --filter @melarc/api run bootstrap:resume -- --custodian <work@email>`, run as the provisioning login like the seed, with the bundle written the same way. **After a commit whose outcome is unknown the bundle stays, and the operator is told to delete nothing and to run nothing until the outcome is established**: if the change committed the bundle holds the only copy of the new secret, and a second run replaces that secret (on the lost-bundle path it supersedes it again, leaving the bundle with one that no longer works; on the re-enrolment path it is refused while the first grant lives). **A missing audit event does not show that the change did not commit**, so the outcome is established by the reconciliation of [§3.3b](#33b-an-outcome-that-is-not-known-reconciling-a-bootstrap-command), on the primary database, in a fresh transaction that first waits for the original one to end. `melarc.bootstrap_identity_state` reads the identity by its canonical work email and holds it under its row lock (the lock the credential operations take); `melarc.resume_bootstrap_identity` judges conditions 1 to 6 on that identity (the origin from the column; not offboarded; no `ACTIVE` factor, which is conditions 4 and 6; no live session), names the one that refuses, and takes the path the state shows: with a password established, a fresh `MFA_REENROLMENT` (its lifetime is the setting `recovery_link_ttl_minutes`, read and never defaulted) after every lapsed grant of the identity is ended and every stale `PENDING` factor is revoked; with none, the unconsumed `BOOTSTRAP_SETUP` superseded by a new one. **A live grant of the identity makes it not stranded yet**: the command refuses until the grant has lapsed, rather than end a person's live enrolment. The audit events are the catalogue's own for what it does, by `SYSTEM`: `auth.setup_grant.issued` (its row already lists the controlled provisioning channel) and `auth.setup_grant.superseded`, and the enhanced `auth.mfa.revoked` for a stale factor. **Beside them it writes one enhanced summary, `auth.bootstrap.resumed`, per committed resume, on both paths** (the owner's adoption of 21 October 2026, A07, [AC-SLICE-000-93](../features/identity/staff-authentication.md); migration [`0022`](../apps/api/migrations/0022_bootstrap_resumed_event.sql)): by `SYSTEM` with a null actor, the reserved bootstrap actor as the named fact `reserved_system_actor_id`, the identity, the path, the grant issued, the grants it ended (superseded or expired) and the factors it revoked, with a bounded, secret-free before and after of their states ([audit.md](../contracts/audit.md) §5.4, *Facts of `auth.bootstrap.resumed`*). The resume function **derives those facts from what it wrote**, under the identity's lock, and refuses, writing nothing, a document whose summary says anything else (a grant that lapsed after the state was read, a factor that appeared); the event is written in the same statement and transaction as the change, so a summary that cannot be written takes the change back with it, and a refused resume writes none.

**The ordering now runs one way.** Nothing is asserted before the thing it asserts exists, and `mfa_enrolled` is derived from the factor rather than written by the seed.

### 3.3b An outcome that is not known: reconciling a bootstrap command

*Added after the review of 21 October 2026 (C01) and hardened by the owner's instruction of the same day. It is a procedure and not a command: no administrative tool reads or changes anything here, and `bootstrap-reconciliation.db.test.ts` executes the statements below, verbatim, against a real PostgreSQL.*

**When it applies.** A `bootstrap:seed` or `bootstrap:resume` that fails with a commit whose outcome is **unknown** (the connection was lost, or the budget ran out, while COMMIT was in flight) keeps its bundles and prints the run's **correlation id**. The change may have committed, or not, or may still be committing. **Nothing is deleted and nothing is run again until the outcome is established.** Reading no audit event is not establishing it: one read can come before the original transaction commits, can be of a replica or an old snapshot, can be taken at an isolation level that does not see a later commit, or can be made by a role whose row-level security hides the rows, and a bundle deleted on that inference is the only copy of a committed secret destroyed.

**How the outcome is established.** An authorised administrator runs one short transaction, and **every condition below is checked in it: a condition that fails, or that cannot be checked, makes the outcome *unresolved*, never *not committed*.**

1. **At `READ COMMITTED`, stated by the transaction itself** (`BEGIN ISOLATION LEVEL READ COMMITTED`), whatever the session's default is. The default of a session can be `REPEATABLE READ`, which takes its snapshot before the wait for the lock and then reads, after the original has committed, as if it had not.
2. **On the primary database of the environment**, found by the check (`pg_is_in_recovery()` is false and `current_database()` is the environment's), on the endpoint the migration login uses and not a replica, a pooler's read-only pool or a restored copy.
3. **With verified visibility of every row**: the role bypasses row-level security (a superuser or a role with `BYPASSRLS`; the check reads it). **Owning the tables is not enough: every table the procedure reads is `FORCE ROW LEVEL SECURITY`, so the owner is filtered by the policies like anyone else, and a filtered read returns no row exactly as a read of a table with no event does.** `SET LOCAL row_security = off` is the **fail-closed** guard and not a way round it: a role that the policies would filter gets an error and not a short answer (a role that bypasses them is unaffected).
4. **Having taken the lock the original holds until it ends**, with a bounded wait: the seed's `SHARE ROW EXCLUSIVE` lock on `staff_identity` (taken by `melarc.bootstrap_status`), or the resume's row lock on the identity (taken by `melarc.bootstrap_identity_state`). The transaction therefore **waits for the original to commit, roll back or lose its session**; no fixed sleep stands in for that. **A wait that ends in `55P03` (lock not available) is *unresolved*, and says nothing of which transaction holds the lock**: it may be the original, which has until `BOOTSTRAP_DEADLINES` (120 seconds idle, 180 in all) to end, or any other writer. Repeat after that; nothing is lost.
5. **For the resume, having locked the identity it meant to**: the lock statement takes the row lock of **every bootstrap identity** (the pair: whichever of them the original resumed is waited for, so that a mistyped address that names the other administrator cannot make an empty read look like a rollback), and **the row of the address given to the command must be among the rows it returns, with `origin` `BOOTSTRAP`**. No such row (the address is mistyped, the identity is absent, or the role cannot see it) means the identity the original held was not shown to be locked: *unresolved*. The audit events of the run must then be about that identity (`<canonical email>`, compared by the reader of the result): a row that names another is *unresolved*.
6. **Only then does it read**, in the same transaction, what is committed.

```sql
BEGIN ISOLATION LEVEL READ COMMITTED;
SET LOCAL lock_timeout = '<wait>';
SET LOCAL row_security = off;
-- the check: isolation is 'read committed', in_recovery is false, database is the environment's, sees_every_row is true; anything else is unresolved
SELECT pg_catalog.current_setting('transaction_isolation') AS isolation, pg_catalog.pg_is_in_recovery() AS in_recovery,
       pg_catalog.current_database() AS database,
       (SELECT r.rolsuper OR r.rolbypassrls FROM pg_catalog.pg_roles r WHERE r.rolname = current_user) AS sees_every_row;
-- the seed: the lock the original holds until it ends
LOCK TABLE staff_identity IN SHARE ROW EXCLUSIVE MODE;
-- the resume: the row lock the original holds until it ends, on every bootstrap identity; the row of '<canonical email>' must be among them, or unresolved
SELECT id, origin, work_email_canonical FROM staff_identity WHERE origin = 'BOOTSTRAP' ORDER BY id FOR NO KEY UPDATE;
-- then, for either, the grants this run issued and where they stand now
SELECT s.work_email_canonical, g.id AS grant_id, g.purpose, g.state, g.expires_at,
       g.expires_at IS NOT NULL AND g.expires_at <= clock_timestamp() AS lapsed
  FROM audit_event e
  LEFT JOIN setup_grant g ON g.id = e.object_id
  LEFT JOIN staff_identity s ON s.id = g.principal_id
 WHERE e.correlation_id = '<correlation id>' AND e.event_code = 'auth.setup_grant.issued'
 ORDER BY s.work_email_canonical, g.id;
COMMIT;
```

(Run the seed's lock or the resume's, not both. The transaction only reads, but the lock blocks writers of `staff_identity` or of one identity while it is held, so it is kept as short as these statements.) **After any SQL error the transaction is aborted: it is rolled back explicitly (`ROLLBACK`) before anything else is run on the connection**, because every later statement of an aborted transaction fails, and a connection that is reused without the rollback reports the failure of the first statement as if it were the result of the last. A new attempt is a new transaction.

| What the read finds, once the conditions above held| Outcome| What the bundle is|
|---|---|---|
| No row| **Not committed.** The original transaction ended and nothing of it is there| This attempt's bundle is an **uncommitted orphan**: delete it, then run the command again (the seed's second run sweeps its own database's orphans itself, from the empty table it finds)|
| Every row's grant is `PENDING` and not `lapsed`| **Committed and current**| The secret to hand over, to the custodian the row names (the bundle names them inside)|
| A row whose grant is `CONSUMED`, `SUPERSEDED` or `EXPIRED`, or `lapsed`| **Committed and since changed**| **Not to be handed over, and not an orphan.** The change committed; its secret was used, replaced or has lapsed, whatever the issuance event says. A `CONSUMED` grant means a secret was used: find out by whom before anything else. The bundle is **obsolete**: it is retired, by deleting it with a recorded deletion, only after the state is confirmed as the row says; if the identity is still stranded, run the resume again once nothing else is unresolved|
| A condition above failed or could not be checked; the lock was not obtained; a row names a grant that is not there or another identity; or anything else is in doubt| **Unresolved**| Keep every bundle, change nothing and run nothing; repeat the reconciliation, or take it to the owner|

**What lets a bundle go, and how it is named.** Only the first row makes a bundle an **orphan** (written for a change that did not commit), and it is the only row that lets a bundle go *as an orphan*: the lock proves the original transaction ended, and the empty read is then a fact. A bundle of a change that **did** commit and was since replaced or used is **obsolete**, which is a different thing: it is retired by a recorded deletion after the state is confirmed, it is never classified, reported or swept as an uncommitted orphan, and the seed's sweep of orphans never reaches one (it runs only from an empty staff table). The seed's own second run reaches the safe answers by the same lock (it refuses a staff table that holds the pair, and sweeps only from an empty one), which is why it may be used as the reconciliation for the seed; for the resume it may not, because a second resume that finds the first one committed supersedes it.

### 3.4 Succession — two proven administrators, not one

**The bootstrap identities are never deleted, and each is retired — offboarded — only after two non-bootstrap Platform Admin successors each** (`MSC-DEC-260`, superseding the trigger in `MSC-DEC-255` item 2; the pair, `MSC-DEC-440`):

- were created through the normal §30.8 maker-checker process, and approved;
- have a **permanent credential established**;
- have an **`ACTIVE` MFA factor**;
- are **authentication-ready**;
- have **completed at least one successful normal privileged MFA sign-in**.

**The condition is the two successors, and it is not multiplied by the number of bootstrap identities retired against them**: retiring both leaves those two, the minimum that lets either reset the other's factor *(derived from the rule above; offboarding itself is `SLICE-009`'s)*.

**Retiring against a single successor produces administrative lockout**, and the arithmetic is short: bootstrap plus one successor, retire the bootstrap, and **one** Platform Admin remains — and with the pair, retire both against one successor and the same one remains. When that person loses their factor, MFA reset requires **another Platform Admin** — and there is not one.

**The proven-sign-in condition is the load-bearing half.** *Approved* is not enough: an account can be approved with no password established, an incomplete enrolment, or a mistyped work email, and offboarding the bootstrap against it converts a formally valid succession into a real lockout. The criterion is **approved + credential-ready + MFA-ready + authentication proven.**

Offboarded, **never deleted** (§30.10), and **`auth.bootstrap.succeeded` is written once for each bootstrap identity retired**. The bootstrap identities' creation and approval events survive with their reserved system actor — **the record of how the product got its first users outlives them.**

**A hard credential expiry was considered at approval and rejected**. Stopping the seeded credential after a fixed window regardless of whether the administrators have completed setup **strands provisioning**: miss the window and nobody can sign in at all, and the environment must be reseeded. Retirement is a policy about when to offboard, not a timer that can lock everyone out.

## 5. Schema migrations

**Forward-only, reviewed, and reversible in effect rather than in form.** §45.6 requires *"migrations, indexes, constraints, data backfills, and rollback/recovery"* to be reviewed before a slice is done.

**Three rules follow from §42.6's historical-integrity requirements rather than from convention:**

- **A migration never rewrites a historical snapshot.** §42.6 requires *"price/settings/reason/provider snapshots required to interpret history"* to be preserved. A backfill that "corrects" a stored price destroys the record of what was charged. Corrections post as **linked adjustments** (§35.6.7).
- **A migration never renames a machine code.** Machine terms are stable; [errors-and-enums.md](../contracts/errors-and-enums.md) §2 makes an error-code rename a **breaking contract change**. A withdrawn code is absent from the `Error` enum, which is what makes "never reused" structural.
- **A migration never deletes history.** §30.10 and §35.1.5: offboarded staff, terminated vendors and failed attempts all stay queryable. Retention deletion is a separate, **enhanced-audited** act (§38.5 category 8), not a migration.

### 5.1 Roles, ownership and RLS at migration time

`MSC-DEC-276`, `MSC-DEC-289`. Migrations run as **`melarc_migration_elevated`** — a **deployment-only** identity obtained through the deployment workload identity, infrastructure-audited, whose credentials are usable **only for the deployment window** and are withdrawn, expired or made unusable when the migration finishes. Tables are owned by **`melarc_owner`** (`NOLOGIN`). **No runtime identity owns a table and none may run DDL.**

**R0 called this identity unprivileged while requiring it to transfer table ownership.** Both cannot be true, and describing an ownership-capable identity as unprivileged does not constrain it — **it only stops anyone constraining it deliberately.** R1 treats it as the privileged identity it is and bounds it by **isolation, duration, workload identity, audit and runtime non-reuse.**

**Every migration that creates a protected table enables and forces row-level security in the same migration**, and grants the runtime roles the minimum DML they need:

```sql
ALTER TABLE <t> OWNER TO melarc_owner;
ALTER TABLE <t> ENABLE ROW LEVEL SECURITY;
ALTER TABLE <t> FORCE  ROW LEVEL SECURITY;   -- without this the OWNER is exempt from every policy
GRANT SELECT, INSERT, UPDATE ON <t> TO melarc_api_runtime;   -- the DML its code uses now (a seed-only table is SELECT-only); never ALL, never DELETE by default
-- worker/scheduler/relay grants are per task class, never a blanket business read
```

**`FORCE` is the line that gets left out**, and leaving it out is invisible: the table reports RLS enabled, the policies exist and are correct, and any connection made as the owner is subject to none of them. The role separation above is the first control and `FORCE` is the second, so that losing one does not lose both.

**A migration that adds a persistent table fails review unless [data-scope-registry.md](../contracts/data-scope-registry.md) classifies it**. This is the enforcement point for that rule, because a table's scope class is decided when the table is created or it is decided never — and an unclassified table has no policy, which means it reads and writes correctly for every actor right up until the day a second hub or a second vendor exists.

**Deletes are explicit** (Product decision, 6 October 2026). The migration lint refuses `ON DELETE CASCADE`, `TRUNCATE` and a `DELETE` grant **unless a comment on that statement records the reason**, written `-- allow-delete: <reason>`. A grant is never `ALL` and never `DELETE` by default, as the block above says; this is the mechanical check that keeps it so ([engineering-standards.md](../standards/engineering-standards.md) §7).

**A migration that changes a bundle or the compiled Vendor or Rider policy carries its own session handling** (Product decision, 8 October 2026, corrected by the R2 review). It runs as the **migration identity** (the provisioning identity can take the seed's locks and cannot change a bundle after the initialization), never as the API runtime, and **takes the exclusive policy lock first** ([SECURITY_DESIGN.md](SECURITY_DESIGN.md) §13.10a), so it cannot interleave with a sign-in or a mutation that holds the shared one. **Every** change to a bundle's authorization content calls the one primitive that raises `RoleBundle.revision` (S0.27, migration `0017`): `SELECT melarc.change_role_bundle(bundle_id, name, grants, correlation_id)` for a bundle and `SELECT melarc.change_fixed_policy(audience, reduction, correlation_id)` for the compiled policy of the Vendor or the Rider, each of which takes its exclusive lock first, decides the kind of change from the difference, and for a reduction ends the sessions below the floor and writes their events in the same transaction (a step that changes several objects calls `SELECT melarc.lock_policy_keys(bundle_ids, audiences)` first, which takes every exclusive lock in the canonical order; a change that cannot be shown to be a widening is a reduction; the correlation id is the fixed label of the release step, a check of shape and never text a user supplied). **The migration lint refuses a plain `INSERT`, `UPDATE`, `DELETE` or `TRUNCATE` of the three policy tables** unless the statement carries `-- allow-policy-dml: <reason>` (a backfill of a new column that is not authorization content, for instance): under forced row-level security a plain statement by the migration login changes no row and raises no error, so a migration that tried would report success and do nothing; a **reduction** also raises `reduction_floor` and ends the sessions recorded below it in the same transaction, while an addition ends none and every existing snapshot is retained. A change to the compiled policy raises `FixedPermissionPolicy.revision`; a reduction of it also raises `minimum_revision` and ends the active sessions below it in the same transaction, and the release carries the new compiled revision, so that an instance still running the old code can neither issue old authority nor serve any request of that type once below the floor (and older code never serves a session of a newer revision) ([SECURITY_DESIGN.md](SECURITY_DESIGN.md) §13.10, [DEPLOYMENT_AND_ENVIRONMENTS.md](DEPLOYMENT_AND_ENVIRONMENTS.md) §7). The seed inserts the first `FixedPermissionPolicy` rows into the empty table, under the same lock, **at the revision of the build that seeds and floor 1** (`SLICE-001`, S1.8, migration `0046`; before it the revision was 1 whatever the build declared). The revision is *the latest released* one, and the floor of a reduction is computed from the stored revision, so a new database whose revision trailed its build would have its first reduction end no session: a database seeded earlier reaches the build's revision by the release steps that follow its seed (each is a migration that calls `melarc.change_fixed_policy`), and a new database, migrated before it is seeded, can meet no release step, so the seed starts it where the steps would have left it. `BUILD_FIXED_POLICY` (`platform/auth/sessions/build-fixed-policy.ts`) is the one place the number is declared; the seed and the build both read it. A migration that only terminates the sessions it finds, and leaves old code free to issue afterwards, is not a conforming reduction. **The primitive and its concurrency are acceptance obligations of the task that builds them** (§13.10a): S0.27 ran them on the real tables under the runtime and migration logins (`policy-change.db.test.ts`, `policy-change-races.db.test.ts`); the randomised interleavings, the starvation run and the two-build proof are S0.63 and S0.64's and are not claimed.

**Seeds and backfills write as `SYSTEM`** (Product decision, 6 October 2026). A seed or a backfill writes a forced-RLS table as the `SYSTEM` principal under an **explicit seed task capability** ([SECURITY_DESIGN.md](SECURITY_DESIGN.md) §14.4, §14.17b), never as the migration login and never by bypassing row-level security. **Each table's policy has a `SYSTEM` branch for that capability**, and **the policies keep deciding on the request context alone**: no accessor is tied to the migration login, and the migration role holds no `BYPASSRLS`. The seed helper (`runSeed`) and the `seed` branches of the seven reference tables exist (S0.9, `0004_seed_policies.sql`: a read policy and an insert policy for each table, each admitting the `SYSTEM` principal under the `seed` capability and no one else); a table a later seed fills gets its branch in the migration that creates it.

**The initialization is the database's rule, not the helper's** (correction F02 of Stage 1, `0005_seed_initialization.sql`). The provisioning login holds **no privilege** on the seven reference tables: it cannot read, insert into, change or remove a row of one, before the seed or after it, with the seed label asserted or without, so asserting the label reaches nothing. It writes them only through two `SECURITY DEFINER` functions owned by `melarc_owner`, which only it may execute (revoked from `PUBLIC`; not the API runtime, not a worker) and which the posture check lists by name (`APPROVED_DEFINER_EXECUTE`): `melarc.initialize_reference_data(document)` fills the seven tables **once, in one statement**, and `melarc.add_reason_fixtures(document)` adds the test-only reason fixtures (codes that start with `FIXTURE_`, and nothing else). **`FIXTURE_` is a naming restriction and not an environment restriction:** the database does not know its environment, so the production refusal of the fixtures stays the command's, and the function remains callable with the provisioning credentials wherever they are held; who holds them in production is settled before release. Each takes its rows as one JSON document and names every table and column itself: no object name, column or statement comes from the caller, the `search_path` is fixed and every table is qualified. The initialization locks the seven tables in one order (`SHARE ROW EXCLUSIVE`, which waits for any other writer and not for a reader), counts every table, and refuses with SQLSTATE `55000`, naming the first table that holds a row, unless all seven are empty: a second run changes nothing, a run that fails at any table leaves nothing (it is one statement of the caller's transaction) and can be run again, and two runs at once cannot both fill the tables (the second waits, then refuses). It sets the `SYSTEM` principal and the `seed` capability itself for its own statements, so the policies of 0004 stay the second line and nothing the caller sets is read as proof, and it puts back what the caller had set. A bundle it writes starts at revision 1 and floor 1, and a fixed policy at the revision the document names for it (1 where it names none) and floor 1, whatever else the document says. **The trust boundary:** the authorized provisioner chooses the initial content (the document), and the database enforces the rules of an initialization (once, into empty tables, atomically, serialized, at revision 1); it does not verify that the content is the approved catalogue, which the seed data's tests hold to its documents and the owner reviews. **A change to a bundle or to the fixed policy after the initialization is not a seed**: it is the controlled primitive that raises the revision under the exclusive policy lock (SLICE-009, S0.27), which decides whether that is a SQL function or application code, and moves this seed onto it. Until then nothing but a migration changes them.

**Grants arrive with the first operation that writes the table** (Product decision, 8 October 2026). A migration grants `melarc_api_runtime` the DML its code uses *now*: a table that only a seed writes — the permission catalogue, role bundles, reasons, settings — is `SELECT`-only for the API runtime until an operation writes it, so a runtime that sets a seed label reaches nothing ([SECURITY_DESIGN.md](SECURITY_DESIGN.md) §14.1). The seed and the bootstrap run as the **provisioning identity**, a login outside the API's and every worker's configuration ([SECURITY_DESIGN.md](SECURITY_DESIGN.md) §14.17); on the seven reference tables it holds no privilege at all and reaches them through the two seed functions above.

**Roles, functions and the posture the migration lint cannot see.** The lint reads each migration's text; it flags `CREATE ROLE`, `ALTER ROLE` and `GRANT <role> TO <role>` unless a comment on the statement records the reason (`-- allow-role: <reason>`, as `allow-delete` does), and it refuses a `SECURITY DEFINER` function that does not fix its `search_path`, is not revoked from `PUBLIC` and granted `EXECUTE` to a named role in the same migration, or uses `EXECUTE` (an argument that could become SQL); a plain function is held by the catalogue check (owner, no `PUBLIC` `EXECUTE`) and not flagged, because an applied migration cannot be edited to carry a comment. What actually holds is the catalogue check, run with the actual runtime logins ([SECURITY_DESIGN.md](SECURITY_DESIGN.md) §14.6), and a new technical table follows §5.3.

**`melarc_api_runtime` never receives `DELETE` on an audit table** ([data-scope-registry.md](../contracts/data-scope-registry.md) §4.5), which is where §42.6's append-only requirement stops being a convention.

### 5.2 Derived scope columns

`MSC-DEC-278`. A migration adding a derived `responsible_hub_id` to an operational child must, in the same migration:

1. **backfill from the parent**, never from a default or a constant;
2. add the **composite foreign key** to the parent's `(id, responsible_hub_id)`, so a child in one hub cannot reference a parent in another;
3. add the **immutability trigger**;
4. set the column `NOT NULL` only **after** the backfill verifies complete.

**A backfill that defaults is worse than no backfill.** A hub column populated with the launch hub's identifier looks complete, satisfies the constraint, and silently mis-scopes every historical row — and §42.6 forbids a migration that rewrites history, which is exactly what a wrong scope value does to the audit trail that reads it.

### 5.3 A persistent technical table is declared, not excused — Gate B R1

`MSC-DEC-294`. A migration that adds a **persistent technical table** — one required by architecture and defined in no domain contract — must, **in the same controlled change**, add:

1. its row in the canonical inventory at [data-scope-registry.md](../contracts/data-scope-registry.md) **§6**, between the parse markers; and
2. its full per-principal row in Registry **§4**.

**Until both exist, the consistency test must reject the mismatch.** That is the intended behaviour, not an obstacle to route around.

**Contract drift is checked against actual implementation output.** Generate the API description from the NestJS application and compare it with the canonical OpenAPI contract under [engineering-standards.md](../standards/engineering-standards.md) §4. Do not copy the canonical file into the generated-output path.

### 5.4 Expand and contract

`MSC-DEC-374`. The six phases and the rollback boundary live at [DEPLOYMENT_AND_ENVIRONMENTS.md](DEPLOYMENT_AND_ENVIRONMENTS.md) §7.1, because that is the document whose reader runs the release. **What belongs here is what binds the person writing the migration.**

**A destructive step may not run while release N−1 is still supported.** Dropping a column, renaming one, or narrowing a constraint is a **contract-phase** act, and the contract phase begins only once every N−1 instance is gone and the rollback window is closed. **A migration that deletes first is a migration that decides, unilaterally, that rollback is no longer available** — and it makes that decision at the moment rollback is most likely to be wanted.

**Every backfill is:**

| Property| Why it is not optional|
|---|---|
| **Idempotent**| It will be re-run. A backfill that double-applies is a data corruption with a deployment log for an alibi|
| **Restartable**| It will be interrupted. Resuming from the start on a large table means it never finishes|
| **Bounded and batched**| An unbatched update takes a lock the length of the table and the width of the outage|
| **Observable**| A backfill nobody can watch is one nobody can tell has stalled|
| **Safe under live traffic**| It runs against a production the product is still serving|
| **Historically truthful**| **No default may fabricate a historical business fact**|

**The last property is §5.2's rule generalised, and it is the one that looks harmless.** A `NOT NULL` column backfilled with a plausible constant satisfies the constraint, passes every check that counts rows, and **records as fact something nobody observed** — which §42.6 forbids for exactly the reason `MSC-DEC-278` gave about a hub column: a wrong scope value silently mis-scopes every historical row and the audit trail that reads it.

**And no huge synchronous transaction may block startup.** A backfill wired into application boot converts a long migration into a failed deployment, and [DEPLOYMENT_AND_ENVIRONMENTS.md](DEPLOYMENT_AND_ENVIRONMENTS.md) §12.3 already makes a missing security value prevent startup — two reasons to refuse to start is one too many to diagnose at 06:00.

### 5.5 An upgrade check: data the migration cannot see

A migration that changes what the database enforces does not repair data written under the old rule, and it cannot always look for it. The migration login reads a forced-row-level-security table like any other login (§5.1), so a check written inside the migration finds no row and **passes because it could not see**, which is the mistake the rule it enforces exists to prevent. Where an existing database may hold data that the new rule would not have allowed, the release therefore has an **upgrade check**, and a persistent database is not migrated until the check has been run, its result recorded and anything it found reconciled.

- **A command, not a migration step.** It runs as the cluster administrator against a database on this machine, **changes nothing unless it is told to**, and has one flag that reconciles in a single transaction that locks the tables against writers, checks its own result before it commits and touches only what the rule makes eligible. The application and the worker are stopped while it runs, and the build is current (the command runs from `dist`). A deployed database is checked by its administrator with the same statements, which are the command's and not copied here.
- **Tested from the old behavior, in the order the procedure gives.** A clean install proves nothing about this path. A test builds the database through the previous migration with the real runner, leaves it what the old code left, and takes it through the procedure in its own order: **the check** (it finds what was left and changes nothing by looking), **the reconciliation with the new migration not yet applied**, so that it runs under the guard of the old behavior that the migration replaces (the test reads the catalogue to show which guard was in force), then **the migration**, which must apply on the reconciled data and change no row, and **the check again**. A test that reconciled after the migration would show that the reconciliation works under the new guard and say nothing about the guard it is documented to run under (the reviewer’s finding of 2 November 2026), so the other order, a database migrated before it was checked, is a second test: the recovery path, never the proof of the first. The commands themselves, built, are run in the documented order with their exit codes (2 when the database does not agree with its claims, 0 when it does) and no credential printed.
- **The result is recorded** (the database, the day, the counts and any request reconciled) in the plan of the slice that owns the migration, before the migration is applied to that database.

**The first is migration `0064` (S1.21; OB-S1-35).** `pnpm --filter @melarc/api run db:commitment-marks [database]` checks that the mark of a rider commitment on each confirmed pickup request agrees with the request's current claim (a stop that has not released its claim holds it on a manifest that has a rider), and says how many requests are stale (marked, not held), missing (held, not marked), and how many that are not confirmed carry the mark. With `--reconcile` it lowers the stale and raises the missing, **only for a confirmed request: a cancelled request keeps the mark and the charge decision it was cancelled on, and no snapshot is touched.** Exit code 0 means the database agrees with its claims, 2 that it does not, 1 that the command failed. It refuses any database but `melarc_dev` and the test databases, any server but this machine's and any environment but a local one. The statements, and the reason the check cannot be the migration's, are in [`commitment-marks.ts`](../apps/api/src/tools/database/commitment-marks.ts) and in the comment of [migration 0064](../apps/api/migrations/0064_current_rider_commitment.sql). **The order is: stop the application and the worker, build (the command runs from `dist`), check, record the result, reconcile if the check found anything, migrate, check again.** The upgrade test walks that order, as functions and as the built commands, and is `apps/api/test/database/commitment-upgrade.db.test.ts`.

**Migration `0065` (S1.22) adds checks and repairs nothing.** Its constraint triggers (a `CANCELLED` request and a stop that holds it and is still to be worked never coexist) check what a transaction writes, not what is already there, and a database built by these migrations holds no row they would refuse, because the cancellation of a request has skipped the stop in its own transaction since `0059`. A row made outside the migrations would be found by the first update of either row, which would be refused at its end. **The Product Owner decided on 2 November 2026 that it is looked at first, with enough visibility to see every row, and that the migration stops if anything is found.** The command is `pnpm --filter @melarc/api run db:open-stops [database]` (it runs from `dist`, so after a build). It connects as the cluster administrator, because the migration login and the runtime login cannot see these rows through row-level security and a check made there would pass because it could not see; it runs in a read-only transaction and writes nothing, and it has no flag that would. It lists each cancelled request that still holds a stop to be worked (the request, the stop and its state, the run), and its exit code is 0 when there is none, 2 when there is at least one (**do not apply `0065` to that database**; the report says so), and 1 when the command failed, which is not a clear result. It refuses any database but `melarc_dev` and the test databases, any server but this machine's, any environment but a local one and any argument that is not a database name. Neither the command nor the migration repairs a row: what to do with a violation is the Product Owner's to decide. A deployed database is checked by its administrator with the statement of [`open-stop-check.ts`](../apps/api/src/tools/database/open-stop-check.ts), and the result is recorded before the migration. The upgrade test walks the order (a history built before `0065` with a violation, the check finding it, the clear case) and is `apps/api/test/database/open-stop-upgrade.db.test.ts`.

**Migrations `0066` and `0067` (S1.23, S1.24) need no upgrade check and say why.** `0066` adds a column with a default (`notification.parameters`, an empty object, which the check it carries holds) and widens what the guards of the manifest and the stop admit for two keys; no row can be inconsistent with it. `0067` adds a table, so no row exists before it, and replaces the manifest's guard with one that also refuses the completion of a run while a handover of it is pending: a run completed before cannot have a handover that is pending, since none could be opened. Neither migration repairs anything. (The rule of `0065`, a cancelled request and a stop still to be worked never coexisting, is the one that checks what a transaction writes and not what is there, and its read-only query above is still the way to look first.)

## 6. Migrating from existing code and data

§46.3 lists *"migration strategy from existing code and data"* as an internal dependency, and §46.4's risk table names the hazard directly: *"existing implementation may not match the amended specification"*, risking *"false completion claims, migration defects, and hidden policy violations."*

**The mitigation §46.4 prescribes is a per-slice code audit before the slice begins** — not a single migration project. This document adopts it unchanged.

**Version 1 is greenfield, and that is why the catalogue never arrived**. **There is no legacy Melarc production application or database whose live transactional records must be migrated.** `OQ-097` asked for an inventory before a plan could be written against it, and **the answer is that there is no such database** — which closes the question rather than deferring it again.

**So there is no legacy database migration project**, and this document requires none.

**The per-slice code audit is unaffected**, because it was never about data. §46.4's mitigation applies to existing **code**, and a running operation described in spreadsheets and habits is not a database.

**Still required, and none of it is a migration:** bootstrap (§3) · controlled seeds · the permission catalogue · role bundles · hub and configuration setup · approved reference and reason data · schema migrations (§5) · verified launch configuration.

**If an opening spreadsheet or manual import is later required, it is a separate controlled import artifact.** It **may not** fabricate historical states · manufacture custody or payment history · bypass normal validation · or silently convert uncertain manual data into authoritative transactional fact. **An import that writes a custody event nobody witnessed is not data entry, it is invention** — and §42.6's historical-integrity rules bind it exactly as they bind a migration, which is also §5.4's point about a backfilled default.

**One rule binds regardless of what the audit finds**: where a documented rule would make a working operational practice harder, **that is a finding for the Product Owner, not a rule to enforce quietly during a migration.**
