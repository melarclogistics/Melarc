# Integrated harness (`e2e`)

A real browser, the built Ops Portal, the API process and a disposable PostgreSQL database, started once per run. Read [README.md](README.md) first. `pnpm run test:e2e` builds the API and Ops through Turbo and needs the local database and Chromium ([DEVELOPMENT.md](../DEVELOPMENT.md)); the harness itself only runs built applications and never builds them. What B0.7 left undone is in the runbook ([B0.7](../delivery/planning/BOOTSTRAP_B0_RUNBOOK.md#carried-forward-from-b07)).

## Rules

- Add specs in `tests/`; do not rebuild the harness. Data comes from the deterministic fixtures, and the browser clock from `freezeBrowserClock`.
- The browser may reach the Ops origin and nothing else, and the API runs under an outbound guard. A slice that adds a provider (SMS, email, payment) adds its own sandbox or capture adapter and asserts on it. Never contact a real provider.
- Never create a context with `browser.newContext()`: it bypasses the browser boundary (`harness/https-test.ts` makes its own, behind the same guard, because Firefox's has to be persistent). `pnpm run test:e2e` runs Chromium over plain HTTP; the trusted HTTPS origin and Firefox and WebKit are `pnpm run test:e2e:https` ([README.md](README.md)): it makes a test CA, so it runs only in CI or on a machine cleared for key material, never on the shared workstation and never on Windows or macOS, and an engine or a run that cannot is reported blocked (skipped with the reason, failed in CI), never green. Never use `ignoreHTTPSErrors` as trust evidence, and never trust a CA machine-wide (the one exception is WebKit's proofs on a GitHub-hosted runner, a machine made for one job, which have no other trust: `harness/system-trust.ts`, the owner's decision of 12 October 2026). A spec that puts a secret on a page is named `<name>.secret.test.ts` and imports `test` from `harness/secret-test.ts`: it runs in the `chromium-secret` project with the recorders off, and `harness/evidence-policy.ts` and `harness/secret-evidence.ts` say what is enforced and what is not.
- A run makes its database with `e2e-database create --seed` (migrated, with the reference data the real seed writes: an API over an unseeded database is not ready, `reference_data_missing`) and removes only the database it made. Never add cross-run cleanup or delete a database on a guess; leftovers of a killed run are listed with `pnpm --filter @melarc/api run db:orphans`. A run ended from outside (a wrapping `timeout`) leaves its database and its custody folders with no record: stop a gate with `pnpm run gate:stop`, which ends the whole stage and lists what it left, never with a timeout.
- The journeys are real: the shared stack is the stack of the journeys (S0.45): the two bootstrap administrators from the real `bootstrap:seed`, the delivery worker as its own process and the capture sink it writes into, all in folders outside the checkout that the stack removes. A journey goes through the screens and reads only what a person is given: a one-time secret from a custody bundle (`harness/custody.ts`), a link from a captured message (`harness/messages.ts`), a code from `harness/totp.ts` for the key the page showed. Time passes by `arrange` and what no operation shows is read by `observe` (`harness/database.ts`, the closed lists of `apps/api/src/tools/e2e/arrangements.ts`); there is no other way to change a row, and a journey that needs one is wrong. The staff journeys are `harness/journeys/staff-journeys.ts`, registered by `staff-journeys.secret.test.ts` (plain HTTP, a diagnostic) and `https-staff-journeys.secret.test.ts` (the evidence): add a journey to the list, never to one spec. **Each journey is counted** (`harness/journeys/request-count.ts`, run 7, Stage 3.5): the harness prints the Ops browser's API requests of each session by operation when the journey ends, and fails it, with those counts, when a session passes 100 in a rolling minute (the API refuses a session past 120 with a 429, and CI runs the journeys in three engines on every push to main, where one extra read turns the run red); a journey that needs more starts a session of its own (`clearBrowser`, `signInAs`). The recovery journeys of rows 10a and 11 (S0.52, `harness/journeys/recovery-journeys.ts`) are in the same list: their vendor half is `harness/journeys/vendor-browser.ts`, a client of the run's API that sends the Vendor origin, because the Vendor PWA does not exist, over the demonstration vendor the real `db:seed --vendor-fixture` writes (`addVendorFixture`).
- The Rider's and the Vendor's halves of the journeys are API clients, since neither client is built: `harness/journeys/rider-handset.ts` reads the enrolment code from the QR the Ops screen draws (the picture's modules, rasterised and decoded with `jsqr`, a test-only dependency pinned like the Ops Portal's) and signs the sign-in challenge with a key of its own, and `harness/journeys/vendor-browser.ts` is the Vendor's browser. The stack's attestation verifier is the substitute (`substitute:VERIFIED` stands for an accepted chain): a real handset's chain is S0.61's, on hardware. What a journey may not reach through an operation is read through the closed lists, which name a staff member by work email, a vendor account by identifier and a rider by phone.
- The `/api/v1/e2e/*` routes (`cookies/issue`, `cookies/expire`, `echo`) exist only for the HTTPS specs of S0.23, in `apps/api/test/support/e2e-main.mjs`, never in `src/`. The technical journey, its notes routes and the `e2e_harness` table were retired by S0.45.
- A failing run must keep its evidence (process logs, sandbox capture, traces). Never add retries or weaken an assertion to get green.

## Tests

`pnpm --filter @melarc/e2e test` runs the harness's own unit tests and needs neither a database nor a browser. `pnpm run test:affected` reports the journeys a change reaches as owed and runs them only with `--with-e2e` ([the loop](../DEVELOPMENT.md#the-development-loop-and-the-gate)).
