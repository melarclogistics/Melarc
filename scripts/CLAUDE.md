# Root tooling (`scripts/`)

Node scripts, and the tests that hold the repository itself to its rules. Node runs them directly with type stripping (`node scripts/<name>.ts`): plain erasable TypeScript and imports written with `.ts`. They may use the root `devDependencies`, except the scripts CI runs before or without an install (`ci-aggregate.ts`, `ci-revision.ts` and `workflow-shapes.ts`, which they import): those import only Node built-ins.

## Rules

- Root tests run with `pnpm run test:root`, which names every test file (a glob would pass on zero tests). Add a new `*.test.ts` to that list or it never runs. `test-inventory.test.ts` fails when a test file of any package or of `scripts/` is run by no runner (`test:root`, a Vitest `include`, a Playwright `testMatch`), or a pattern matches nothing.
- `dependency-policy.test.ts` holds the manifests, `pnpm-workspace.yaml` and the lockfile to exact versions, no override but the one recorded exception (`OVERRIDE_EXCEPTIONS`: an exact selector and version, in `pnpm-workspace.yaml` and the lockfile alone, a finding once it goes stale), no patches or pnpmfile, `allowBuilds` false only, and registry sources only. `gitignore.test.ts` asks Git which names are ignored and that no tracked file is.
- CI is [.github/workflows/ci.yml](../.github/workflows/ci.yml): a `plan` job, then nine jobs and the `CI result` verdict, on a pull request, a push to main, a weekday nightly schedule and a manual run. A pull request runs every job but `browser-firefox-webkit` (the Firefox and WebKit shards of the browser tests; the Chromium shards are `browser-chromium`) and leaves the wall-clock database tests out; the others run everything ([what CI runs when](../DEVELOPMENT.md#what-ci-runs-when)). `ci-plan.ts` is the plan: the nightly run stands down when the last successful nightly run tested the commit main is at, and every way the question can fail answers "run". `ci-workflow.test.ts` fails when a mandatory command (it must be the whole script of its step, in the default shell and folder) or the aggregate wiring is dropped, a failure can be absorbed or skipped, a job leaves `ubuntu-24.04`, a trigger beyond push, pull request, schedule (a cron on weekdays, `1-5`, is required) and manual run appears, a job has a condition other than the plan's (`needs.plan.outputs.run == 'true'`, with `needs: plan` and nothing else; the Firefox and WebKit job adds `&& github.event_name != 'pull_request'`, never on a job that holds Chromium shards), the verdict does not name the plan (`ci-aggregate.ts --plan=`: a skipped job passes only on the schedule event with the plan's `run=false`, and the Firefox and WebKit job's only on a pull request with `--skipped-on-pull-request=` and `EVENT`; any other skip is a failure), a step that runs tests has no `timeout-minutes` at least two below its job's, an upload waits for `failure()` alone and not `failure() || cancelled()`, an install of browsers has no `actions/cache` of `~/.cache/ms-playwright` keyed by the system, the lockfile and the browsers before it, the database step does not set `MELARC_SKIP_TIMING_TESTS` to its one value (or another step does) or the database job is not a literal matrix of shards (`MELARC_DB_SHARD`), a browser job is not a literal matrix of its shards (shards 1 to N of an engine once, `fail-fast: false`) whose jobs are each handed their engine and shard (`MELARC_BROWSERS`, `MELARC_BROWSER_SHARD`), install that engine alone and name their artifacts for the entry, a pull request runs an engine but Chromium or a push to main, the nightly run or a manual run leaves one out, or the HTTPS journeys are not a literal matrix of the harness's shards (`MELARC_HTTPS_SHARD`, the browsers of its runs, artifacts named for the shard), or a job that holds WebKit's runs (the Firefox and WebKit shards, the HTTPS journeys) does not install the display (`sudo apt-get install --no-install-recommends --yes xvfb xauth`) before its test step or does not run that step as exactly `xvfb-run --auto-servernum --server-args="-screen 0 1920x1080x24" <command>` with `MELARC_WEBKIT_HEADED=1` (the one prefix a mandatory command may have, `DISPLAY_DRIFT`: WebKit is launched headed in CI, D-B4, and both Playwright configurations read the value), or a job that holds none has either, or `xvfb-run` is written anywhere else, or a step, a job or the workflow sets `CI` to anything but `true` (in an `env` or in a script) or takes it away (`unset CI`, bare or quoted, `env -u CI`, `export -n CI`, `declare +x CI`, `env -i`), or `MELARC_MIGRATION_BASE` is set in an `env` (the guard refuses an empty base and an expression is empty on a pull request; a push names it in the step `node scripts/ci-migration-base.ts`, which writes it to `$GITHUB_ENV` and must come before the guard in its job, in the default shell and folder, with no step between the two that writes the base again, handed the event, the previous revision, whether the push was forced and the job's token: a guard with no base compares a push to main with itself and passes, so the step, its place and its env are held, `MIGRATION_BASE_STEP`). `turbo-config.test.ts` holds every `MELARC_` variable the workflow sets on a task's step to that task's `passThroughEnv` (Turborepo's strict environment drops the rest, silently). `browser-shards.test.ts` lists the tests of every shard with `playwright test --list` (no browser) and fails, for each kind of run, when a test, a project or an engine is run by no job or by two, or a pull request runs Firefox or WebKit; `https-shards.test.ts` holds the HTTPS matrix to the shards of `e2e/harness/https-shards.ts`; `db-shards.test.ts` cuts the database test files into the CI matrix's shards with Vitest's own node interface and sequencer (`apps/api/test/database-shard-files.ts`, no test runs) and fails when a file is in no shard or two, or the variable does not reach the configuration. `workspace-pins.test.ts` holds the Node.js, JDK (`.java-version`), pnpm and action pins. A new check goes into the workflow and `REQUIRED_COMMANDS`; a new job also goes into the aggregate's `needs` and command line, and has the plan's `needs` and condition; more shards go into the matrix alone. Never add `continue-on-error`, `|| true` or a condition that can skip a check. The runbook's [B0.8 notes](../delivery/planning/BOOTSTRAP_B0_RUNBOOK.md#carried-forward-from-b08) say what CI does not cover.
- Documentation is held to the repository. `local-setup.test.ts` checks [DEVELOPMENT.md](../DEVELOPMENT.md). `agent-docs.test.ts` checks every `CLAUDE.md`: at most 90 lines for the root file and 40 for an area file, the required root sections, links and commands, every top-level folder mapped, and every Markdown file reachable from a `CLAUDE.md`. A new Markdown file or folder must be linked from the root map or from a document it reaches.
- `setup-env.ts` (`pnpm run setup:env`) creates the git-ignored settings files. It never overwrites, prints no secret and writes each file whole or not at all.
- `package-source.ts` (`pnpm run package:source`) makes the ZIP for source review from what Git knows, refuses settings files, keys, dependencies and output by name, and fails if a local credential or a private key block appears inside a file it would pack, or a path cannot be unpacked on Windows and macOS (names differing only by case, device names, a trailing dot or space). It never changes the working tree and prints no value. Its ZIP writer is plain (65535 files, 4 GiB): do not add ZIP64 without a need.
- `design-contrast.ts` recomputes every ratio in the colour tables of [DESIGN_SYSTEM.md](../design/DESIGN_SYSTEM.md) §4.5 and §4.6 from the hex values the document names, and `design-contrast.test.ts` fails when a figure, a ✗ or a "thin" flag does not follow. Change a colour and its table together.
- `design-tokens.ts` holds [apps/ops-web/src/styles/tokens.css](../apps/ops-web/src/styles/tokens.css), the one executable token source, to the same document: every documented token exists with its value, the pairings the components use meet their contrast threshold from the file's own values, no colour is written outside the file, no `var()` names a property nobody defines, no stylesheet imports, loads from another origin, uses `!important` or redeclares a token, and every focus rule draws an outline (forced colours keeps outlines, not shadows). Change a token in the document and the file together.
- `eslint-rules.test.ts` runs the real `eslint.config.mjs` over snippets: the Ops Portal may not use raw network, web storage, `window.open`, HTML injection or `eval`, and no driver is given a connection string. Loosening a restriction fails it. `markdown-links.test.ts` fails on a relative link or anchor between tracked Markdown files that leads nowhere, and `repository-shape.test.ts` on Python tooling, a second package manager's lockfile or a tracked settings file.
- `shadcn-wiring.test.ts` holds how shadcn/ui is wired into the Ops Portal ([DESIGN_SYSTEM §29.2](../design/DESIGN_SYSTEM.md#292-the-component-foundation)): `.mcp.json` runs the pinned `shadcn` package installed in `apps/ops-web` (no `npx`, no `@latest`, no environment), `apps/ops-web/components.json` writes the primitives into `components/primitives` in the `new-york` style with no registry but the official one, and the CLI is an exact development dependency. `design-tokens.ts` lets `apps/ops-web/src/styles/tailwind.css`, and no other stylesheet, `@import` a package: the build resolves it, and `apps/ops-web/test/build.test.ts` reads the built stylesheet for an import.
- `jdk.ts` judges the JDK the verifier needs, for `verifier.ts`, and for the gate and the affected run before they start what needs it. `verifier.ts` (`pnpm run verifier:test`, `verifier:build`) runs the attestation verifier's Gradle build ([apps/attestation-verifier/](../apps/attestation-verifier/CLAUDE.md)) once the JDK is the pinned major version; it never skips for a missing JDK. `verifier-process.ts` (`verifier:start`, `verifier:stop`, `verifier:status`) starts the JVM itself in the background from the verifier's git-ignored `.env`, records its process id below the operating system's temporary folder, and ends only a process whose command line is the verifier's; it hands the service its own settings and nothing else of the environment. `verifier-provenance.test.ts` holds the vendored library, the wrapper and the dependency checksums to what they claim, with no JDK.
- `infra-check.ts` (`pnpm run infra:check`) says whether PostgreSQL answers where the database tools look. It probes this machine only, sends no credential and changes nothing; its loopback rule is held to the API's by a test.
- `migration-immutability.ts` holds the migrations to main: it fails when a migration file that the merge base of `HEAD` and `origin/main` (or a local `main`, or `MELARC_MIGRATION_BASE`, which CI sets to the revision a push came from with `ci-migration-base.ts`: after a force push it fetches that revision by name with the job's token, and when it could not be fetched the run fails in words that name the force push, with git's error and no credential, and never falls back to `origin/main`; a push whose previous revision is all zeros created main and fails too) holds is changed, renamed or removed, and ends `2`, in CI and outside it, and says what to do when it cannot tell (no main, a shallow clone, a base with no migration: it never passes with nothing to look at; the precheck shows `2` as `warned` with these words in its summary and goes on, the gate and CI fail on it); a base that was named and is empty or is not a commit, and an option it does not know, end `1` everywhere (an empty `MELARC_MIGRATION_BASE` is a variable that was not filled in, never "none named"); a file only the branch has is free until it merges. It uses only Node's own modules, `migration-immutability.test.ts` builds real repositories, and the `static` job of CI checks out the whole history for it.
- `gate.ts` (`pnpm run precheck`, `pnpm run gate`, `pnpm run gate:status`, `pnpm run gate:stop`) holds the order of a full local check so that nobody has to remember it: [the development loop](../DEVELOPMENT.md#the-development-loop-and-the-gate). Its stages are the commands of CI, less the HTTPS run (`gate.test.ts` fails until a new check of CI is in `gate.ts` too); every cheap check runs before any test and a failed one stops the tests; a fingerprint of the files Git tracks or sees as new ends the run `UNSETTLED` when one changes. It starts only its own commands, ends only the process tree it started, never drops a database and parses no test output: a stage passes when its command exits 0. Never add an option that skips, retries or shards a stage. Every Vitest configuration bounds its own workers (`MELARC_TEST_WORKERS`, which turbo passes through); the gate removes `VITEST_MAX_WORKERS`, which Vitest would apply to every project, and `MELARC_BROWSER_SHARD` (CI's jobs each run one shard of the browser tests; a gate and an affected run run theirs whole), refuses an agent (`CLAUDECODE` set) without `--asked`, and refuses to start beside an affected run or without the JDK. Each test stage that passed on the settled tree records its targets for the affected run (`GATE_STAGE_TARGETS`).
- `affected.ts` (`pnpm run test:affected`) chooses and runs the tests a change can reach, by target: imports read from the source (resolved as Node, TypeScript and Vite resolve them), tests that read files or start processes, and per-target rules; `SPEC_AREAS` gives each Ops browser spec its page folders. Every rule leans to more tests: what it cannot place runs more, and `affected.test.ts` holds that every test file belongs to one target, every page folder to a spec, and every import of the code that runs resolves. It is not a gate: never let a rule choose fewer tests to save time, and never record a target that did not pass on a settled tree. `affected-baselines.ts` keeps each target's last green tree in the local build cache (below the installed dependencies, never committed), a saving only: a missing or untrusted record compares with the last commit. Like the journeys, the API's process tests (unless a `PROCESS_START_UP` file changed) and the development-server browser projects are run on request (`--with-process`, `--with-dev-browser`) and owed to the gate (the owner's decision of 27 October 2026): never defer more without the owner. It runs one at a time on a machine (`markRunning`, a heartbeat below the temporary folder) and never beside a gate. A new test folder or page folder goes into `DEFINITIONS` or `SPEC_AREAS` in the same change.
- Never write a check that passes when it has nothing to check.

## Tests

`pnpm run test:root` runs them all and needs no service.
