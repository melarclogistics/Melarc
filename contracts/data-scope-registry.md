## 1. What this document is for, and what v1 got wrong

`MSC-DEC-277` created it so that **an unclassified persistent table is impossible to miss.** That purpose is unchanged.

**What changed at R1 is the shape of the answer.** v0.1 gave each table a single RLS family — `HUB`, `VENDOR`, `RIDER`, `AUDIT` or `NONE` — and left a reader to compose them. The composition it implied was: *apply Hub scope, then restrict further for Vendor and Rider.* **That is the wrong model, and on one table it is wrong in the direction that denies legitimate access.**

**`Order` is the clearest case.** A vendor's order sits in whichever hub is fulfilling it. Under the layered model a Vendor principal would have been evaluated against a Hub predicate first — and a Vendor holds no `authorized_hub_ids` at all, so the honest outcomes were *see nothing* or *quietly treat an empty Hub set as permissive*. **The second is the failure `MSC-DEC-275` spent a whole decision preventing.** The vendor's boundary was never the hub; it was always `vendor_organization_id`.

**So access is evaluated by principal type, not composed across principals**:

| Principal| Boundary|
|---|---|
| `STAFF`| Table-specific Staff predicate, Hub `SET` or explicit `ALL` where the table is Hub-operational, global-master lookup only where explicitly allowed|
| `VENDOR`| `vendor_organization_id` = current Vendor. **Never inherits Staff Hub scope**|
| `RIDER`| Assignment or custody relationship to the current Rider. **Never inherits Staff Hub scope**|
| `SYSTEM`| Explicit task capability, or trusted `Outbox`-derived authority where a business object is involved|
| anything else, missing or malformed| **`DENY`**|

**`DENY` is written, never implied.** An empty cell in v0.1 could mean *denied*, *not yet considered*, or *inherits something*. All three read identically, and only one of them is a control.

## 2. Scope classes still describe the table. They no longer describe the access rule

The six classes remain, because they answer a real question — *what is this table's authoritative boundary* — and they carry the naming the rest of the programme cites:

`PLATFORM` · `HUB` · `VENDOR` · `RIDER_ASSIGNMENT` · `AUDIT` · `SYSTEM`

**But a class is not an access rule.** `Order` is class `HUB` and Vendor-owned to a Vendor. `PickupManifest` is class `HUB`, assignment-scoped to a Rider, and unavailable to a Vendor at all. `VendorStatement` is class `VENDOR` and Vendor-global, while Hub staff get Hub-filtered operational projections instead. `Evidence` is class `HUB` and carries **either** a Hub boundary **or** a Vendor-global one depending on its owner.

**`SYSTEM` is not a parking space**. A table whose scope is genuinely ambiguous is a finding in §8, not a `SYSTEM` row.

## 3. How to read the predicate columns

| Value| Meaning|
|---|---|
| **`DENY`**| This principal type has **no branch**. The `CASE` arm returns false|
| `hub&isin;SET/ALL`| Row's authoritative Hub is in `authorized_hub_ids`, **or** the Session explicitly grants all-Hub authority|
| `global`| Any authenticated Staff principal, subject to the operation's own permission key. Used for platform master data|
| `global *(master)*`| Identity lookup only. **Does not carry operational history**|
| `all-Hub <key>`| The named key **held with all-Hub grant scope**. A Hub-limited grant of the same key does not reach the row. Used for the global Vendor **control** records C1 separated from the master|
| `own`| `vendor_organization_id` = `melarc.current_vendor_organization_id()`. **Hub-independent**|
| `self`| The row's own principal — a Session, a factor, a device, an identity|
| `admin key`| Staff write gated by the existing administration permission for that domain|
| `task cap`| An explicit SYSTEM task capability, granted per task class and **named in §5.1 (a worker capability, reached through an `Outbox` envelope or the credential-delivery job) or in §5.2 (a capability that exists before a principal)**; where a row below says only `task cap`, the capability is the one whose *May touch* or *Reads/Writes* column lists that table. **A seed or backfill is a task class too**: it writes a forced-RLS table as `SYSTEM` under an explicit seed capability and never under a migration login ([MIGRATION_AND_SEEDING.md](../architecture/MIGRATION_AND_SEEDING.md) §5.1). **A capability is a label on the context, not an identity** ([SECURITY_DESIGN.md](../architecture/SECURITY_DESIGN.md) §14.1): a `SYSTEM` policy branch tests the capability it serves and never `SYSTEM` alone|
| `task cap *(authentication)*`| **The pre-authentication read path.** Sign-in, MFA proof, device proof and grant redemption all read these tables **before any principal exists**, so no `self` or hub predicate can serve them. It is a narrow SYSTEM capability bound to the authentication task and **limited to what §5.2 lists for `authentication`**, and it is written explicitly because the alternative — leaving the row `DENY` for every principal — describes a table nothing can reach and a product that cannot authenticate|
| `outbox scope`| SYSTEM authority derived from the immutable `Outbox` envelope|
| `api` `worker` `relay` `sched` `migration` `provisioning`| Technical identities of §5 — `melarc_api_runtime`, `melarc_worker_runtime`, `melarc_outbox_relay_runtime`, `melarc_scheduler_runtime`, `melarc_migration_elevated`, `melarc_provisioning`|
| `worker:<task>`| A **worker task capability** — `melarc_worker_cap_<task>` (§5.1). **Bare `worker` on a protected business table is a defect**, because the base runtime holds no such grant: it is the capability that reaches the table, and the consistency test must reject the mismatch if the base identity acquires one|

**A predicate here is a security boundary, never a permission.** Holding `pickup.request.create` is a separate gate that runs first; this document says which **rows** the holder may then reach.

**The `Staff authority` column says which gate that is** (`MSC-DEC-299`, C1). `operation key` means the row needs nothing beyond the calling operation's own `x-permission`, because its predicate is already bounded by hub, self or ownership. A **named** key means the read is not bounded that way and the key is what bounds it. **Every named key already exists in [permissions.md](permissions.md) §7** — the column reports the catalogue, it does not extend it.

**`hub&isin;SET/ALL` is resolved per operation, not per Session**. `SET` is the **intersection** of the authorizing grant's hub scope with the Session's authorized membership; `ALL` requires **that grant** to carry explicit all-Hub authority. An unrelated all-Hub grant held for some other operation does not widen this one, and an empty intersection returns no rows rather than all of them. See [SECURITY_DESIGN.md](../architecture/SECURITY_DESIGN.md) §14.1a.

**`VendorOrganization` moved here at R1**. **Nor is it a grant to the Vendor's global control records** (C1). §4.3 separates the master identity from `VendorAccountAllowance`, `VendorSuspensionHold` and `SecurityRiskHold`, which R1 left readable by any authenticated Staff principal on the strength of the master being global.

Returns the raw secret once, to the controlled channel (a custody bundle), and never logs it|
| `policy_change`| `migration` (`melarc_migration_elevated`)| The two functions of migration `0017`, `melarc.change_role_bundle` and `melarc.change_fixed_policy`, which run as the owner for their own statements and which only the migration identity may execute: no application context is opened under it, and the API, the worker and the provisioning login hold no `EXECUTE`| `RoleBundle` · `FixedPermissionPolicy`: `SELECT` and `UPDATE` (the revision, the floor and, for a bundle, the name) · `RoleBundleGrant`: `SELECT`, `INSERT`, `UPDATE` and `DELETE` (the complete new set of one bundle's grants), each **only inside those functions, under the exclusive policy lock** ([SECURITY_DESIGN.md](../architecture/SECURITY_DESIGN.md) §13.10a). The identity holds **no privilege of its own** on these tables, so a label asserted from any login reaches nothing it does not already hold. The sessions the function ends and the audit events it writes are statements under `authentication`, which already has their policies, inside the same transaction| By the bundle id or the principal type the caller names, each under its exclusive advisory lock taken before anything is read. Returns the kind of change (`NONE`, `NAME_ONLY`, `ADDITION`, `REDUCTION`), the new revision and floor, and the ids of the sessions it ended|

**Three rules keep a label from becoming an identity, and one limit stays.** First, DML on a table arrives with the first operation that writes it: the `api` identity holds no `INSERT`, `UPDATE` or `DELETE` on a table that only a seed writes, so asserting `seed` from the API reaches nothing; and the `provisioning` identity holds no privilege on those tables either, so asserting `seed` from the provisioning login reaches nothing outside the seed functions, and after the initialization nothing at all. The `api` and `worker` identities stay `SELECT`-only on the three policy tables (`RoleBundle`, `RoleBundleGrant`, `FixedPermissionPolicy`) for good ([SECURITY_DESIGN.md](../architecture/SECURITY_DESIGN.md) §13.10a); the controlled change of a bundle after the seed is the primitive of migration `0017` (S0.27, `policy_change`): a function that the migration identity alone may execute, not a write by any runtime identity. Second, a capability that touches a credential table (`authentication`) is bounded by the columns it may `UPDATE`, and its lookups are by the key the request presents because the port offers no other (a row policy cannot enforce that; the security matrix tests the interface, Family E). Third, `bootstrap` is bounded by the bootstrap shape its policy admits, by **the role** (since migration `0028` its policies admit the role the four functions run as and no other, so asserting the label from the API reaches nothing: a separation and not a narrowing) and by the command's own refusal to run against a non-empty staff table. **The limit:** for `authentication` the API also holds DML under its own operations, so it is a narrowing and not a separation, and code running as the API could assert the label — the accepted residual risk of [SECURITY_DESIGN.md](../architecture/SECURITY_DESIGN.md) §14.1. A **Write identity** column names the runtime identity that holds DML once an operation writes the table; until a slice builds one, only `seed` writes it.

## 7. Coverage and implementation requirements

Every persistent business or technical table requires a scope classification and explicit applicable principal predicates. Cross-check the domain model, architecture's technical-table declarations and the inventory here whenever a table is introduced. Embedded values and non-persistent projections are not tables.

### 7.1 Implementation validation

Use [security-test-matrix.md](../standards/security-test-matrix.md) for positive and negative controls at their specified enforcement layer. Classifications are requirements, not proof that database policies exist. Implement and test the actual policies for the task's scope. No documentation admission or signature package is required.

### 7.2 A read that counts, and the one that counts several queues (`getQueueSummary`)

A count over a table is a read of it, so **it is scoped by the rows of this registry and by nothing else**: no table is added and no predicate is changed by the queue counts of [the reporting data dictionary](../features/reporting/reporting-data-dictionary.md#55-the-queue-counts-queue-what-they-have-in-common). `getQueueSummary` (`self`: no key admits the call) reads `PickupRequest`, `OnePackageException` and `PickupStop` (the pickup queues), `PickupManifest` (the runs in progress) and `StaffIdentity` (the profiles waiting for approval) **once for each queue, in the context of that queue's own list operation**:

- **The key, the hub mode and the hub set are the grant of the list's key** (§3: resolved per operation, not per Session). The operation finds the session's grant for `pickup.read` or `staff.read` in the snapshot the session was issued with, computes its effective scope the way the authorization step does for that list, and runs the count under them. A key the session does not hold gives no context and no entry; a grant that reaches no hub gives a count of `0`. **It never takes the widest grant the session holds, or the scope of another key.** A decision key (`pickup.exception.approve`, `staff.identity.approve`) only admits the entry of its approver's queue; it scopes nothing.
- **Row-level security does the scoping**, as for the list: the `pickup_request_read`, `pickup_manifest_read` and `staff_identity_staff_read` policies of the tables above, with the key of the context (and the `one_package_exception_read` and `pickup_stop_read` policies for what a request shows of its exception and of its stops, which the filters on those read). The operation holds no predicate of its own on hubs, vendors or ownership, so a count cannot reach a row its list cannot. The one thing a caller may add is the optional `hub_id` ([hub filters](../features/operations/hub-filters.md), task C3): the list is given it as a filter and the count is given the same, one more condition inside the statement and **never part of the context**, so it can only remove rows the policy shows and never add one (a hub outside the grant, or that names no hub, counts `0`).
- **What it returns is a count and a moment** (`queue`, `count`, `oldest_at`): no row, so nothing of §4's `Notes` about field masking applies, and a count reveals no record the same grant's list would not.

### 7.3 A read that searches several tables (`lookupRecords`)

A search over a table is a read of it, so **it is scoped by the rows of this registry and by nothing else**: no table is added and no predicate is changed by the global lookup of [the feature](../features/operations/global-lookup.md). `lookupRecords` (`self`: no key admits the call; a POST that changes nothing, with the text in its body and never in a URL, the Product Owner's decision of 6 November 2026) reads `PickupRequest` and `PickupManifest` (under `pickup.read`), `VendorAccount` with its `VendorOrganization` (under `vendor.read`), `RiderIdentity` (under `dispatch.read`) and `StaffIdentity` (under `staff.read`), **once for each key, in the context of that key's grant**, the way §7.2 counts:

- **A kind is searched only under the key of its own read**, in the transaction that key's grant gives (the key, the hub mode and the hub set of the grant, never the widest grant the session holds). A kind whose key the session does not hold is not read and is absent from the answer; absence tells nothing about the records.
- **Row-level security does the scoping**, as for each kind's list and read: `pickup_request_read`, `pickup_manifest_read`, `vendor_account_select` (the organisation is read through the account, which is the hub-scoped row), `rider_identity_staff_read` and `staff_identity_staff_read`. The operation holds no predicate of its own on hubs, vendors or ownership, so a result cannot be a row the kind's own list would not give the same session. **`AdHocSender` is not read**: its policy is global to staff, and a phone resolved through it would tell a person which hub a sender is booked in; a phone is matched on the request's own contact phone, which the request's policy scopes.
- **What it returns is a pointer and the facts that say where the record stands, not the record**: the kind, the id, a code, a title, the record's own state, its hub (id and display name) and, for a request and a run, the service date, and for a request alone its sender's name as its own read shows it (`sender_name`); a phone only when the person searched by it and only masked (`phone_hint`). It names no page and carries no sentence (the Product Owner's decision D1, 6 November 2026). §4's `Notes` about field masking apply to these facts, and they say nothing a list would not show the same grant; a hub's display name is the label the session already shows for its own hubs, and a sender's name is the label the request's own read shows.
- **The name search of pickup requests is limited to current work** ([the feature](../features/operations/global-lookup.md), section 5; the Product Owner's decision D3, 6 November 2026). That is a limit of the question, asked of rows the session may already read: it narrows what a name finds and widens nothing.
- **It is audited as the lists are**: a staff read of a record outside the actor's own hub writes `auth.hub_boundary.crossed` once for each foreign hub the results represent ([audit.md](audit.md) section 5.4).

## 8. Findings — recorded, not resolved

### 8.1 `ZonePairRate` outlived the model that needed it

`MSC-DEC-207` withdrew the zone-pair matrix for flat service-area pricing, and [settings.md](settings.md) §7.6 lists `zone_pair_matrix` as **retired — must not govern**. **The entity is still in [domain-model.md](domain-model.md) §6.9's Hub row.** Classified so it cannot be created unclassified, and reported so it is not created at all without a decision.

### 8.2 ~~`AdHocSender` block reach~~ — closed at R1

Recorded at v0.1 as underdetermined. **`MSC-DEC-296` settles it**: Hub Senior Ops blocks are `HUB_LOCAL`, Platform Admin blocks are `PLATFORM_WIDE` with mandatory reason and enhanced audit. `AdHocSenderBlock` carries the discriminator explicitly, and **platform-wide reach is never inferred from a null `hub_id`**. `OQ-104` closes.

### 8.3 `Notification` inherits a scope whose field detail does not exist

A cross-cutting entity at §6.9 with **no field detail** — deferred to Phase 4 and `SLICE-010`. Its Hub and Vendor columns say *via subject*, which is the correct rule and is not yet a column a policy can read. `BACKGROUND_JOBS_AND_EVENTS.md` §3.4 names the hazard exactly. **The classification is sound; the fields it points at are owed by `SLICE-010`.**

### 8.4 Two persistent tables exist in architecture and in no contract

`Outbox` and `IdempotencyRecord` are required by `SOLUTION_ARCHITECTURE.md` §7 and `BACKGROUND_JOBS_AND_EVENTS.md` §3.7 and appear in **no** contract document. **R1 gives them a canonical home in §6** — which is a security inventory, not a domain model. **Whether they belong in the domain model is a contract question this document may not settle**; architecture carries no product authority (§42.7).

### 8.5 `VendorAccount`'s hub boundary: the operations' rule, held by a row-level rule through `VendorOrganization`

`MSC-DEC-442` narrows `getVendorAccount` and `listVendorAccounts` to accounts whose linked `VendorOrganization`'s responsible hub is in the caller's grant, **and says the record stays a global master at the persistence level**: a vendor has one account whichever hub serves it, and nothing of the table changes for that. The question this section left to the Backend Engineer, whether a Staff row-level rule through `VendorOrganization` should also exist, was answered by S0.47 (migration `0034`; the Product Owner's to confirm): **it exists**. A Staff context reads an account under `vendor.read`, `vendor.organization.approve` or `vendor.credential.recover` only where its organisation's `responsible_hub_id` is in the caller's hubs (or the caller's grant reaches every hub), and the scope probe of [SECURITY_DESIGN.md](../architecture/SECURITY_DESIGN.md) §14.4b reaches the account **through** the organisation (the account has no hub column of its own; `hubVia` of `platform/database/scope-probe.ts`), so an account outside the caller's hubs is `HUB_SCOPE_VIOLATION` and one that does not exist is `NOT_FOUND`, decided by the database and not only by the operations' code. The record is still the master of the vendor's identity; the rule narrows who may read it, not where it lives.
