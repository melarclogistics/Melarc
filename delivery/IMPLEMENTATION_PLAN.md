## 1. What a slice is

A slice delivers a demonstrable product capability across its required surfaces and backend. Implement it as bounded tasks under [DEVELOPMENT_EXECUTION_PLAN.md](DEVELOPMENT_EXECUTION_PLAN.md); a task may cover a small part of a slice. Preserve existing slice IDs.

## 2. How a slice moves

Define scope and unresolved requirements, implement bounded increments, run meaningful checks, fix failures and demonstrate the integrated capability. The readiness and completion standards apply to the actual scope. A specification status is not a build or release result.

## 3. Sequence

Ordered by dependency, not by value. A slice appears after everything it needs.

**What the slices are collectively for — §43.4.** The baseline states the acceptance gate for the whole product, and **no document cited it** until the Phase 4 audit:

> *"Version 1 cannot be accepted until the approved launch transaction can be demonstrated **from booking through a terminal delivery/return and financial outcome, including exception recovery**."*

**That is one continuous demonstration, not a sum of slice demonstrations.** `SLICE-000` through `SLICE-004` are each demonstrable alone; §43.4 asks for booking → pickup → hub → price → dispatch → delivery → payment → reconciliation **in one run, with an exception recovered along the way**. Nothing in this plan produces that until `SLICE-004` completes, and the plan should not be read as implying otherwise.

§43.4 also names what launch acceptance still depends on: payment and reconciliation detail, technical security and OTP contracts, exceptional returns and claims, reporting targets, and measurable NFRs.

**A performance task C1 leaves: the marker for the manifest pool (decided by the Product Owner on 5 November 2026; not built).** The count of the pool of confirmed pickups not yet on a run (`PICKUP_UNMANIFESTED_POOL`), and the list filter `manifested=false` that it follows, read every confirmed request, because a collected request stays `CONFIRMED` with an unreleased stop and "has no unreleased stop" cannot be made a lookup by an index. C1 measured it at 380,000 confirmed requests (PostgreSQL 18.6, the runtime role, the real security context): 0.7 seconds for a session that reads no hub, 1.7 seconds at all hubs and 2.3 seconds at one hub of 190,000, where each of the five other counts took 2.5 milliseconds or less. **The Product Owner chose option (a): a marker on the request, set when a stop claims the request and cleared when that stop is released, kept by the database,** so that the pool becomes an indexed lookup. It is a task of its own: a migration, the trigger or function that keeps the marker, the change of the shared filter in `pickup-request-criteria.ts` (so the list and the count change together), and a new run of the scale plans. **It is to be done before production volumes, and in any case before a hub's history passes about 100,000 confirmed requests.** Since task P1.1 (decision D11a) the summary fails whole when one of its counts passes 3 seconds (`AC-QSUM-13`), so the cost of this count, which grows with the history, becomes a failed summary (no counts in the menu, a failure on the landing) and not only a slow one: at the cost C1 measured (2.3 seconds for a hub of 190,000 confirmed requests, about 12 microseconds a request) that is a hub of roughly 250,000 confirmed requests (a linear extrapolation, not a measurement). The two other options (ending the claim of a request whose pickup is closed, and bounding the pool by a date) were not chosen. The measurements and the options are in [the data dictionary](../features/reporting/reporting-data-dictionary.md#14-unresolved-requirements).

**A second performance task, from C2: the cost of the row-level security policy (decided by the Product Owner on 6 November 2026; not built).** A statement that reads a hub-scoped table and has no condition the planner may run before the policy (a leakproof one: an equality or a range comparison, not `LIKE` or `ILIKE`) evaluates the policy for each row it reaches, and that costs about 3 microseconds a row on the runtime login: 1.1 to 1.5 seconds for the 400,000 pickup requests of the name search of the global lookup (C2, C2.1), where the approved `pg_trgm` index cannot take effect for the same reason, and perhaps a part of the pool count above. Caching the policy's settings and its hub set inside the policy expression did not reduce it, so where in the policy it lies is not identified. **The task is to find out why, and to fix it in the policy of every table**, which would speed every read that cannot use an index at once. **It is to be done before production volumes**, next to the marker above, and measured on the name search, the pool count and the other counts of C1 at 400,000 rows. The measurements, the cause and the other options are in [the lookup feature, section 14](../features/operations/global-lookup.md#14-unresolved-requirements).

**A performance task from the audit of 7 November 2026: the filter on approved or refused exceptions (not built).** `listPickupRequests` with `one_package_exception_state=APPROVED` or `REJECTED` takes about 1 to 6 seconds at 100,000 approved exceptions, in both forms of its condition ([the feature, section 14.1](../features/operations/hub-filters.md#141-measured-at-400000-requests) and item 6 of its section 14): the candidates scan the approved exceptions and evaluate the exceptions' policy for each, and each candidate request is then checked. No screen asks for it and the queue summary does not count it. It is a statement written for the history, measured at its volume, to be done when a screen offers the filter.

**A performance task from the audit of 7 November 2026: a lookup path that does not hold the bundle policy lock (not built).** `lookupRecords`, a POST that changes nothing, runs each key's search on `OperationRunner.mutate`, which holds the shared lock of the bundle's policy for as long as the search runs, so a slow scan holds that lock for everything that changes a bundle. Since audit fix A5 every statement of the lookup is bounded at 3 seconds (the general authenticated bucket already counts the lookup, so no bucket of its own was added), but a door for a POST that changes nothing without that lock would remove the cost itself: it is a change of the authorization step ([SECURITY_DESIGN 13.10a](../architecture/SECURITY_DESIGN.md)) that needs the Product Owner's decision, and the name scan of [the global lookup, section 14](../features/operations/global-lookup.md) is the case to measure. To be read with the row-level security cost task above.

**A third performance observation, from C3: the request list's order is served by no index (not built).** The list is ordered by `created_at, id`; with a hub the statement reads the hub's rows through `pickup_request_hub_idx` and sorts them, 0.8 seconds for a first page at 200,000 requests in a hub (1.4 seconds without a hub, which scans the table). An index on `(responsible_hub_id, created_at, id)` is the candidate for the read with a hub, and one on `(created_at, id)` for the read without; neither was measured. To be read with the two tasks above, at the volumes of production ([the feature, section 14.1](../features/operations/hub-filters.md#141-measured-at-400000-requests)).

**A later task, from P1.1 (decided by the Product Owner on 6 November 2026; not built): tell the Senior Ops of a rider's hub whenever the device of one of their riders is replaced by someone outside that hub.** The Platform Admin may replace a rider's device at every hub (decision D5), and the Product Owner accepted that as it stands, with the risk that attendance in person is an operating rule the system cannot check (the contract says so). No second approver, step-up of the second factor or alert is built now; this notification is the control the Product Owner chose to add later. It is specified and built in a task of its own.

**A later contract task, from the review of 499399c (decided by the Product Owner on 9 November 2026; not built): a history that names who did each act.** The history of a pickup request and of a pickup run (the Timeline of the record page) is the record's own dated facts; naming who did each act (who confirmed, who assigned, who dispatched, who cancelled) needs a read of the audit trail that the pickup API does not give an Ops session, so the page does not draw it and invents nothing. The task is an operation, specified and contracted in its own task, that serves the acts of a record to a session that may read it. (The history of a pickup run now begins with its moment of making, `created_at`, contract 5.100.0; the moment of a cancellation is an open item of the manifests slice, OB-S1-79.)

## 4b. The dead-letter triage queue has an architecture requirement and no slice

*CRIT-16 audit remediation, 13 September 2026.*

**§42.5 requires it in the Master Specification's own words**: *"Failed jobs must be visible and recoverable without duplicating business effects."* [BACKGROUND_JOBS_AND_EVENTS.md](../architecture/BACKGROUND_JOBS_AND_EVENTS.md) §3.3 restates the requirement in operational terms — *"a queue a person can look at,"* with audited, idempotent replay — and **nothing in this table, `surfaces/ops-portal.md`, or any slice document names the screen that satisfies it.** A dead-lettered job carrying a financial or custody effect is invisible not because the architecture failed to say so, but because no slice was ever told to build what it said.

**Assigned to `SLICE-013`, engineering scope rather than a Product sequencing call.** §42.5 sits in §42's cross-cutting API/backend engineering section, not in any of the operational domains §21–§34 map to a specific slice — the same reason `SLICE-013` exists at all: **Settings, reason-catalogue and courier administration is cross-cutting platform operation that belongs to no single parcel-flow domain**, and background-job/dead-letter administration is the identical shape of concern, one layer further down the stack. `IMPLEMENTATION_PLAN.md`'s own approver line routes **sizing** to engineers and reserves only **sequence and priority** for the Product Owner; which existing slice's scope a screen falls under is a sizing call, not a priority one, and this section makes it rather than leaving the requirement unscoped indefinitely. **The Product Owner may reassign it** — to a dedicated slice, or elsewhere — at any point without this reasoning standing in the way; what this section removes is the state where nobody owns it at all.

**No new slice is opened, and no slice count changes.** `SLICE-013`'s `Depends on` (`000`) is unaffected — the dead-letter queue's own dependency is the background-job infrastructure `000` already requires nothing beyond, since audit and permission enforcement are the only cross-cutting foundations a triage-and-replay screen needs.

*`SLICE-009`, rider administration — a status change ends the session:*

```text
Given a rider with a live session and a valid access_token,
When an authorised officer sets the rider's status to INACTIVE or SUSPENDED,
Then every live session of that rider is terminated in the same transaction as the status change,
And the rider's next API call returns 401 SESSION_INVALID,
And no later sign-in succeeds while the status stands.
```

*`SLICE-009`, staff administration — a reduced bundle ends the session:*

```text
Given a Senior Ops user with an ACTIVE session issued four hours ago,
When a Platform Admin approves a bundle change that reduces that user's authority,
Then every live session for that identity is terminated with AUTHORITY_CHANGED,
And the next request returns 401 SESSION_INVALID,
And a fresh sign-in receives a snapshot carrying the reduced bundle.
```

*`SLICE-009`, staff administration — removing a permission needs no code change:*

```text
Given a bundle holding a permission,
When an approved bundle change removes that permission,
Then every live session issued from that bundle ends with AUTHORITY_CHANGED in the same transaction, a session created after the edit is refused with PERMISSION_DENIED,
And no deployment or code change was required.
```

*`SLICE-009`, staff offboarding — succession:*

```text
Given a bootstrap Platform Admin and two non-bootstrap successor Platform Admins who are approved, credentialed, MFA-ready and have each signed in,
When that bootstrap identity is offboarded,
Then its live sessions end with OFFBOARDED and the bootstrap-resume mechanism refuses to operate for it,
And auth.bootstrap.succeeded is written once for that identity, as an enhanced record,
And offboarding a bootstrap identity with fewer than two such successors is refused with the code the offboarding operation declares, and neither bootstrap identity is ever deleted.
```

*`SLICE-009`, staff offboarding — recovery cannot outlive the identity:*

```text
Given a staff identity with a PENDING recovery request, a PENDING setup grant and their delivery jobs,
When it is offboarded while a completion of that recovery link waits for the identity lock, and again with the completion first,
Then with the offboarding first the completion is RECOVERY_TOKEN_INVALID and changes nothing, and with the completion first it stands and the offboarding ends what is left,

```

*`SLICE-008`, vendor termination — recovery cannot outlive the account's organisation:*
