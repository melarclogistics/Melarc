> **Status:** ACTIVE SPECIFICATION — implementation status is stated separately

> **Owns:** navigation, screen inventory and interface states for the internal command centre

## 1. What this surface is

Melarc's **desktop-first responsive internal logistics command centre** (§17.1). One controlled environment for creating work, monitoring operational state, resolving exceptions, recording custody, applying approvals, and seeing cross-vendor activity appropriate to the user's role.

**Boundary.** Not a rider field tool. Payroll, general accounting and procurement are outside Version 1. Desktop-first workflows must stay usable at narrower widths but may optimise dense operational tables for desktop (§10.3).

## 2. Users

The seven bundles at §11.3 that use this surface: **Ops Staff**, **Senior Ops**, **Platform Admin**, **Finance/Reconciliation**, **Auditor**, **Executive/Report-consumer**, **Fleet Manager**.

**Customer Support and Warehouse Supervisor deliberately have no dedicated bundle** — support sits inside Ops Staff, hub-floor supervision inside the Ops Staff / Senior Ops split (§11.3, `MSC-DEC-137`, §11.3, `MSC-DEC-140`). §17.2 is explicit that this is a decision, **not an undefined gap**.

## 3. Hub visibility

§17.5, and this is finer-grained than it first appears:

| Bundle| Sees|
|---|---|
| Ops Staff and hub staff| Primary hub **plus any currently effective temporary-assignment hub**|
| Senior Ops| Own hub|
| Platform Admin and authorised company-wide roles| All hubs|

**A temporary hub assignment never grants company-wide visibility**, and "cross-vendor" never implies unrestricted database access. Enforced server-side and audited.

**How the portal presents it** (Product Owner, 5 November 2026; presentation only, the server's scoping is unchanged). The hub switcher of the top bar (§4) sets which hub's work the screens show. A create form starts with the chosen hub filled in. An act on an existing record uses that record's own hub, whatever the switcher says. A Platform Admin may choose "All hubs" to browse, but every act is taken in one hub, which the screen header shows. Choosing "All hubs" is a request and creates no access. Task C3 gave the four reads the switcher narrows (`listPickupRequests`, `listPickupManifests`, `listNotifications` and `getQueueSummary`) an optional `hub_id`, a filter that narrows and never widens ([hub filters](../features/operations/hub-filters.md)); redesign step R4 sends it, and checked how each other operation names its hub (below).

**As built in redesign step R4** (`apps/ops-web/src/platform/hub`). The choice is held in memory in the tab and is never kept in the browser; it starts at *All hubs* for a session that lists more than one hub, and a session that lists one has no choice to make (the top bar names the hub and offers no menu). It lives above the router and inside the session (`HubChoiceScope`, scoped to the session's id), so that it lasts as long as the session does: a person who goes to a page outside the shell (the page of an address that matches no route) and comes back finds the hub they had chosen, and the next person to sign in never finds the previous person's. A screen reads it in one place only, `useActiveHub`, which gives the hub chosen or nothing for *All hubs* (the switcher itself, which also lists the hubs and changes the choice, is `useHubChoice`'s, and only the shell uses it); a page may also read `useHubScope`, which gives the hub with its name and the one thing a page may do about it, *Show all hubs*, and cannot choose a hub. **A chosen hub is a filter** (audit B1, 7 November 2026): a list that is empty while a hub is chosen says "Nothing at <hub>" and offers *Show all hubs*, and never "No <things> yet"; My work says "Waiting for you at <hub>" (B9). **A run is for one hub** (audit R4-12): the run builder asks which hub the run is for when the switcher is on *All hubs* and the session reaches several, takes the switcher's hub otherwise, reads the pool of that hub only (also for a session of one hub), says "Run for <hub>", and asks before it clears the requests already chosen when the hub of the run changes, so that a run of two hubs' requests cannot be made. The message log of one record is the one list the switcher does not narrow (`AC-HUBF-09`, decided by the Product Owner on 7 November 2026). How an operation names a hub decides what the choice can do, and the contract names it in four ways: in a create body (`createPickupRequest` for a walk-in, `createStaffIdentity`, `createVendorOrganization`, `openCashHandover`, `requestAccountingExport`), in a query `hub_id` that narrows a list (`listStaffIdentities`, `listRiders`, `listVendorAccounts`, `listAccountingExports` and, since task C3, `listPickupRequests`, `listPickupManifests`, `listNotifications` and `getQueueSummary`), in the path of a hub's own record, or in another meaning (the destination of a handover, the hub a request moves to). So the portal starts the two create forms it has built with the chosen hub (the walk-in booking's *Hub*, the staff profile's *Primary hub*), and sends `hub_id` on the staff, riders and vendors lists and on the pickup requests, the pickup runs, the message log and the queue summary when a hub is chosen, and nothing for *All hubs*, so that the counts beside the menu and My work follow the choice; a list starts again at its first page when the hub changes. The booking form does not offer only the hubs whose booking settings are in force: no read of a hub's settings exists to tell it.

## 4. Navigation model

Seven groups in the sidebar, in the order of the hub's day (Product Owner, 5 November 2026). A group is shown only when the session holds a key for one of its built pages, and only built pages appear: a page that is not built has no entry even when its key is held. **Queue counts and filters that make pending work visible are the organising principle** (§17.4): this is a surface where the primary job is knowing what needs attention. A queue entry carries a live count where the server states one, and a count that is missing or still loading is never drawn as `0` (§8). **The server states one through `getQueueSummary`** (task C1; [the six queues](../features/reporting/reporting-data-dictionary.md#55-the-queue-counts-queue-what-they-have-in-common) and the moment each is old from are defined in the data dictionary): beside *Requests* (waiting for confirmation), *Decisions* (one-package exceptions waiting for approval), *Pickup runs* (runs in progress) and *Staff* (profiles waiting for approval). The late bookings and the pool of confirmed pickups not yet on a run have no entry of their own (the pool's page is an action of the New menu, which draws no count) and show on My work alone. A read that failed draws no count and leaves the sidebar as it is. **When the count is read is [`AC-QSUM-09`'s](../features/reporting/reporting-data-dictionary.md#13-acceptance-criteria)** (on load, on a change of page, on a queue's refresh, on a change of hub and after an act that changes a queue, never on a timer), and what is drawn is `AC-QSUM-07`'s. The acts that change a queue are listed in one place, `platform/queue-summary/queue-changing-acts.ts`, which a test reads against the contract. **The counts follow the switcher** (task C3; [the hub filters](../features/operations/hub-filters.md)): with a hub chosen each count is that hub's, and with *All hubs* it is every hub the session's grant reaches. The staff approver's queue is counted by the profile's primary hub, so a profile with none is in the all-hub count only and the per-hub counts of that queue need not add up to it, which is intended (Product Owner, 6 November 2026; [the data dictionary, 5.5.6](../features/reporting/reporting-data-dictionary.md#556-queuestaffawaitingapproval--staff-profiles-waiting-for-approval) owns the rule).

The groups and entries are those the Product Owner decided on 5 November 2026, together with the Product Owner's placement, the same day, of the pages the groups left out: Carrier handoffs in Dispatch, Parcel returns in Hub, Road expenses in Money, the OTP fallback in Decisions, and the audit log and Reports in System when they are built. A page that no entry names is placed in a group by the Product Owner when it is built.

**The needs-decision queue is specified in unusual detail** by §17.3 and the fields are mandatory: failure category, reason, evidence, contact attempts, wait time, attempt count, retryability, cap state, escalation state.

**Signed-in navigation comes from the caller's current session** (Product decision, 8 October 2026; the source was an open question before it). `getCurrentSession` returns it as `CurrentSession`: the permission **keys** the session holds, as hints, together with the principal's display name and its authorised hubs (id and name only). Only that representation carries the name and the hubs; `listSessions` and `revokeSession` do not. Navigation entries are derived from those hints and from the **implemented** route definitions only: a permission that exists in the catalogue exposes no entry for a feature that is not built. A hint never authorises: every operation authorises on its own on the server, and hiding an entry is not enforcement (§45.7). The shell's navigation component takes a plain list, so showing and hiding stay presentation; no bundle contents, credential or role name is returned or inferred ([staff-authentication](../features/identity/staff-authentication.md) §12).

**The navigation is the sidebar** (Product decision, 25 October 2026: the Ops Portal is an application and not a website; its form since redesign step R4, Product Owner, 6 November 2026). It is an Ink sidebar docked at the left of every signed-in screen, 248px wide, with the all-white lockup at its head and, for each entry, an icon, a label and where the server states one a count. **The current entry is a solid crimson fill with white bold text** and `aria-current="page"`. It is the 64px rail of icons below 1280px and when the person asks for it (the name of an entry is then in a tooltip and stays in the entry for a screen reader, and the choice lasts as long as the page and is never kept in the browser), and the full sidebar from 1280px and when the person asks for it. **Under 768px it is a sheet** that the top bar's menu button opens: a modal dialog named *Main menu*, with focus kept inside, closed by Escape, the scrim or *Close menu*, and the page behind it out of reach of assistive technology. At its foot it names the person and says where they act (the hub, or how many hubs): **the session names no role** (the contract returns none and none is inferred), so none is shown. The sign-out control is in the account menu of the top bar. The pre-sign-in screens have no navigation at all and are drawn in a split-screen layout, decorative photography beside the form. The look and the behaviour are in [DESIGN_SYSTEM.md](../design/DESIGN_SYSTEM.md) (§13.1, §13.1a, §24) and [COMPONENT_PATTERNS.md](../design/COMPONENT_PATTERNS.md) (§12, §22).

**The top bar** (Product Owner, 5 November 2026; as built in step R4) is 56px high, is the banner of every signed-in screen, and holds five things.

- **The hub switcher.** A person browses the hubs their session lists, and a session that lists more than one may browse "All hubs" (the portal cannot tell which session's grant reaches every hub, and for a session with two hubs "no hub" is what its screens show; the choice creates no access, §3). It is a 6px crimson square and the hub's name; a session with one hub gets the name alone, with no menu. What the switcher sets, and where an act takes its hub from, is §3's.
- **A global search** that opens any record by its code, a name or a phone number (Ctrl/Cmd K). It is a read under the session's own permissions and scope, and it obeys §10: it never leaks another vendor's or an unauthorised hub's data. The contract owns what it searches, for whom and what it returns: `lookupRecords` serves it (task C2; [the feature](../features/operations/global-lookup.md); a POST that changes nothing, the text in its body and never in a URL, because a phone number typed in full must not travel in an address). **The search is a button that looks like a field, not a field:** opening a dialog when a control merely takes focus is a change of context on focus (WCAG 3.2.1, level A), so a click, Enter or Space opens the palette, as does Ctrl or ⌘ K from anywhere in the shell. **The palette** has three groups in this order: *Go to* (the built pages the session may open, found by their name or by what they are for), *Create* (the New menu's actions) and *Records* (the search, asked once the text has stood still and is two to 64 characters, which is what the server takes). The line under a record is **written by the portal from the facts the server gave**: the sender, the state in the words the same state has on its own page, the hub, the day, and a phone number only as the server masked it, on the record that number found; a state the portal has no words for is left out and never drawn as it came. A record opens by the portal's own page for its kind. Each state of the search is told in plain words (a hint under two characters, *Searching…*, *No record matches “…”*, a text too long to search, and a failure with *Try again*), and **nothing is asked again by itself**: when the session has asked too often (`429 RATE_LIMITED`; the limit is [`rate_limit_authenticated_api`](../contracts/settings.md#77-platform--security-operations), which owns the number), the palette says in its own words to wait, and asks again only when the person presses *Try again*. Escape closes it and gives focus back to what had it; a record or a page chosen gives focus to the new page's heading.
- **The theme control.** *System* (the default, which follows the computer's setting), *Light* or *Dark*, in the top bar and in the account menu (on a narrow screen in the account menu alone). The choice is the one thing the portal keeps in the browser (`localStorage`, the key `melarc-theme`, written for Light and Dark and removed for System) and is applied before the first paint by a script of the page's own origin (`/theme-init.js`), because the content-security policy refuses an inline script.
- **A New menu.** Every create action moves into it from the sidebar: Book a pickup (`/pickup-requests/new`), Build a pickup run (`/manifests/new`), Build a delivery run (`/delivery-runs/new`), Add a staff profile (`/admin/staff/new`), and later New vendor and New rider. An item is offered only when the session holds the key its page needs and the page is built, and each page keeps its own route and permission. It is the one crimson button of the portal; a session that may create nothing has no button and no empty menu.
- **The account menu.** Who is signed in and where they act, the personal pages (Trusted browsers, `/account/trusted-browsers`), the theme, and sign out. **No page called "Profile and hubs" is offered: none exists**, and a page that is not built has no entry. Sign-out keeps the menu open on *Signing out…* while it is under way, and a sign-out that did not finish is told at the top of the page, as [the shell's section of the component patterns](../design/COMPONENT_PATTERNS.md#126-the-authenticated-ops-shell-as-built-s042-the-sidebar-and-the-top-bar-since-redesign-step-r4) says.

**A record opens beside its list.** Opening a record from a queue shows it in a side panel beside the list, with "Open full page"; the queue's filters, scroll and selection survive. At 768px the panel becomes a full-screen sheet and the sidebar collapses to icons ([DESIGN_SYSTEM.md](../design/DESIGN_SYSTEM.md#12-responsive-model)). The template is the record's ([PRODUCT_DESIGN_DIRECTION.md](../design/PRODUCT_DESIGN_DIRECTION.md#62-record)), and the panel changes nothing that a record's page offers or refuses.

**How many requests a session sends** (measured on 7 November 2026, audit follow-up B13). The Product Owner's decision stands: [`rate_limit_authenticated_api`](../contracts/settings.md#77-platform--security-operations) is **120 a minute** (`CONFIRMED`, `MSC-DEC-371`), with no new bucket and no sub-ceiling. The Portal sets no timer and reads nothing again when the window gains focus, so the requests of a session are the person's: the reads of a page, one read of the counts at each change of page, of hub, at a refresh and after an act that changes a queue ([`AC-QSUM-09`](../features/reporting/reporting-data-dictionary.md#13-acceptance-criteria)), one search for each text the palette has stood still on, and the acts. A browser test, `apps/ops-web/test/browser/request-rate.spec.ts`, drives one officer through a heavy session against the browser tests' stand-in for the API and counts the requests the browser sent, by operation, with the time of each. It is skipped unless `MELARC_MEASURE=1` (it takes about four minutes; its header says how to run it, and `MELARC_MEASURE_QUICKER=2` halves every pause). **The officer** reads a page for 4 seconds, waits 2.5 seconds between clicks and 3 after an act, and types a key every 130 ms: My work, a switch of hub and back, the pickup queue (a filter, the next page, a refresh), three requests opened and confirmed, two palette searches typed with a correction (one closed, one opening the record it found), a run built from the pool and made, the runs and My work again; twice round, 249 seconds. **The busiest 60 seconds** (a window that slides over the requests) held **30 requests, under the 60 that is half of the limit**, and the average was 25.3 a minute. With every pause halved (an officer twice as quick, 135 seconds) the same actions gave an average of 46.6 and a busiest 60 seconds of **52**, still under 60. No waste had to be removed, and the setting is not changed.

**What the stand-in does not model:** real latency (it answers at once, so a slow answer that keeps a person waiting, or makes them click again, is not here), a second tab or a background tab, the browser's own retries and any failed read, a second person on the session, and real data (sixty requests, two hubs, a search that finds three records). The pace is one reading of "heavy", written in the test. The figures are what the Portal asks for at that pace, and say nothing of what each request costs the server. Records open as pages: the side panel above is not built yet, and opening a record there will not read more than the page does.

## 5. Two booking channels, one set of rules

`MSC-DEC-215` confirms vendors book **by WhatsApp, entered by Ops**, or **through the Vendor PWA** directly. Both run concurrently; neither is a migration stage.

**The binding requirement is that they are indistinguishable downstream.** Both paths must apply identical validation and produce identical records — the minimum-package rule, the 10am cutoff queue, the corridor batch-day fee and the indicative estimate all behave the same way whether a vendor typed the booking or an Ops officer transcribed it from a chat. **A rule enforced on one channel and not the other is a defect, not a channel difference.**

This also explains `MSC-DEC-196`. Vendor self-service was deferred not as a scheduling choice but because WhatsApp is how vendors actually book today, which is why Ops-created bookings are the primary path in Version 1.

**WhatsApp has no surface document.** It carries no screens Melarc controls, so §41's interface states do not apply to it in the ordinary way — the same situation as the recipient channel. Whether it belongs here as an intake path or needs its own entry is `OQ-063`.

Two routes carry rules that a competent implementation will otherwise get wrong:

**Gate A added four, and three of them are pre-authentication** — which is the point of them. Before Gate A the product had **no screen on which an employee could establish their own first credential**, so onboarding ended at an administrator typing someone else's password.

**Three rules here would be broken by an ordinary, well-intentioned implementation.**

**`/sign-in/mfa` must look like a sign-in page, not the application.** The natural build renders the app shell once the password is accepted and overlays a code prompt. That shell implies a session exists. It does not — `MSC-DEC-228` withholds the session entirely until the factor lands, and a shell that suggests otherwise trains users to expect access they have not yet earned.

**`/recovery` has no *account not found* state, and `/sign-in` has no *locked* state.** Every framework offers both and each is exactly the disclosure §37.7 forbids: it confirms which addresses belong to real staff, and Melarc staff emails follow a predictable pattern. The lock is announced at the second factor, where the person has already proved the password.

**No page that acts on another principal's credential may have a field capable of displaying one.** Not masked, not reveal-on-click. Recovery and re-issue re-establish a path for someone to set their own credential; a screen that could show one turns an administrator into a person who knows a colleague's password. This is the rule `/admin/recovery` carried, and it now binds `/admin/staff/{id}` and `/admin/vendors/{id}`.

**`/setup/*` must not render the authenticated shell either, and for a sharper reason than `/sign-in/mfa`.** These pages are reached by a **grant**, and a grant authorises exactly one act on one principal. A shell around it invites the natural next build — treating the grant as a session and letting the user navigate — which would be an unaudited authentication path around every control above it.

**`/admin/staff/{id}/mfa/reset` must never show the re-enrolment grant.** The acting Platform Admin resets the factor; **the target completes the enrolment.** A screen that displayed the grant would let one administrator enrol a factor on another person's account, which is exactly the concentration of authority the Platform-Admin-only rule exists to bound.

**Two rules here that an ordinary implementation will break.**

**`/delivery-runs/{id}` must show a rollback as a rollback.** §24.5 dispatch is atomic: one order's failed revalidation rolls back all twenty stops and the run stays `DRAFT`. The natural rendering is a generic error toast — which leaves Ops staring at a `DRAFT` run unable to tell whether the dispatch was attempted and refused, or never submitted. **The screen must name the failing order and the failing check**, because `dispatch.run.rollback` records exactly that and the screen is where it is acted on.

**`/pre-dispatch-confirmation/{orderId}` must not rank the four outcomes.** A form that puts `confirmed` first and styles it as success trains Ops to treat the other three as failures to avoid. `reschedule`, `address_correction` and `unreachable` are **routine outcomes of a routine call** — and one of them, address correction, is how a wrong delivery gets prevented.

**Only `unreachable` takes a reason, and the picker offers four** (`MSC-DEC-409`, 25 September 2026): `NO_ANSWER`, `NUMBER_INCORRECT`, `RECIPIENT_DECLINED` and `CONTACT_NOT_POSSIBLE_MELARC`. **`RECIPIENT_NOT_AT_LOCATION` is not offered here** — it is `DOORSTEP`-only and the server refuses it with `REASON_NOT_VALID_FOR_CHECKPOINT`, so a screen that listed it would make a refusal discoverable only on submit. **`reschedule` and `address_correction` must not ask for a reason**: the person was reached, and the record they produce is a commitment revision or a location-change request. **`RECIPIENT_DECLINED` routes to the Ops decision queue and requires a note**; `NUMBER_INCORRECT` and `RECIPIENT_DECLINED` notify the Vendor and `CONTACT_NOT_POSSIBLE_MELARC` does not, because that failure is Melarc's own.

### The Overview: section authorization and destinations

**Approved direction (1 November 2026). Nothing here is built, and every assignment carries its status.** This is the one place that maps the Overview's sections to what each needs. It adds no permission and grants nothing: [permissions.md](../contracts/permissions.md) stays the authority for keys, grants, scopes, tiers and bundle assignments, [exception-ownership-matrix.md](../features/operations/exception-ownership-matrix.md) for who answers an exception (its *Key* column, never a role name), and [the Overview design](../design/OVERVIEW_DASHBOARD_DESIGN.md) for composition and refresh. It is a page of its own in the Today group when `SLICE-012` builds it, with no route yet (the Overview paragraph above), and the matrix adds none.

**Rules (approved requirements).**

- **One Overview, composed from what the session holds.** A section appears only when its own read is authorized. Authorization is a held permission, the scope of the grant exercised, the authority tier and any workflow restriction. No code compares a role name; the letters below are the catalogue's holders, for reading the tables.
- **Each section is its own read**, with its own permission, the scope of the grant that authorizes that read ([SECURITY_DESIGN §14.1a](../architecture/SECURITY_DESIGN.md#141a-the-context-is-bound-to-the-grant-authorizing-this-operation)), and its own freshness. The session's hints carry permission keys and hub names only (`CurrentSession`): no scope and no tier. So the page never works a section's scope out from them; it draws the scope the section's answer states. Hints guide presentation, and the server enforces every read and every act.
- **Nothing unauthorized is returned to be hidden**: no record, count, aggregate, financial figure, comparison, or total that reveals one.
- **Hub selection is a request, not authority.** All-hub authority is the scope of the one grant exercised and never widens another: a hub-limited grant stays hub-limited beside an all-hub one, and choosing "All hubs" creates no access. A section whose scope is narrower than the selection states which hubs it covers, or is unavailable. Figures of different scopes are never summed or compared as if they shared one.
- **A composite is served only when the server verifies authorization for every contributing component at the intended scope, and the approved measure definition permits their combination** (a total across domains, a comparison across hubs). No grant widens another. Otherwise show the separately authorized components, each with its scope, or omit the composite.
- **Summary, destination and act are three checks.** A summary read authorizes neither a detail page nor an act, and access to a detail page authorizes no aggregate. A figure whose destination the hints do not hold is drawn without a link; the destination enforces its own permission and scope regardless.
- **Financial information keeps its own authorization.** `report.read` authorizes only the report projections its owning specification covers, within the scope of the grant. Canonical balances and other protected financial information keep the read permissions they independently require. Every financial act or approval keeps its own permission, authority tier, scope and workflow restrictions, and Finance's approved acts are unchanged.
- **A person authorized for no section** gets the permission-restricted state ([§8](#8-the-nine-interface-states)), never *nothing is waiting*.
- **Status words.** *Confirmed*: an approved source named in the row establishes it. *Proposed*: a recommendation for the Product Owner, in force nowhere. *Unresolved*: no approved source, or the measure is undefined. An assignment that rests on one of P-1 to P-5 stays proposed or unresolved until that proposal is decided, and for P-1 until the domain's assessment is made.
- **Holders:** A Ops Staff · S Senior Ops · P Platform Admin · Fin Finance/Reconciliation · FM Fleet Manager · Exec Executive/Report-consumer. Where a row names holders of a key, they are the catalogue's approved holders of that key unless it says the bundle is `PROPOSED`. **The Executive and Auditor bundle contents are `PROPOSED`** ([permissions.md §8](../contracts/permissions.md#8-bundles)); no row relies on them, and Exec appears only as a proposed audience.

#### Proposals for the Product Owner

None is in force. P-1 to P-5 are recommendations: no permission key is added, changed or granted, nothing is built, and a row that cites one stays proposed or unresolved until the Product Owner decides it and the catalogue or the owning specification records the decision.

- **P-1. Work summaries (counts, ages and states of one domain's records).** A proposal, not an inference: no existing text says that a domain read key covers a summary, so extending one is a decision, taken domain by domain. Recommendation: reuse the existing domain read key where an assessment supports it, rather than add a key, and declare no aggregate access across the domains in one stroke. The assessment of each domain (`pickup.read`, `hub.read`, `dispatch.read`, `delivery.read`, `returns.read`, `fleet.read`, `fleet.custody.read`, and `payment.read` for a handover count) records, before any summary of it is served: (1) which counts, ages and states are covered, named one by one; (2) the grant scope and record visibility the key already has, and that a summary never reaches a record the same grant's list would not; (3) the protected fields and the information a figure could let a reader infer, such as the blind count, a small count that identifies one record, or money; (4) the workflow restrictions that apply. The result goes in the measure's data-dictionary entry and shows in its row here. A domain that does not pass stays unresolved. Separate narrow `<domain>.summary.read` keys, with the same staff holders and scopes as the key each mirrors, remain the alternative wherever summary access must be grantable apart from record access (for example for an audience that holds no record read); the Product Owner chooses per domain. **First applied by task C1** (5 November 2026): the six queue counts of `getQueueSummary` reuse `pickup.read` and `staff.read` (and, for the two approver's queues, the decision key as well), and their assessment is recorded before they are served, in [the data dictionary](../features/reporting/reporting-data-dictionary.md#55-the-queue-counts-queue-what-they-have-in-common). That is the assessment of those six counts and of nothing else: the rows below stay proposals.
- **P-2. Money-related summaries.** `report.read` authorizes only the report projections its owning specification covers, within the grant's scope. Today that is the dated daily operations and cash report (`DailyOperationsCashReport`, domain-model.md §6.13), whose holders are Senior Ops at own hub and Platform Admin and Finance at all hubs (Executive once its bundle row is signed); Ops Staff hold none, by decision (`MSC-DEC-393`). Recommendation: a dashboard money figure is authorized by `report.read` only if its data-dictionary entry places it within a projection that specification already covers. A live counterpart of the dated report, and every other money figure (outstanding obligations, items awaiting action), needs its own definition and authorization assessment and stays unresolved until then. `report.read` never reaches canonical balances or other protected financial information, which keep the permissions they independently require (`settlement.read` at the all-hub scope, `payment.read`, `vendor.read`), and never an act or approval, which keeps its own permission, authority tier, scope and workflow restrictions. A visible summary grants neither an act nor its destination. No new key.
- **P-3. Hub comparison.** Recommendation: only on a grant of the all-hub scope. An all-hub `report.read` may authorize the comparison of the report measures the data dictionary approves for comparison; it does not unlock unrelated operational or financial data, so a comparison of any other measure needs that measure's own key at the all-hub scope. Today that audience is Platform Admin and Finance, and Executive once signed. A Senior Ops sees none unless the Product Owner grants all-hub `report.read` explicitly, as §32.4 requires of company-wide export access ("explicit, not implied by ordinary Senior Ops status").
- **P-4. Vendor exposure.** All-hub `settlement.read` covers the canonical balance, statement, statement-line and adjustment records that the data-scope registry gives it (Finance and Platform Admin), and no contract operation is gated by it yet. It establishes nothing about an exposure: the allowance and limit side sits in restricted control records read through all-hub `vendor.read`, for which the registry invents no projection. Recommendation: an exposure measure needs a canonical data-dictionary definition and an authorization assessment of every record it reads, each with its own key and scope, before any audience is assigned. The only candidates are Finance and Platform Admin at the all-hub scope, and there is no hub-level exposure until `SLICE-007` defines a hub-filtered projection.

## 8. The nine interface states

| State| Requirement here|
|---|---|
| `loading`| Queue counts may load progressively; a count must never render as `0` while still loading|
| `empty`| An empty queue is a **success** message, not an error — "no intakes awaiting receive"|
| `validation error`| Field-level, with recovery guidance (§17.4)|
| `error`| Maps the machine code to copy. **Never shows the diagnostic `message`**|
| `retry`| §41.1. A failed queue load or rejected write offers an explicit retry, distinct from the error itself|
| `offline`| **N/A** — desktop web, no offline mode. Connection loss surfaces as an error, not a queue|
| `stale / conflict`| Substantive here. `STATE_CONFLICT` on a concurrent action must explain what changed, not just refuse. See §6|
| `success`| Confirms the state reached, not merely that the request succeeded|
| `permission-restricted`| Degrades to a clear refusal. §45.7: hidden buttons are not enforcement|

**A request that was too fast (`RATE_LIMITED`, `429`) has one handling for every screen** (Product Owner, 7 November 2026, A2 of the audit; the server's side, and the `Retry-After` it gives a signed-in caller, is `AC-SLICE-000-131`; the limit is the setting's, [settings.md](../contracts/settings.md) §7.7, and is not restated here):

- It is told in calm plain words, _"You're going a little fast. Try again in a few seconds."_, for every operation a signed-in person asks, and never as a fault, a lockout or a reason to leave. The screens reached before sign-in keep their own words, because their answer carries no wait.
- It holds the **automatic** reads for the wait the API asked for (`Retry-After`, whole seconds; a short wait when the header is missing or unusable and a ceiling of one minute when it is absurd): the refresh of the counts beside the menu when a page is returned to and the search as the person types are sent once when the wait ends, and the renewal of a cached read when a page opens is not made while it lasts; none is ever a retry. A read the person asks for by pressing a control, or that follows the person's own act, is never held, and the hold ends by itself.
- Nothing is tried again by itself: a `429` is never retried by the query client, and no timer re-sends a read when a hold ends.
- The command palette ([step R4](../delivery/IMPLEMENTATION_PLAN.md#3a-the-ops-portal-redesign)) shows the same words in its status line and not in an error alert.

## 9. Concurrency is a first-class interface concern

§17.4 requires **concurrency indication for sensitive work such as receiving**, and §22.8 approves an advisory soft lock showing the active receiver with takeover after an idle TTL.

**The lock is advisory and the interface must not imply otherwise.** §22.8: a visual lock alone is not sufficient. Two receivers may still submit; exactly one wins and the other gets `STATE_CONFLICT`. The screen must make that outcome comprehensible — showing who took the intake and what to do — rather than presenting a bare failure.

## 10. What this surface must never do

- **Never expose the rider-declared count before the blind count commits** (§17.3, §22.3). The awaiting-receive queue is the specific screen at risk, and the contract enforces it structurally: `HubIntakePreCount` has no such property.
- **Never leak another vendor's or an unauthorised hub's data through search** (§17.4). Search is the most common leak path because it crosses record boundaries by design.
- **Never offer bulk actions where the operation is not safe and atomic** (§17.4).
- **Never show an action a user cannot perform without explaining why**, and never rely on hiding it for control.
- **Never present a temporary hub assignment as company-wide access.**
- **Never apply the Platform Admin's maker-checker exception silently.** Where it applies (the approver is the actor who made the record, at tier P: [permissions.md §6](../contracts/permissions.md#6-maker-checker)), the screen says so in plain words, and the audit is unchanged: it records both identities. The session lists keys and no tiers, so until a record or the session carries the fact, the screen says it as the staff-profile row of §7 does: the act is offered with a note that only a Platform Admin can use it. **Open item** (Product Owner, 5 November 2026): that note is accepted as the interim, and an exact message waits for a server fact, recorded as `OB-S1-77` in [the SLICE-001 plan](../delivery/planning/SLICE-001-IMPLEMENTATION-PLAN.md#71-acceptance-obligations). Nothing is changed meanwhile.
- **Never call the API on a separate origin**. This surface is served from **`ops.<melarc-domain>`** and its browser requests go to a same-origin **`/api/...`** path. Cross-origin, the `SameSite=Lax` session cookie is not attached at all — and **the change that presents itself as the fix is a parent-domain cookie**, which would let this surface's session authenticate the Vendor PWA and back. **Cookies stay host-only.** Topology at [DEPLOYMENT_AND_ENVIRONMENTS.md](../architecture/DEPLOYMENT_AND_ENVIRONMENTS.md) §12.1.
- **Never allow itemization before receiving and reconciliation conditions are met** (§17.3).

## 11. Responsive, device baseline and accessibility

Desktop-first. Dense operational tables may optimise for desktop, but every workflow stays usable at narrower widths (§10.3, §41.2). §41.2 adds that authorised hub and all-hub dashboard and report views are role-driven. **The hub-floor tasks are the exception** (Product Owner, 5 November 2026): intake, blind count, itemization, discrepancies, and cash and parcel handovers are designed tablet-first at 768px ([DESIGN_SYSTEM.md](../design/DESIGN_SYSTEM.md#12-responsive-model)).

**§40.5 client baseline, to be defined and tested:** supported desktop browsers and the narrower responsive layouts. Accessibility conformance is `OQ-030` and §40.6. **Interim baseline for the `SLICE-000` screens — accepted by the Product Owner for Version 1, the Frontend Engineer confirming it by approving this document; narrower than §40.5 asks, and it closes neither question:** the current and previous major release of Chrome, Edge, Firefox and Safari on desktop; layouts verified at **1280 px** and **768 px**, with narrower widths usable and not optimised. **Accessibility, for every `SLICE-000` screen:** keyboard-operable with a visible focus; every input has a programmatic label and its error is associated with it; status and error messages are announced to assistive technology; nothing is conveyed by colour alone. **WCAG 2.2 level AA is the working target; it is not a conformance claim.** The bootstrap browser smoke test runs Chromium only: acceptance on the other browsers named here is future work, and that test makes no claim about it.

**§41.1 requires every user action mapped to an OpenAPI operation and an acceptance criterion.** **The operation half is done for the `SLICE-000` routes** — each names its operations in §7 — and **not for the others**; the acceptance-criterion half is part of what `OQ-030` owes.
