REFERENCE 01 / PICKUP QUEUE / REVIEW BEFORE IMPLEMENTATION

A calmer queue that keeps the work visible.

The existing screen is functional, but nine separate columns give every field similar weight and force narrow screens to scroll sideways. This proposal groups those same facts into six desktop columns and a labeled card list on narrow screens. Status and exception information remain explicit; each request opens through its operational code.

Try the state filter, clear filters, paging, refresh and request links. Resize this file to inspect the mobile layout. All records, times and interactions are synthetic. This is a design reference, not production code or acceptance evidence.

1. Existing behavior that constrains the design

  • /pickup-requests requires pickup.read; “Book a pickup” appears only with pickup.request.create. The server enforces scope. The preview assumes both permissions.
  • The current page offers state and service-date filters in the URL. Keep the existing defaults: every state, every service date. The example intentionally applies 2 November; it does not propose a new default.
  • The list response supplies records and a next-page token, not a total. The API currently orders by created_at, id ascending. Preserve that server order; do not add sorting, counts by status, search, hub filters or client-side filtering to production in this task.
  • Existing reads disable polling, automatic retry, window-focus and reconnect refetch. This protects the session activity model. Query results are discarded when unobserved (gcTime: 0). Preserve those policies.
  • Attention text follows existing attentionOf rules, including their precedence. A display grouping must not invent urgency, eligibility, blockers or new decision rules.

3. Proposal requiring approval: explicit freshness

Recommend a manual “Refresh page” action, with a last-successful-check time. Refresh the current cursor and current valid filters, without changing position or resetting to page 1. “Last checked” is the browser time when this page’s successful network read completed, formatted through the existing Accra time rules. It is not a server snapshot time, a guarantee that the whole queue is current, or a claim that all pages were checked.

  • Initial read: loading indicator and skeleton, no count and no fabricated timestamp. Success includes an empty result: it was still checked. Filtering or paging clears the displayed timestamp until that specific query succeeds.
  • Refresh: keep the refresh button mounted and focusable with loading/disabled semantics; prevent duplicate requests. Mark results busy and temporarily replace rows with the existing loading treatment. This intentionally avoids presenting old rows as the result of an in-flight read.
  • Successful refresh: show the replacement page and update its time. Keep focus on the refresh control unless the user moved elsewhere. Announce a short completion message once.
  • Failed refresh: show the existing read failure and allowed recovery action. Remove the rows; never show old results beside failure. Say “Refresh failed. Last successful check: [time]” when available, with no implication that results remain current. Ordinary retry follows existing unavailable/rate-limit rules.
  • Offline: show the existing connection/read failure treatment, with manual retry. A browser connectivity hint alone is not evidence that the API is unreachable. Reconnection does not trigger a request.

Alternative: polling or refetch-on-focus would update without a click, but changes the deliberate session/activity policy and may shift results unexpectedly. It is outside this proposal. Refreshing page 1 is another explicit navigation action, not an undisclosed side effect of “Refresh page”.

4. Proposal requiring approval: return to the same working context

Recommend short-lived, in-memory queue context for a same-tab queue → record → queue visit. Filters remain in the URL. Keep only the cursor stack, page number, scroll position and originating record identifier in authenticated application memory; keep no response records, sender names, addresses or rendered snapshots. This changes the lifetime of navigation metadata, not the existing query-cache policy.

  • Bind the context to the signed-in session, authorized-hub scope, queue and normalized filters. Clear it on session end/replacement, relevant scope change, filter change, explicit first-page reset, full reload or navigation outside the queue/record visit. It never grants access.
  • Browser Back and the record’s “Back to pickup requests” link restore that context. Re-read the saved cursor with the existing API; do not paint a cached queue. No cursor in the URL, localStorage or sessionStorage. A direct record link, new tab or lost context returns to page 1 using valid available filters.
  • A record action may make it leave the filtered queue. After the fresh read, restore focus to the originating request link if still present; otherwise to the results heading/region. Restore scroll after layout, clamped to available content, and keep the focus target visible. Do not steal focus if the officer moved it during the read.
  • A later-page read can now be empty. Say “No requests on this page” and offer “Back to first page”; do not say the entire queue is empty or automatically scan earlier pages. A rejected cursor must show its actual failure and an explicit first-page recovery, not silently change filters.
  • This is continuity of place, not a frozen result set. Records can move or disappear. Preserve the server’s order and authorization decisions; do not promise identical rows.

This explicitly amends COMPONENT_PATTERNS §22f and the hook comment that currently describes a page as “not a place to come back to.” Retain the prohibition on URL/persistent cursor storage. Alternative: URL cursors are shareable but expose internal navigation metadata and imply durable queue positions; persistent storage extends their lifetime without a current requirement. Keeping rows mounted or cached would retain business data and needs a separate decision.

5. Responsive and accessible behavior

  • Wide screens: six-column semantic table, request code as the row header, subtle separators and existing approved typography and spacing. The composition is spacious; the data is compact. No fixed row height: long names, addresses and attention labels must wrap.
  • Narrow screens: render the same records as one labeled list of cards. Order: code and state; sender; service date; pickup address and hub; packages and booking intent; attention note. Do not hide operational facts or make horizontal scrolling the normal phone workflow.
  • Use the repository breakpoint tokens when implementing. The prototype switches at 760px only to demonstrate the treatment; that number is not a new approved token. At constrained intermediate widths or enlarged text, switch before the columns become unreadable.
  • Expose only one representation at a time to assistive technology and keyboard navigation. Keep record links usable with normal modifier-click and new-tab behavior. Do not make entire rows clickable or add redundant “View” links.
  • Pagination must park focus safely while loading and land on the new results afterward, including empty/error responses. Filter changes keep focus on their controls; update announcements once without repeatedly announcing the whole table.
  • Refresh/retry controls must not unmount beneath focus. Respect user-moved focus. Test keyboard, 320px, 200% text, forced colors and reduced motion, and changed browser cases as required by the repository. Automated checks do not establish screen-reader acceptance.

7. Engineering boundaries and next task

Use PageHeader, existing controls, ReadState, QueueTable, StatusBadge and local wrappers. Keep wire types generated. Extract a pickup-specific row presentation model only if useful; derive it from the already-parsed record and existing mappings. Do not introduce a grid dependency or a configurable universal page engine.

Implement in two bounded tasks after this design is approved.

  1. Queue presentation: grouped desktop columns, mobile cards, shorter page copy and existing interface states. Preserve fetching, paging lifetime, URL defaults, permissions and attention rules. Record this concrete implemented pattern in the owning docs. Target layout, responsive and accessibility checks.
  2. Queue freshness and continuity: implement the two approved behavior proposals, update §22f and affected surface/plan text, and cover session/scope cleanup, return after record change, cursor failure/empty-page recovery, focus and refresh outcomes. Validate the query and navigation changes with targeted tests. Report the affected selector’s breadth; do not run the full gate unasked.

Approve the visual direction and the two behavior proposals before issuing either implementation task. Claude should receive only the first task initially. No application code, dependency, contract or repository design document was edited to produce this reference.
